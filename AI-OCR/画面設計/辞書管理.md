# 辞書管理画面 パターン比較

AI-OCR 製品(ABBYY / UiPath / Azure Document Intelligence /
Google Document AI / DX Suite など)を調査すると、辞書管理画面には
共通して以下の情報が必要となる。

最近の AI-OCR では:

```text
「誤字修正辞書」
```

だけではなく、

```text
「OCR後処理ルールエンジン」
```

として設計されている。

---

# 凡例

各セクションで使う見出しの意味:

- **必須情報**
  - 辞書管理画面に存在する/載せるべき項目
- **関連実装(他画面)**
  - 辞書管理画面外で既に実装されている関連機能(参考用)
- **将来要件**
  - 辞書管理画面に追加する予定/検討中の機能
- **注意事項**
  - 実装上の制約・設計上の前提・既知の挙動など、画面利用時の留意点

---

# 辞書管理画面に必要な画面情報

---

## 1. 辞書一覧(最重要)

### 必須情報

- 辞書名 + 「(システム)」ラベル
  - システム辞書は編集不可、ユーザー辞書のみ削除可
- エントリ数(「N エントリ」表示)
- 適用範囲表示
  - 領域辞書: 「N 領域」(青色)
  - 共通辞書: 「共通」(灰色)
- 一覧アクション
  - 新規 / 名前変更 / 削除

### 将来要件

- 辞書カテゴリの表示・分類
  - OCR 補正 / 正規化 / Regex / 数値補正
  - 現状はマッチタイプ(EXACT / REGEX / FUZZY)がエントリ単位の属性のみ
- 辞書単位の有効/無効トグル
  - 現状はエントリ単位のみ
- 辞書単位の優先順位
  - 現状はエントリ単位のみ
- 適用件数(統計)
- 更新日時の一覧表示
  - モデル保持済(`UpdatedAt`)
- 更新者
  - ユーザー識別の仕組みが現状なし
- 辞書のドラッグ並べ替え
- 辞書複製・テンプレート化

### 注意事項

- システム辞書とユーザー辞書の 2 種類があり、システム辞書は名前変更・削除不可
  - ただしシステム辞書にもエントリは追加可能

---

## 2. 辞書エントリ管理

### 必須情報

- パターン
  - マッチタイプに応じて文字列 or 正規表現
- 置換テキスト
- マッチタイプ
  - 完全一致 (`EXACT`) / 正規表現 (`REGEX`) / あいまい (`FUZZY`)
- 優先度(数値、大きいほど優先)
- 大文字小文字の区別フラグ
- 説明(複数行入力、コメント相当)
- 有効/無効トグル
  - DataGrid のチェックボックスでインライン切替
- DataGrid 表示列
  - 有効 / パターン / 置換 / タイプ / 優先度

### 将来要件

- タグ
  - モデル / API にフィールドが現状無い
- 一括 CSV インポート
- 重複エントリ検出
- 表記揺れの自動検出

### 注意事項

- マッチタイプ「あいまい (`FUZZY`)」は Levenshtein 編集距離ベースの単語置換
  - 閾値はパイプライン側で固定値

---

## 3. 適用範囲設定

### 必須情報

- Template 選択(ComboBox)
- Minimap 表示
  - テンプレート画像と領域オーバーレイをサムネイル表示
  - クリックで領域への割当をトグル
- 適用領域一覧
  - 割当済の領域を青ドット + 名前で表示
- 共通適用モード
  - 領域未割当時は「共通適用(全テキスト)」と表示
  - 全テキストブロックに対して辞書を適用

### 関連実装(他画面)

- テンプレートとの連動はテンプレート管理.md セクション 4 の `DictionaryIds` フィールドを介して行う
  - 領域(`TemplateRegion`)に紐付く形で永続化

### 将来要件

- 帳票種別での絞り込み
  - テンプレート管理.md セクション 3 の `category` 追加と連動
- 項目名単位の適用
  - テキストブロックが項目構造を持たないため、結果確認.md セクション 3 と連動
- OCR Engine 別の適用
- confidence 条件
  - 信頼度が閾値未満のときだけ適用する仕組み
- タグによるグループ適用
- 条件式による動的適用

### 注意事項

- AI-OCR では「全文共通補正」だけでは弱く、
  「請求金額だけ補正」のようなフィールド単位の絞り込みが必須
- 現状の適用範囲は **Template + 領域 ID 単位** のみで、bbox 座標による直接指定は不可

---

## 4. テストエリア

### 必須情報

なし。本画面ではテスト入力機能を持たない。
辞書の効果確認は OCR 実行 → 結果確認の往復で行う必要がある。

### 関連実装(他画面/共通基盤)

- パイプライン内の補正処理は `TextPostprocessor`
  - 優先度順にエントリを適用
  - EXACT / REGEX / FUZZY の各マッチ処理
  - REGEX エラーは `re.error` をログ警告のみ(クライアントに返さない)

### 将来要件

- テスト入力エリア
  - 任意のテキストを入力して修正結果を即時確認
- Regex 検証
  - 正規表現のマッチ結果と置換結果を表示
- 適用辞書 / エントリの表示
  - どの辞書のどのエントリにマッチしたかを可視化
- 複数エントリヒット時の適用順序可視化
- 期待値との差分表示(回帰テスト)

### 注意事項

- Regex は誤マッチが業務影響に直結するため、テスト機能の常設化が望ましい
- 現状は本番運用前の Regex 検証手段が無く、辞書追加時のリスクが大きい

---

## 5. OCR 信頼度条件

### 必須情報

なし。本画面では信頼度条件を持たない。
`TextPostprocessor` は信頼度に関係なく一律適用する設計。

### 関連実装(他画面/共通基盤)

- 共通 `Confidence` VO は実装済(OCR 実行.md / 結果確認.md セクション 5 参照)
  - 閾値: 高 (≥0.9) / 中 (≥0.7) / 低 (<0.7) / 不明
- 信頼度表示と色分けは結果確認画面の bbox オーバーレイで実装済

### 将来要件

- 辞書 / エントリ単位の confidence 閾値
  - 「信頼度がこの値未満のときだけ適用」フラグ
- Provider 別の閾値設定
- 閾値の bbox 色分け連動

### 注意事項

- 共通 `Confidence` VO が既にあるため、閾値判定ロジック自体は流用可能
  - パイプライン側で適用条件を判定する変更が必要

---

## 6. 適用履歴・統計

### 必須情報

なし。本画面では適用履歴・統計を持たない。

### 関連実装(他画面/共通基盤)

- パイプラインの `TextPostprocessor` は適用ごとに `CorrectionResult` を返す
  - 適用前後のテキスト、ヒットしたエントリ情報を持つ
  - ただし **永続化や集計はしていない** ため統計には未利用

### 将来要件

- 辞書 / エントリ単位の適用回数集計
- 最終適用日時
- 適用前後の文字数差分などからの改善率指標
- Error 件数(Regex 失敗・想定外置換)
- エントリ別ヒット数のグラフ表示
- ヒット 0 エントリの検出
  - 陳腐化辞書のクリーンアップに使う

### 注意事項

- `CorrectionResult` は既にパイプライン内で生成されているため、永続化基盤を追加すれば統計化は比較的低コスト

---

## 7. Import / Export

### 必須情報

なし。本画面では Import / Export 機能を持たない。
辞書とエントリの登録は API 経由の個別 CRUD のみ。

### 関連実装(他画面)

- 辞書とエントリの API は CRUD のみ
  - `POST /v1/dictionaries` / `POST /v1/dictionaries/{id}/entries`
  - 一括投入の専用エンドポイントはなし

### 将来要件

- CSV Import / Export
  - 大量エントリの一括管理
  - 表計算ソフトでの編集サポート
- JSON Export
  - 辞書定義のバックアップ・移送
- 一括登録 UI
- 差分インポート(既存マージ)
- インポート前のドライラン
  - 重複エントリの検出と確認

### 注意事項

- 現状は GUI からの 1 件ずつ登録のみで、大量辞書の構築には不向き
- 初期辞書は `scripts/init/dictionaries.json` 経由で投入する設計
  - 運用後の追加は CRUD のみ

---

## 8. バージョン管理

### 必須情報

なし。本画面ではバージョン管理機能を持たない。
現状は `UpdatedAt`(最終更新日時)のみ保持。

### 関連実装(他画面/共通基盤)

- 辞書のアーカイブ機構(ソフトデリート)
  - `ArchiveDictionaryUseCase` + `t_dictionary_archived` テーブル
  - `archived_at` を記録
- ※「復元」UI は未実装だが、Rollback の基盤として活用可能

### 将来要件

- Version 番号
- 更新履歴
  - 過去状態のスナップショット保存
- 差分比較
- Rollback(過去版への復元)
  - アーカイブ機構の延長として実装可能
- ブランチ機能(本番/検証の並走)
- 承認フロー
  - ユーザー識別の仕組み(現状なし)とセットで設計が必要

### 注意事項

- OCR 運用監査対応として、辞書の変更履歴は最低限保持したい
- 現状の `UpdatedAt` で「いつ変更したか」は分かるが、
  「何を変更したか」「以前の状態は何か」は記録されない
- テンプレート管理.md セクション 9 と同じ設計方針

---

## 9. エラー表示

### 必須情報

- 画面全体エラーメッセージバナー
  - `ErrorMessage` バインド + ClearError ボタン
  - `DictionaryManagerView.xaml:491-517`

### 関連実装(他画面/共通基盤)

- 共通 `ErrorHandler` / `ErrorCategory`(OCR 実行.md セクション 10)
  - 本画面では未活用、raw メッセージ表示のみ
- パイプラインの Regex エラーハンドリング
  - `TextPostprocessor` で `re.error` を catch してログ警告
  - クライアントには伝わらず、エントリ作成時の検証もなし

### 将来要件

- Regex Error の事前検証
  - エントリ追加時にパターンをコンパイルして UI に即時エラー表示
- 重複 Rule 検出
  - 同一パターン + マッチタイプの重複検知
- 無限置換警告
  - 置換結果が再度マッチして無限ループになるパターンの検出
- 適用競合の検出と解消提案
  - 優先度が同じで結果が衝突するエントリの警告
- カテゴリ別エラー表示
  - 共通 `ErrorHandler` を経由した構造化表示

### 注意事項

- 現状の Regex 不正は **保存時もパイプライン実行時も静かに失敗** する
  - 入力されてしまうと OCR 結果に補正が一切効かないため、検証は重要
- 共通 `ErrorHandler` 基盤未活用は他画面と同じ課題

---

## 10. Provider 別設定

### 必須情報

なし。本画面では Provider 別の辞書設定を持たない。
`TextPostprocessor` は OCR Provider に関係なく一律適用する設計。

### 関連実装(他画面)

- OCR Provider 自体は OCR 実行.md セクション 2 で seed 済
  - azure / google / paddleocr / yomitoku / gemini / qwen
- Provider 別の誤認識傾向は把握できる

### 将来要件

- Provider 別の辞書振り分け
  - 「この辞書は Azure 専用」「この辞書は全 Provider 共通」のような指定
- Provider 切替時の自動適用
- Provider 別の優先度
- Provider 別誤認識傾向の統計
  - 適用履歴(セクション 6)と連動

### 注意事項

- Provider ごとに誤認識傾向が異なるため、共通辞書と Provider 別辞書の併用が望ましい
- 現状は全 Provider 共通の辞書プールで運用する設計

# 辞書管理画面の代表的な画面分割

現在の実装状況・将来要件・AI-OCR 製品の実例を踏まえ、
辞書管理画面のレイアウト案を以下の 2 軸 × 3 パターンで整理する。

- **将来設計なし版**(現実装寄り) … パターン①〜③
- **将来設計あり版**(AI-OCR 完成系寄り) … パターン④〜⑥

辞書管理は単なる「誤変換置換」ではなく、
**OCR 後処理ルールエンジン** として考える必要がある。

---

## 前提整理

現在の設計は、辞書 / エントリ / 適用範囲 / Template 連携 / Regex / Priority が
綺麗に分離されており、かなり `UiPath + ABBYY` 寄りの AI-OCR 設計。

| 方針 | 評価 |
| ---- | -- |
| 左:辞書一覧 | ◎ |
| 中央:エントリ一覧 | ◎ |
| 右:適用範囲 | ◎ |
| Template / 領域連携 | ◎ |
| Regex / MatchType / Priority | ◎ |

# 最終推奨

現在の設計思想なら:

```text
パターン①
+
Regex Preview
+
適用範囲可視化
```

が最も合っている。

## 理由

現在の設計では:

```text
辞書
↓
エントリ
↓
適用範囲
↓
OCR
↓
結果確認
```

という責務分離がかなり綺麗。

そのため:

- 左:辞書
- 中央:Rule
- 右:適用範囲

を維持した方が、

- OCR 補正管理
- Template 連携
- Regex 運用
- Provider 別制御
- 将来の AI 学習

に対応しやすくなる。
