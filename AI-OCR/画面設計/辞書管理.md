> 内部値と画面表記の対応は [用語集.md](用語集.md) を参照。

各セクションで使う見出しの意味:

# 辞書管理画面に必要な画面情報

---

## 1. 辞書一覧(最重要)

### 必須情報

- 辞書名 + 「(システム)」ラベル
  - システム辞書は編集不可、ユーザー辞書のみ削除可
- エントリ数(「N エントリ」表示)
- 適用範囲表示
  - 領域辞書: 「N 領域」(青色)
  - 共通辞書: 「共通」(灰色)
- 一覧アクション
  - 新規 / 名前変更 / 削除

### 将来要件

- 辞書カテゴリの表示・分類
  - OCR 補正 / 正規化 / Regex / 数値補正
  - 現状はマッチタイプ(EXACT / REGEX / FUZZY)がエントリ単位の属性のみ
- 辞書単位の有効/無効トグル
  - 現状はエントリ単位のみ
- 辞書単位の優先順位
  - 現状はエントリ単位のみ
- 適用件数(統計)
- 更新日時の一覧表示
  - モデル保持済(`UpdatedAt`)
- 更新者
  - ユーザー識別の仕組みが現状なし
- 辞書のドラッグ並べ替え
- 辞書複製・テンプレート化

### 注意事項

- システム辞書とユーザー辞書の 2 種類があり、システム辞書は名前変更・削除不可
  - ただしシステム辞書にもエントリは追加可能

---

## 2. 辞書エントリ管理

### 必須情報

- パターン
  - マッチタイプに応じて文字列 or 正規表現
- 置換テキスト
- マッチタイプ
  - 完全一致 (`EXACT`) / 正規表現 (`REGEX`) / あいまい (`FUZZY`)
- 優先度(数値、大きいほど優先)
- 大文字小文字の扱い(`case_mode`: `sensitive` / `insensitive`)
  - SDK 側は `bool CaseSensitive`、API/DB 側は文字列で持ち、相互変換は SDK で実施
    (`DictionaryGatewayAdapter.cs:184, 296`)
- 説明(複数行入力、コメント相当)
- DataGrid 表示列
  - パターン / 置換 / タイプ / 優先度
  - 先頭の「有効」チェックボックス列は描画されるが現状は永続化されない(将来要件参照)

### 関連実装(他画面/共通基盤)

- エントリ無効化の DB 基盤
  - `t_dictionary_entry_disabled` テーブル(`dictionary_models.py:163-180`)
  - 読み出し時の除外フィルタ(`dictionary_repository_impl.py:94-103, 200-201`)
  - ※書き込みを行う UseCase / API エンドポイントが無いため、現状は孤立基盤。
    Enabled トグル完成時に活用可能
- 校正(`proofreading`)モジュール
  - LLM ベースの別系統で、本辞書テーブル(`dictionary_id`)を参照しない
  - OCR 実行画面の「校正(`ProofreadingId`)」と「辞書補正」は別概念

### 将来要件

- エントリ単位の有効/無効トグル
  - UI は実装済(`DictionaryManagerView.xaml:297` の DataGrid 列、
    `DictionaryManagerViewModel.cs:705-723` の `ToggleEntryEnabledCommand`)
  - API `EntryResponse` / `UpdateEntryRequest` に `enabled` フィールド無し、
    SDK の `UpdateEntryAsync(... bool? enabled)` 引数は「未使用」コメント付きで送信されない
    (`DictionaryGatewayAdapter.cs:164, 176-187`)
  - `MapToEntry` が `Enabled = true` をハードコード(`DictionaryGatewayAdapter.cs:290-300`)
  - 完成には API の `enabled` フィールド追加 + SDK の `enabled` 引数を実送信に変更 +
    無効化 UseCase 追加が必要
- 既存エントリのインライン編集 / 編集ダイアログ
  - `UpdateEntryAsync` は実装済だが、ViewModel から呼ばれるのは Toggle 経由のみ
- 辞書種別(`dictionary_type`)の作成時指定 UI
  - API `CreateDictionaryRequest.dictionary_type` は受け付けるが、画面からは常に `user` で作成
- 画面側の入力長バリデーション
  - API 側の `name` 100 / `description` 500 / `pattern`,`replacement` 1000 /
    `priority` 0-1000 を画面側でも先行検証
- タグ
  - モデル / API にフィールドが現状無い
- 一括 CSV インポート
- 重複エントリ検出
- 表記揺れの自動検出

### 注意事項

- マッチタイプ「あいまい (`FUZZY`)」は Levenshtein 編集距離ベースの単語置換
  - 閾値はパイプライン側で固定値

---

## 3. 適用範囲設定

### 必須情報

- Template 選択(ComboBox)
- Minimap 表示
  - テンプレート画像と領域オーバーレイをサムネイル表示
  - クリックで領域への割当をトグル
- 適用領域一覧
  - 割当済の領域を青ドット + 名前で表示
- 共通適用モード
  - 領域未割当時は「共通適用(全テキスト)」と表示
  - 全テキストブロックに対して辞書を適用

### 関連実装(他画面)

- テンプレートとの連動は `TemplateRegion.DictionaryIds` フィールドを介して行う
  - 領域に紐付く形で永続化

### 将来要件

- 帳票種別での絞り込み
  - テンプレート側に `category` フィールド追加が前提
- 項目名単位の適用
  - テキストブロックが項目構造を持たないため、結果側の項目化が前提
- OCR Engine 別の適用
- confidence 条件
  - 信頼度が閾値未満のときだけ適用する仕組み
- タグによるグループ適用
- 条件式による動的適用

### 注意事項

- AI-OCR では「全文共通補正」だけでは弱く、
  「請求金額だけ補正」のようなフィールド単位の絞り込みが必須
- 現状の適用範囲は **Template + 領域 ID 単位** のみで、bbox 座標による直接指定は不可

---

## 4. テストエリア

### 必須情報

なし。本画面ではテスト入力機能を持たない。
辞書の効果確認は OCR 実行 → 結果確認の往復で行う必要がある。

### 関連実装(他画面/共通基盤)

- パイプライン内の補正処理は `TextPostprocessor`
  - 優先度順にエントリを適用
  - EXACT / REGEX / FUZZY の各マッチ処理
  - REGEX エラーは `re.error` をログ警告のみ(クライアントに返さない)

### 将来要件

- テスト入力エリア
  - 任意のテキストを入力して修正結果を即時確認
- Regex 検証
  - 正規表現のマッチ結果と置換結果を表示
- 適用辞書 / エントリの表示
  - どの辞書のどのエントリにマッチしたかを可視化
- 複数エントリヒット時の適用順序可視化
- 期待値との差分表示(回帰テスト)

### 注意事項

- Regex は誤マッチが業務影響に直結するため、テスト機能の常設化が望ましい
- 現状は本番運用前の Regex 検証手段が無く、辞書追加時のリスクが大きい

---

## 5. OCR 信頼度条件

### 必須情報

なし。本画面では信頼度条件を持たない。
`TextPostprocessor` は信頼度に関係なく一律適用する設計。

### 関連実装(他画面/共通基盤)

- 共通 `Confidence` VO は実装済
  - 閾値: 高 (≥0.9) / 中 (≥0.7) / 低 (<0.7) / 不明
- 信頼度表示と色分けは結果確認画面の bbox オーバーレイで実装済

### 将来要件

- 辞書 / エントリ単位の confidence 閾値
  - 「信頼度がこの値未満のときだけ適用」フラグ
- Provider 別の閾値設定
- 閾値の bbox 色分け連動

### 注意事項

- 共通 `Confidence` VO が既にあるため、閾値判定ロジック自体は流用可能
  - パイプライン側で適用条件を判定する変更が必要

---

## 6. 適用履歴・統計

### 必須情報

なし。本画面では適用履歴・統計を持たない。

### 関連実装(他画面/共通基盤)

- パイプラインの `TextPostprocessor` は適用ごとに `CorrectionResult` を返す
  - 適用前後のテキスト、ヒットしたエントリ情報を持つ
  - ただし **永続化や集計はしていない** ため統計には未利用

### 将来要件

- 辞書 / エントリ単位の適用回数集計
- 最終適用日時
- 適用前後の文字数差分などからの改善率指標
- Error 件数(Regex 失敗・想定外置換)
- エントリ別ヒット数のグラフ表示
- ヒット 0 エントリの検出
  - 陳腐化辞書のクリーンアップに使う

### 注意事項

- `CorrectionResult` は既にパイプライン内で生成されているため、永続化基盤を追加すれば統計化は比較的低コスト

---

## 7. Import / Export

### 必須情報

なし。本画面では Import / Export 機能を持たない。
辞書とエントリの登録は API 経由の個別 CRUD のみ。

### 関連実装(他画面)

- 辞書とエントリの API は CRUD のみ
  - `POST /v1/dictionaries` / `POST /v1/dictionaries/{id}/entries`
  - 一括投入の専用エンドポイントはなし

### 将来要件

- CSV Import / Export
  - 大量エントリの一括管理
  - 表計算ソフトでの編集サポート
- JSON Export
  - 辞書定義のバックアップ・移送
- 一括登録 UI
- 差分インポート(既存マージ)
- インポート前のドライラン
  - 重複エントリの検出と確認

### 注意事項

- 現状は GUI からの 1 件ずつ登録のみで、大量辞書の構築には不向き
- 初期辞書は `scripts/init/dictionaries.json` 経由で投入する設計
  - 運用後の追加は CRUD のみ

---

## 8. バージョン管理

### 必須情報

なし。本画面ではバージョン管理機能を持たない。
現状は `UpdatedAt`(最終更新日時)のみ保持。

### 関連実装(他画面/共通基盤)

- 辞書のアーカイブ機構(ソフトデリート)
  - `ArchiveDictionaryUseCase` + `t_dictionary_archived` テーブル
  - `archived_at` を記録
- ※「復元」UI は未実装だが、Rollback の基盤として活用可能

### 将来要件

- Version 番号
- 更新履歴
  - 過去状態のスナップショット保存
- 差分比較
- Rollback(過去版への復元)
  - アーカイブ機構の延長として実装可能
- ブランチ機能(本番/検証の並走)
- 承認フロー
  - ユーザー識別の仕組み(現状なし)とセットで設計が必要

### 注意事項

- OCR 運用監査対応として、辞書の変更履歴は最低限保持したい
- 現状の `UpdatedAt` で「いつ変更したか」は分かるが、
  「何を変更したか」「以前の状態は何か」は記録されない

---

## 9. エラー表示

### 必須情報

- 画面全体エラーメッセージバナー
  - `ErrorMessage` バインド + ClearError ボタン
  - `DictionaryManagerView.xaml:491-517`

### 関連実装(他画面/共通基盤)

- 共通 `ErrorHandler` / `ErrorCategory`
  - 本画面では未活用、raw メッセージ表示のみ
- パイプラインの Regex エラーハンドリング
  - `TextPostprocessor` で `re.error` を catch してログ警告
  - クライアントには伝わらず、エントリ作成時の検証もなし

### 将来要件

- Regex Error の事前検証
  - エントリ追加時にパターンをコンパイルして UI に即時エラー表示
- 重複 Rule 検出
  - 同一パターン + マッチタイプの重複検知
- 無限置換警告
  - 置換結果が再度マッチして無限ループになるパターンの検出
- 適用競合の検出と解消提案
  - 優先度が同じで結果が衝突するエントリの警告
- カテゴリ別エラー表示
  - 共通 `ErrorHandler` を経由した構造化表示

### 注意事項

- 現状の Regex 不正は **保存時もパイプライン実行時も静かに失敗** する
  - 入力されてしまうと OCR 結果に補正が一切効かないため、検証は重要
- 共通 `ErrorHandler` 基盤未活用は他画面と同じ課題

## 10. Provider 別設定

### 必須情報

なし。本画面では Provider 別の辞書設定を持たない。
`TextPostprocessor` は OCR Provider に関係なく一律適用する設計。

### 関連実装(他画面)

- OCR Provider は seed 済 (実装登録順: `engine_registry.py:27-34`)
  - mock / azure / google / paddleocr / yomitoku / gemini (pro + flash-lite) / qwen
  - Engine 総数 8 / Provider 総数 7
  - クレデンシャル必須は azure / google / yomitoku のみ (`ProviderCredentialMap.cs:23-43`)
- Provider 別の誤認識傾向は把握できる

### 将来要件

- Provider 別の辞書振り分け
  - 「この辞書は Azure 専用」「この辞書は全 Provider 共通」のような指定
- Provider 切替時の自動適用
- Provider 別の優先度
- Provider 別誤認識傾向の統計
  - 適用履歴(セクション 6)と連動

### 注意事項

- Provider ごとに誤認識傾向が異なるため、共通辞書と Provider 別辞書の併用が望ましい
- 現状は全 Provider 共通の辞書プールで運用する設計

# 辞書管理画面の代表的な画面分割

現在の実装状況・将来要件・AI-OCR 製品の実例を踏まえ、
辞書管理画面のレイアウト案を以下の 3 パターンで整理する。

- **将来設計なし版**(現実装寄り) … パターン①〜②
- **将来設計あり版**(AI-OCR 完成系寄り) … パターン③

辞書管理は単なる「誤変換置換」ではなく、
**OCR 後処理ルールエンジン** として考える必要がある。

---

## 前提整理

現在の設計は、辞書 / エントリ / 適用範囲 / Template 連携 / Regex / Priority が
綺麗に分離されており、かなり `UiPath + ABBYY` 寄りの AI-OCR 設計。

| 方針 | 評価 |
| ---- | -- |
| 左:辞書一覧 | ◎ |
| 中央:エントリ一覧 | ◎ |
| 右:適用範囲 | ◎ |
| Template / 領域連携 | ◎ |
| Regex / MatchType / Priority | ◎ |

# 将来設計なし版(現実装ベース)

---

## パターン① シンプル3ペイン型(最推奨)

現在の構成をそのまま強化。辞書一覧/エントリ一覧/適用領域設定を 3ペインで配置し、
辞書/エントリの編集はモーダルダイアログで開く現実装の動線を維持する。

### 画面図

```text
┌──────────────────┬───────────────────────────────┬────────────────┐
│ 辞書一覧         │ エントリ一覧 - 請求書補正     │ 適用領域設定   │
│                  │                       ＋ ×    │                │
│ 請求書補正       │                               │ テンプレート:  │
│   25 エントリ    │ ☑ パターン  置換  タイプ 優先 │ [請求書    v]  │
│   3 領域         │ ────────────────────────────  │                │
│                  │ ☑ 100O      1000  FUZZY  90   │ ┌────────────┐ │
│ 金額補正         │ ☑ 東〒京    東京  EXACT  100  │ │ ミニマップ │ │
│   12 エントリ    │ ☐ ltem      Item  REGEX  80   │ │ 画像+領域  │ │
│   共通           │                               │ │ bboxオーバ │ │
│                  │                               │ │ ーレイ     │ │
│ システム辞書     │                               │ └────────────┘ │
│   (システム)     │                               │                │
│   142 エントリ   │                               │ 適用領域:      │
│   共通           │                               │ ・会社名       │
│                  │                               │ ・請求金額     │
│ ＋ ✎ ×           │                               │                │
└──────────────────┴───────────────────────────────┴────────────────┘

凡例:
  辞書一覧 下の ＋/✎/× = 新規辞書/名前変更/削除 (アーカイブ、モーダル)
  ※ 「(システム)」ラベル付き辞書は名前変更・削除不可 (エントリ追加は可)
  ※ 辞書下の表示: 「N エントリ」 + 「N 領域」(青) or 「共通」(灰)
  エントリ一覧:
    ヘッダーに選択中の辞書名を表示
    右上 ＋/× = 新規エントリ追加(モーダル)/エントリ削除
    「有効」列 ☑ = ⚠️ 既知不具合: クリックは検知されるが API/SDK の修正不足により
      **永続化されない** (再読込で必ず ☑ に戻る)
      DB テーブル `t_dictionary_entry_disabled` と読み出しフィルタは存在するが、
      書き込み UseCase が未実装 (Section 2 将来要件「エントリ単位の有効/無効トグル」)
      対応: API `EntryResponse.enabled` 追加 + SDK 引数の実送信 + 無効化 UseCase の追加
  適用領域設定:
    テンプレート選択 ComboBox の先頭は「共通」項目
    ミニマップ上の領域 bbox をクリックで割当をトグル → 即時保存
    共通辞書/未選択時はミニマップ非表示で「テンプレートを選択すると...」を代替表示
  空状態:
    辞書なし → 「辞書がありません」
    エントリなし → 「エントリがありません」
    辞書未選択 → 「辞書を選択してエントリを追加してください」
```

# 一押しのパターン

## 短期 (即時実装) → パターン① シンプル3ペイン型(最推奨)

### 理由

- **現実装そのまま**、改修コストゼロ
- 辞書 / エントリ / 適用範囲を **3ペインで同時表示** し、辞書編集の3大タスク (辞書選択・エントリ管理・領域割当) を画面遷移なしで完結
- 辞書の **「N 領域」/「共通」表示** で適用範囲が一目でわかる
- **ミニマップでの領域割当トグル** が直感的 (クリックで即時保存)
- システム辞書とユーザー辞書を「(システム)」ラベルで視覚的に区別
- 12/12 責務完全カバー
- 編集 (新規辞書/名前変更/新規エントリ) は **モーダル**で、誤操作リスク低い

### 既知不具合 (画面構造の変更は不要)

エントリの「Enabled トグル」(☑ 有効) は ⚠️ **永続化されない既知不具合**。
画面上はチェックを操作できるが、再読込で必ず ☑ に戻る。
API/SDK の修正で対応可能 (画面構造の変更不要、Section 2 将来要件、任意タスク)。

## 長期 (将来ゴール) → パターン③ 3ペイン + 中央縦分割型(運用統合完成系)

中央を縦分割して **エントリ一覧と適用統計を同時表示**。
- 各エントリの **適用回数 (24h)** が DataGrid 列に表示される
- **陳腐化エントリ** (ヒット数 0) を検出してクリーンアップ可能
- 辞書一覧に **最終更新日時** が表示される (Section 1 将来要件)
- 精度改善 PDCA サイクルを画面内で可視化
