# 設定画面 パターン比較

以下に、AI-OCRで実際にあり得る
設定画面の構成案を複数提示します。

> 共通用語 (JobStatus / ReviewStatus / Provider / 対応ファイル形式 等) の
> 内部値と画面表記の対応は [用語集.md](用語集.md) を参照。

---

# 凡例

各セクションで使う見出しの意味:

- **必須情報**
  - 設定画面に存在する/載せるべき項目
- **関連実装(他画面)**
  - 設定画面外で既に実装されている関連機能(参考用)
- **将来要件**
  - 設定画面に追加する予定/検討中の機能
- **注意事項**
  - 実装上の制約・設計上の前提・既知の挙動など、画面利用時の留意点

# 設定画面に必要な画面情報

---

## 1. OCR Provider 設定(最重要)

### 必須情報

- Azure 認証情報
  - API Key (PasswordBox) / Endpoint
- Google 認証情報
  - Service Account JSON (ファイル選択) / Project ID / Location / Processor ID
- YomiToku 認証情報
  - License Key (開発モードでは不要)
- PaddleOCR
  - 認証情報不要(ローカルエンジン)
- 各エンジンの有効化トグル(`AzureEnabled` / `GoogleEnabled` / `PaddleOcrEnabled` / `YomiTokuEnabled`)
- 接続テスト
  - API エンドポイントの到達性確認
  - 成功/失敗の色分けバナーで結果表示
- DPAPI による認証情報の暗号化保管

### 関連実装(他画面)

- Provider / Engine 一覧はサーバー側の `scripts/init/engines.json` に依存
- seed/API 登録: mock / azure / google / paddleocr / yomitoku / gemini / qwen
- ⚠️ WPF から実行可: azure / google / yomitoku / mock / paddleocr のみ
  (gemini/qwen は `ProviderCredentialMap.cs` 未対応)

### 将来要件

- Region 設定の明示
- Provider 別の接続テスト
  - 現状は API エンドポイントの確認のみで、Provider 個別の認証は検証していない
- 接続状態のリアルタイム表示
- デフォルト Provider の選択
- Provider 追加 UI(動的登録)
- 認証方式の追加(OAuth / 環境変数経由)
- AWS / ABBYY 等の Provider 追加

### 注意事項

- AWS / ABBYY は現状未対応
- YomiToku は開発モード(`yomitoku_require_license=false`)では License Key 不要

---

## 2. API サーバー設定

### 必須情報

- API エンドポイント URL
  - HTTP/HTTPS のみ受け付け、URI フォーマット検証あり
- 接続テスト
  - `GetEnginesUseCase` 経由で到達性確認
  - 成功/失敗を色分けバナーで表示
- ポーリング間隔
  - 500ms〜60000ms、スライダー + TextBox で指定

### 将来要件

- Backend URL の分離
  - 現状は API エンドポイントと一本化
- Webhook URL 設定
- Timeout 設定
- Retry 回数の指定
- Proxy 設定 / Proxy 認証情報
- 接続テストでの応答時間表示

### 注意事項

- ポーリング間隔は `PollJobStatusUseCase` の最小ガード値(100ms)を下回らない

---

## 3. ライセンス管理

### 必須情報

- YomiToku ライセンスキー入力(PasswordBox)
- 開発モード判定
  - サーバー設定 `yomitoku_require_license` で必須/不要を切替

### 関連実装(他画面)

- 使用量の確認はセクション 4 「使用量・監視」 で代替
  - 現状はライセンス枠ではなく Provider 単価ベースの使用量集計

### 将来要件

- ライセンスキーの有効性検証エンドポイント
- 契約状態の表示(有効 / 期限切れ / 停止中)
- 使用期限の表示
- 利用可能ページ数 / 現在使用量の表示
- 期限切れ警告通知
- ライセンス自動更新
- 上限到達時のジョブ自動停止

### 注意事項

- 現状ライセンス概念は YomiToku のみで、他 Provider は外部サービスのライセンス管理に依存
- 「現在使用量」は使用量画面(セクション 4)で参照

---

## 4. 使用量・監視

### 必須情報

- 当月の合計ページ数
- 当月の推定コスト(¥表記)
- Provider 別の TotalPages / TotalCost
  - `ItemsControl` で Provider ごとに一覧表示
- 更新ボタン
  - `LoadUsageCommand` で再取得
- 履歴データ取得
  - `GET /v1/usage` で当月 + 過去履歴を取得
- 推定コストの注記
  - 「※ 各社公式料金を基にした目安。実際の請求額とは異なる場合があります」
- エラーバナー(`UsageError`)

### 関連実装(他画面/共通基盤)

- 単価は `t_engine_pricing_set` で履歴管理
- 実行時点の単価で `t_usage_recorded` にスナップショット記録
- 通貨はデフォルト JPY(エンジン単位で変更可)

### 将来要件

- OCR 処理件数(ジョブ件数の集計)
  - 現状はページ数のみ
- Error 件数 / Queue 数 / 処理時間
- 無料枠残数(`FreeTierRemaining`)の表示
  - API レスポンスにはあるが UI 未表示
- 期間指定(月次 / 任意レンジ)の集計
- ユーザー / 部署別の利用状況
- CSV エクスポート
- グラフ表示

### 注意事項

- 推定コストは各社公式料金を基にした目安であり、実請求とは差異があり得る
- すべての画面が同じ Job パイプラインを共有しており、使用量はここに集約される

---

## 5. UI 設定

### 必須情報

- ダークモードトグル
  - `IsDarkMode` で切替、`ThemeService` 経由で即時反映
  - 設定は `AppSettings` に永続化

### 将来要件

- テーマ選択(ダーク/ライト以外のバリエーション)
- 表示言語選択(日本語以外への対応)
- フォントサイズ調整
- テーブル密度(コンパクト / 標準 / 広め)
- アクセシビリティ設定(コントラスト / フォントサイズ拡大)
- 画面別のレイアウト/列幅の保存

### 注意事項

- OCR 確認作業は長時間化しやすいため、目への負担を抑える設定の充実が望ましい

---

## 6. OCR デフォルト設定

### 必須情報

- 結果表示のデフォルト
  - `DefaultShowWords` / `DefaultShowLines` / `DefaultShowTables`
  - 結果確認画面で初回表示時のチェック状態を制御
- 履歴表示のデフォルト
  - 表示件数(`HistoryDisplayCount`)
  - ソート順(`HistoryDisplaySortOrder`)

### 関連実装(他画面)

- OCR 実行画面の設定値(Provider / Engine / Template / Language / 前処理)は
  画面遷移ごとに手動選択する設計
  - 設定画面でデフォルト保存する機構は未実装

### 将来要件

- デフォルト OCR Engine / Template / Language
- デフォルト前処理オプションのプリセット
- ユーザー別のデフォルト設定
  - ユーザー識別の仕組みが現状なし
- 帳票種別ごとのデフォルト切替
  - テンプレート側に `category` フィールド追加が前提

### 注意事項

- 「OCR 実行画面のデフォルト」と「結果表示のデフォルト」は別概念
  - 現状は **結果表示のみ** デフォルト指定可能

---

## 7. セキュリティ設定

### 必須情報

なし。本画面ではセキュリティ設定 UI を持たない。
ユーザー識別の仕組みが現状なく、シングルユーザー前提の設計。

### 関連実装(他画面/共通基盤)

- DPAPI による認証情報の暗号化保管
  - `SettingsRepository.GetSecureValue` / `SetSecureValue`
  - 利用者個人のキーで暗号化、別ユーザーは復号不可
  - 設定可能な UI は無く、認証情報入力時に自動適用される

### 将来要件

- ユーザー管理 (ローカル DB or 外部 IdP 連携)
- Role / 権限管理
  - 結果確認の「承認 / 差戻し」、テンプレート管理の「承認フロー」と連動
- IP 制限 (許可リスト / 拒否リスト)
- API Token 管理
- Audit Log
  - テンプレート / 辞書 / 結果の更新履歴と連動
- SSO / SAML / OIDC 連携
- 2 要素認証

### 注意事項

- AI-OCR は個人情報を扱うことが多いため、最低限 Audit Log と権限管理は必須
- 現状はシングルユーザー前提でユーザー識別を行わないため、
  「編集者」「承認者」等の人ベースの仕組みはすべて未実装

---

## 8. ストレージ設定

### 必須情報

なし。本画面ではストレージ設定 UI を持たない。
OCR 結果はサーバー側で固定パスに自動保存される。

### 関連実装(他画面/共通基盤)

- サーバー側ストレージ
  - `api/jobs/infrastructure/storage/file_storage.py`
  - `storage_root` ベースで結果ファイルを管理
- クライアント側のローカル設定保存
  - `%LocalAppData%\OcrViewer` 配下に JSON 形式で永続化
  - `settings.json` / `secure-store.json` / `result-display.json` 等

### 将来要件

- OCR 結果保存先の設定
  - サーバー側 `storage_root` の UI からの変更
- 一時ファイル保存先
- Backup 設定 / Archive 設定
- クラウドストレージ連携(S3 / SharePoint / OneDrive)
- 保持期間ポリシー
- 自動圧縮

### 注意事項

- OCR 結果データは容量が膨らみやすく、保持期間と圧縮戦略の明示が必要
- 現状の `storage_root` は環境変数 / `.env` で指定するサーバー側設定

---

## 9. 通知設定

### 必須情報

なし。本画面では通知設定 UI を持たない。
通知基盤自体が現状なく、ログ出力のみ。

### 関連実装(他画面/共通基盤)

- バックグラウンドワーカー(`MailMonitorWorker` / `folder_event_worker`)は
  `ILogger` でログ出力するのみ
- メール送信機構(SMTP アダプタ)も未実装

### 将来要件

- OCR 失敗通知 / Error 通知 / Queue 異常通知
- 通知チャネル
  - Mail / Slack / Teams / Webhook カスタム通知
- 通知レベル(Error / Warning / Info)の切替
- 通知の有効化フラグ
  - アカウント別 / 画面別の絞り込み

### 注意事項

- 無人 OCR 運用が前提のため、通知設計は監視と連動して必須化したい
- 通知基盤は **設定画面で一元管理し、各画面から共通使用** する設計が望ましい
- 共通 `ErrorHandler` / `ErrorCategory` とも連携する

---

## 10. ログ設定

### 必須情報

なし。本画面ではログ設定 UI を持たない。
ログ出力は基盤のみ実装、設定は固定値。

### 関連実装(他画面/共通基盤)

- クライアント側: `FileLogService`(`OcrViewer.Sdk/Infrastructure/LogService/FileLogService.cs`)
  - エラー / 警告 / 情報レベルでファイル出力
- サーバー側: `ILogger` ベースのログ出力
- バックグラウンドワーカー(`MailMonitorWorker` / `folder_event_worker`)も同じログ機構

### 将来要件

- OCR ログ / API ログ / Error ログのカテゴリ分離
- ログレベル切替(Error / Warning / Info / Debug)
- 保持期間ポリシーの設定
- ログのダウンロード / エクスポート
- 監査ログとの分離
  - 通常ログ: 動作確認 / デバッグ用途
  - 監査ログ: 操作履歴・承認履歴(セクション 7 と連動)

### 注意事項

- 現状のログは開発・サポート用途のみで、運用監査には不足
- 監査要件を満たすには、各画面の変更履歴を
  ログとは別の専用テーブルで管理する設計が必要

# 設定画面の代表的な画面分割

現在の実装状況・将来要件・AI-OCR 製品の実例を踏まえ、
設定画面のレイアウト案を以下の 2 軸 × 3 パターンで整理する。

- **将来設計なし版**(現実装寄り) … パターン①〜③
- **将来設計あり版**(AI-OCR 完成系寄り) … パターン④〜⑥

設定画面は単なる「システム設定」ではなく、
**OCR 基盤管理コンソール** に近い設計として考える必要がある。

---

## 前提整理

現在の設計はかなり `UiPath + ABBYY + Document AI Console` 寄り。
特に OCR Provider / API 接続 / 使用量監視 / UI 設定 / OCR デフォルト / ログ・通知 を
分離している点が良い設計と一致する。

| 方針 | 評価 |
| ---- | -- |
| OCR Provider を中核 | ◎ |
| API 接続と Provider の分離 | ◎ |
| 使用量・コスト集約 | ◎ |
| UI / OCR デフォルトの分離 | ◎ |
| Security / Notification / Log の分離 | ◎ |

---

    結果確認画面の初期表示状態を制御

    HistoryDisplayCount (50/100/200/500)
    HistoryDisplaySortOrder (date_desc/date_asc/name_asc/name_desc)

    GET /v1/usage で当月使用量を取得
    Provider 別 ItemsControl で TotalPages / TotalCost を一覧
    [更新] = LoadUsageCommand で再取得
    推定コスト注記 (公式料金ベース)
    エラー時は UsageError バナー表示

  下部アクションバー:
    [キャンセル] = 編集を破棄して画面遷移
    [保存] = SaveSettingsUseCase 実行 + 接続情報を GatewayConfigurator に反映
    CanSave = HasUnsavedChanges && IsApiEndpointValid && IsPollingIntervalValid
    左側にエラーメッセージバナー (条件付)

## パターン② タブ分離型(DX Suite 系)

設定カテゴリをタブで分離した整理型。Web SaaS や小画面向き。
タブ間で関連性は分断されるが、各カテゴリの情報密度を抑えられる。

### 画面図

│  ☑ Azure  ☑ Google  ☑ Paddle ☑YomiToku│
│ ─ Azure ─                            │
│  APIキー (PasswordBox)               │
│  Endpoint                            │
│ ─ Google ─                           │

# 一押しのパターン

## 短期 (即時実装) → パターン① ScrollView + GroupBox/Expander 階層型(最推奨)

### 理由

- **現実装そのまま**、改修コストゼロ
- 縦スクロール内に **GroupBox + Expander** で階層的に整理されており、関心領域に集中可能
- グローバル設定 / 画面別設定 / 使用量 の 3 セクションで設定カテゴリが明確
- Expander 折り畳みで **情報密度を抑えつつ全責務を保持**
- ダークモードは ThemeService 経由で **即時反映**
- API エンドポイントの **接続テスト** + 成功/失敗バナーで設定確認が容易
- 17/17 責務完全カバー

### 設定画面の特性に最適

設定画面は監視ではなく構成画面なので、Dashboard 型のような常時監視 UI は不要。フラットなスクロール + 折り畳みが最もシンプルで保守しやすい。

### 既存実装の良さを保つ

DPAPI による暗号化保管、未保存変更フラグ (HasUnsavedChanges)、CanSave 判定など、現実装の堅実な動作を変更不要。

## 長期 (将来ゴール) → パターン④ OCR 基盤 Dashboard 型 (大規模運用時の併設候補)

24時間運用 / OCRセンター運用に進化する場合、**監視盤としてパターン④を併設**するのが現実的。
- 左ペインに Provider 接続状態 (●/⚠) を常時表示
- Queue 監視 (実行中/完了/Error/Retry/CPU)
- API 接続状態のリアルタイム監視
- 編集系は **モーダル前提**で割り切る方針

ただし設定画面は基本的に①で十分。Dashboard型は別画面として併設する選択が自然。
