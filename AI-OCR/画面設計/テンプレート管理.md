# テンプレート管理画面 パターン比較

以下に、AI-OCRで実際にあり得る
テンプレート管理画面の構成案を複数提示します。

> 共通用語 (JobStatus / ReviewStatus / Provider / 対応ファイル形式 等) の
> 内部値と画面表記の対応は [用語集.md](用語集.md) を参照。

---

# 凡例

各セクションで使う見出しの意味:

- **必須情報**
  - テンプレート管理画面に存在する/載せるべき項目
- **関連実装(他画面)**
  - テンプレート管理画面外で既に実装されている関連機能(参考用)
- **将来要件**
  - テンプレート管理画面に追加する予定/検討中の機能
- **注意事項**
  - 実装上の制約・設計上の前提・既知の挙動など、画面利用時の留意点

# テンプレート管理画面に必要な画面情報

---

## 1. テンプレート一覧(最重要)

### 必須情報

- テンプレート名(`TemplateSummary.Name`)
- 領域数(`TemplateSummary.RegionCount`、表記例: `5 領域`)
- 一覧アクション
  - 新規作成 / 名前変更 / 削除
  - `TemplateManagerView.xaml:124-139`

### 将来要件

- 帳票種別タグ
  - 「請求書」「申請書」「名刺」「注文書」等のカテゴリ属性
  - `TemplateSummary` への `category` フィールド追加と DB スキーマ拡張が必要
- OCR Engine の紐付け表示
- 使用回数の集計表示
- 更新者の表示
  - 現状ユーザー識別の仕組みなし
- 有効/無効トグル
- Version 表示
- 検索・絞り込み(帳票種別タグ / 名前)
- Template の複製・インポート / エクスポート
- お気に入り / ピン留め

### 注意事項

- AI-OCR では Template が OCR 精度の中核となるため、運用中の Template 一覧を一目で把握できる必要がある
- `TemplateSummary` モデルには `Description` / `ReadingMode` / `CreatedAt` / `UpdatedAt` が存在するが、
  現状の一覧 UI には未表示
  - UI への追加コストは低い(モデル拡張不要)

## 2. 帳票画像表示(中核)

### 必須情報

- 帳票画像表示
  - `TemplateEditor.BackgroundImage` を `Stretch=Uniform` で描画
  - `TemplateManagerView.xaml:248-251`
- bbox 表示
  - `RegionOverlays` を `ItemsControl` で Canvas 上にオーバーレイ
  - 選択中/非選択で色分け(`RegionOverlayViewModel`)
  - `TemplateManagerView.xaml:260-264` / `TemplateEditorViewModel.cs:967-976` 付近
- 画像差し替え
  - 「画像を選択」ボタンで API 経由でアップロード/ダウンロード
  - `TemplateManagerView.xaml:238-241` / `TemplateEditorViewModel.SelectImageCommand`

### 関連実装(他画面)

- 結果確認画面の `ImageDisplayViewModel` に以下が実装済(`ImageDisplayViewModel.cs`)
  - Zoom (`Ctrl++` / `Ctrl+-`、0.1〜5.0、`MinZoom/MaxZoom/ZoomStep` 定義)
  - PDF ページレンダリング (`LoadPdfPage`)
  - ページナビゲーション (`PreviousPage` / `NextPage`、`CurrentPageIndex` / `TotalPages`)
  - Pan は `ScrollViewer` ベース(`ResultView.xaml:298-300`)
- 共通コンポーネント化されているため、Template 管理画面への取り込みは低コスト

### 将来要件

- Zoom / Pan
  - `ImageDisplayViewModel` を Template 管理画面の Canvas にも組み込み
  - bbox オーバーレイの座標計算が ZoomLevel に追従するよう修正が必要
- PDF ページ表示
  - Template 編集対象が PDF の場合のページ切替 UI
  - 現状 `BackgroundImage` は画像ファイル想定で `LoadFromFile` 経由
- 回転
  - `RotateTransform` の適用と bbox 座標の回転対応
  - 共通基盤に未実装
- Fit Width / Fit Page
  - 現状 `FitToWindowCommand` / `ActualSizeCommand` は両方とも `ZoomLevel = 1.0` を返すだけで未差別化
    (`ImageDisplayViewModel.cs:173-186`)
  - 実質的なフィット計算(画像サイズと Viewport サイズに基づくスケール算出)が必要
- Grid 表示
  - 領域配置の整列補助用オーバーレイ
  - 共通基盤に未実装
- 多ページ PDF のサムネイル一覧
  - 共通基盤に未実装

### 注意事項

- Template 管理画面は結果確認画面と異なり、**bbox を編集する** ため Canvas を直接操作する設計
  - 結果確認画面の `ImageDisplayViewModel` を流用する際は、編集モードとの整合性に注意
- 領域座標は正規化(0.0〜1.0)で保持されるため、Zoom/Pan 追加時も座標値そのものは変更不要

## 3. OCR 領域(Region)管理

### 必須情報

- 矩形選択(ドラッグで新規領域描画)
  - `TemplateManagerView.xaml.cs:64-100` (Canvas MouseDown/Move/Up)
  - 描画中は点線青枠のプレビューを表示(`TemplateManagerView.xaml:294-303`)
- 領域名
  - 新規作成時に入力ダイアログを表示(`TemplateManagerView.xaml:324-348`)
  - 既存領域は右ペイン「領域詳細」で編集
- bbox 座標
  - Canvas 座標 + 正規化座標(0.0〜1.0)の両方を保持
    (`RegionOverlayViewModel.cs:940-962`)
  - 右ペインで X / Y / Width / Height を数値編集可
- 領域色分け
  - 選択中: 青(`#0078D7`) / 非選択: 赤(`#DC3545`)
  - `TemplateEditorViewModel.cs:967-976`
- ドラッグ移動・リサイズ
  - 8 方向リサイズハンドル(`HitTestResizeHandle` + `ResizeDirection` enum)
  - カーソル形状フィードバック(`TemplateManagerView.xaml.cs:131-158`)
- 領域削除
  - `DeleteRegionCommand` / `TemplateManagerView.xaml:529-531`

### 将来要件

- 領域 ON/OFF
  - 領域単位での有効/無効トグル
  - `TemplateRegion` モデルへの `enabled` フラグ追加と DB スキーマ拡張が必要
- Group 化
  - 複数領域をまとめて移動・有効化できるグルーピング機構
  - モデル拡張(group_id) と UI が必要
- 多角形 / 不定形領域
  - 現状は矩形のみ
  - 座標モデルの変更(点列 vs 矩形)が必要
- 領域コピー / ペースト
  - クリップボード or 同一テンプレート内のクローン
- ドラッグ並び替え
  - `sort_order` フィールド追加と一覧 UI が必要

### 注意事項

- 「OCR 対象範囲」は矩形選択(領域定義)そのものを指す
  - 領域 = OCR を実行する範囲、領域外は OCR 対象外
- 領域座標は正規化(0.0〜1.0)で保持されるため、Canvas サイズ変更や Zoom 追加時も
  座標値そのものは変更不要
- AI-OCR では「ここを読む」定義が中核となるため、領域編集の操作性を優先する

## 4. 項目設定

### 必須情報

- 項目名(領域名)
  - `RegionDetailViewModel.RegionName` / `TemplateManagerView.xaml:405-407`
- 出力フォーマット型
  - text / number / date の 3 種(`TemplateManagerView.xaml:451-457`)
  - 説明: 抽出テキストの型変換
- テキスト結合方式
  - none / space / concat / newline の 4 種(`TemplateManagerView.xaml:466-473`)
  - 説明: 領域内の単語を 1 つの行としてまとめる方式
- バリデーション
  - 座標範囲(0.0〜1.0)と x+w, y+h の境界チェック
  - テーブル行列数の最小値チェック
  - `RegionValidator.cs:27-62`

### 関連実装(他画面)

- 辞書管理画面の辞書 ID リスト
  - `TemplateRegion.DictionaryIds` モデルには存在(`Template.cs:65`)
  - 辞書管理画面で辞書 CRUD は実装済
  - ただし Template 管理画面で領域に辞書を紐付ける UI は未実装
  - 候補値リスト機能の基盤として活用可能

### 将来要件

- 出力フォーマット型の拡張
  - **Currency**(通貨記号付き数値の正規化)
  - **Barcode**(バーコード/QR の値抽出)
- 必須/任意フラグ
  - 領域単位の必須属性
  - モデルへの `required` フラグ追加が必要
- Regex パターン
  - 抽出テキストの正規表現バリデーション
  - モデルへの `regex` フィールド追加が必要
- カスタム Validation Rule
  - 範囲チェック(数値の最大/最小)、日付フォーマット、文字種制限等
- 候補値リスト UI
  - 領域に辞書を紐付ける ComboBox / リスト操作 UI
  - モデル側(`DictionaryIds`)は既に存在
- 手書き文字 / 印影
  - 領域に特化フラグを持たせ、エンジンに別パラメータを渡す設計が必要
- 後続フィールドへの値依存設定
  - フィールド間の参照関係を定義する仕組み

### 注意事項

- `RegionValidator.Validate` は **座標とテーブル行列数の範囲チェックに限定**
  - 抽出テキストの内容バリデーション(Regex 等)は未実装
- 出力フォーマット型の `number` / `date` は型変換のみで、Currency などの記号処理は含まない

## 6. テーブル定義

### 必須情報

- 明細範囲(テーブル領域として設定)
  - `IsTable` チェックボックス(`TemplateManagerView.xaml:482-484`)
  - 説明: 「文字中央寄せ」前処理用のセル分割を定義
- 行数 / 列数
  - `TableRows` / `TableColumns` (数値 TextBox)
  - `TemplateManagerView.xaml:494-501`
- TableStructure VO
  - API ドメイン: `rows` / `columns` / `row_heights` / `column_widths`
  - 行高さ・列幅は正規化(合計 1.0 ± 0.01 tolerance)
  - デフォルトで均等分割(`create_uniform()`)
  - `api/templates/domain/value_objects/table_structure.py:55-171`

### 関連実装(他画面)

- LLM ベースエンジン(Gemini 等)のレスポンスパーサー
  - `api/jobs/infrastructure/engines/llm_response_parser.py:21` で
    `row_span` / `col_span` を指定するプロンプト
  - ただしこれは **OCR 結果側でセル結合を解釈する** ものであり、
    テンプレート定義側でセル結合を指定する機能ではない

### 将来要件

- Header 定義
  - テーブル内のヘッダー行/列を区別する仕組み
  - `TableStructure` への `header_rows` / `header_columns` 追加が必要
- Dynamic Row(動的行数)
  - 行数が帳票内容により可変な明細表への対応
  - 現状は固定行数のみ
  - 行数推定ロジック or 終端マーカー検出が必要
- 行高さ・列幅の個別調整 UI
  - モデル側(`row_heights` / `column_widths`)はサポート済だが、
    現状 UI からは常に `[]`(均等分割)で送信される
    (`RegionDetailViewModel.cs:380-381`)
  - 個別ドラッグでの分割線調整 UI を追加すれば対応可能
- 画像処理による行・列境界の検出補助
  - OpenCV 等で罫線を直線検出し、セル境界の初期値を提示
  - 採用/手動補正は人が確定
- セル結合 / 分割
  - `row_span` / `col_span` フィールド追加と編集 UI が必要
- 別サンプルでの表構造確認
  - テンプレート保存後、別サンプル画像で表構造の整合性を視覚確認

### 注意事項

- 請求書 OCR では明細部分の認識精度が業務影響に直結する
- 現状の UI はテーブル領域を「均等分割のセル」としてのみ定義可能
  - 不均一な明細(欄外の備考列等)は領域分割で表現する必要あり

## 7. OCR 前処理設定

### 必須情報

なし。本画面では前処理設定を持たない方針。
前処理は OCR 実行時に選択する設計。

### 関連実装(他画面)

- OCR 実行画面の前処理選択 UI
  - 7 オプション: `auto_rotate` / `deskew` / `contrast` / `binarize` /
    `center_text` / `upscale` / `border_padding`
  - `PreprocessingOptionDefinitions.cs` にクライアントハードコード
  - OCR 実行画面 ListBox + CheckBox(`ExecutionView.xaml:254-275`)
- テンプレート連動の前処理
  - `center_text`(文字中央寄せ)は **テーブル領域を持つテンプレート選択時のみ** 有効化
  - `OcrConfigViewModel.cs:339-363`

### 将来要件

- Template ごとの前処理プリセット
  - テンプレートに「推奨前処理オプション」を紐付け
  - OCR 実行画面でテンプレート選択時に前処理を自動適用
  - モデル側に `default_preprocessing` フィールド追加が必要
- 前処理 Before/After プレビュー
  - サンプル画像に各前処理を適用した結果を可視化
  - 領域編集時の精度調整に活用
- ノイズ除去(`denoise`)
  - 現状の前処理オプションには未実装
- 傾き補正 / 二値化 / 解像度補正の個別有効化 UI を本画面に持たせる場合は
  Template ごとのプリセット機能とセットで設計する

### 注意事項

- 現状の前処理は OCR 実行時に毎回手動で選ぶ設計
  - テンプレートごとに最適な前処理が決まっている場合の運用負荷が課題
- 前処理オプション一覧の追加は API 側パイプラインとクライアント側両方の更新が必要
  - 将来的には API レスポンスから動的取得する設計に寄せるのが望ましい

## 8. テスト OCR

### 必須情報

なし。本画面ではテスト OCR を実行できない。

### 関連実装(他画面)

- OCR 実行画面でジョブを投入 + 結果確認画面で結果確認
  - テンプレートを指定して OCR を実行することは可能
    (`OcrConfigViewModel.SelectedTemplate` 経由)
  - ただし画面往復が必要で、領域編集中の即時検証には不向き
- 結果確認画面の信頼度表示
  - `TextBlockViewModel.ConfidenceLevel`(High / Medium / Low)
  - bbox の信頼度別カラーコーディング

### 将来要件

- 本画面内でのテスト OCR 実行
  - サンプル画像 + 現在編集中の Template で OCR を実行
  - API 側にプレビュー専用エンドポイント(永続化しない試行実行)が必要
- 結果プレビュー
  - 領域別の抽出テキスト表示
  - 共通 `Confidence` VO で信頼度を可視化
- 領域別のエラー表示
  - 抽出失敗・低信頼度領域のハイライト
- 期待値との差分表示
  - 領域単位の期待値登録機能と差分計算
- 複数サンプルでの一括テスト
  - サンプル画像群を Template に紐付け、一括実行
- 精度レポート
  - サンプル群に対する正解率・誤抽出傾向の集計

### 注意事項

- Template 調整の効果を即時検証できないと、精度改善サイクルが回らない
- 現状は OCR 実行画面 → 結果確認画面の往復が必要
  - サンプル画像を毎回投入する手間が発生

## 9. バージョン管理

### 必須情報

なし。本画面ではバージョン管理機能を持たない。
現状は `UpdatedAt`(最終更新日時、`TemplateSummary.UpdatedAt`)のみ保持。

### 関連実装(他画面/共通基盤)

- テンプレートのアーカイブ機構(ソフトデリート)
  - `ArchiveTemplateUseCase` + `t_template_archived` テーブル
  - `archived_at` を記録(`api/templates/application/archive_template_use_case.py`)
- 領域単位の論理削除
  - `t_template_region_disabled` テーブル + `disabled_at` 記録
  - `db/alembic/versions/da225d0ce920_initial_idm_schema.py:292-304`
- ※ いずれも「復元」UI は未実装だが、Rollback の基盤として活用可能

### 将来要件

- Version 番号
  - `TemplateSummary` への `version` フィールド追加
  - 編集毎にインクリメント、または明示的なリリース時のみインクリメントなどポリシー検討が必要
- 更新履歴
  - 過去状態のスナップショット保存
  - イベントソーシング or 履歴テーブル(`t_template_history`)の追加が必要
- Rollback(過去版への復元)
  - 履歴スナップショットからの復元 UI
  - アーカイブ機構の延長として実装可能
- 差分比較
  - 領域追加・削除・座標変更を可視化
  - 履歴スナップショット間の diff 計算が必要
- ブランチ機能(本番/検証の並走)
  - 同一テンプレートの本番用・検証用バリエーション管理
  - `parent_template_id` 等の関係定義が必要
- 承認フロー
  - 編集→レビュー→承認→公開のステート管理
  - 権限管理(ユーザー識別の仕組みが現状なし)とセットで設計が必要

### 注意事項

- 現状の `UpdatedAt` で「いつ変更したか」は分かるが、
  「何を変更したか」「以前の状態は何か」は記録されない
- アーカイブテーブル(`t_template_archived`)は存在するが、復元 UI/API は未実装
  - Rollback 実装時はこの基盤を活用できる

## 10. エラー表示

### 必須情報

- Validation Error
  - 領域名空 / 座標範囲(0.0〜1.0) / 境界(x+w, y+h ≤ 1) / テーブル行列数の最小値チェック
  - `RegionValidator.cs:31-59`
  - 領域詳細パネル内の赤バナーで表示(`TemplateManagerView.xaml:506-514`)
- Dirty Indicator
  - 「* 未保存の変更があります」黄色テキスト
  - `TemplateManagerView.xaml:517-521`
- 操作エラー(2 レベル表示)
  - 領域詳細パネル内: 保存/削除等の操作エラー(`TemplateManagerView.xaml:535-543`)
  - 画面全体オーバーレイ: テンプレート全体の操作エラー + ClearError ボタン
    (`TemplateManagerView.xaml:550-573`)
- Editor 系エラー
  - 領域の読み込み失敗 / 画像のアップロード・読み込み失敗 / 位置の保存失敗 / Canvas サイズ無効
  - `TemplateEditorViewModel.cs:198-776`
- Loading Overlay

### 将来要件

- bbox 重複検出
  - 領域同士の座標重複を検証して警告
  - 領域追加/更新時のバリデーションとして実装
- 領域未設定警告
  - テンプレートに領域が 1 つも無い場合や、必須領域(将来要件)が未配置の場合の警告

# 一押しのパターン

## 短期 (即時実装) → パターン① シンプル3ペイン型(最推奨)

### 理由

- **現実装そのまま**、改修コストゼロ
- bbox 編集に必要な 3 要素 (**テンプレ一覧 / Canvas / 領域詳細**) を**同時表示**
- 左ペインで複数テンプレを一覧管理しつつ、中央 Canvas で領域編集、右ペインで領域属性を即座に編集できる
- **読取方式 (全体読取/領域別読取)** の切替を中央ヘッダで明示
- ドラッグで新規領域描画、8方向リサイズハンドル、領域色分け (選択青/非選択赤) など bbox 編集の操作性が高い
- Validation エラーバナー + Dirty Indicator で**未保存変更を視覚化**
- 20/20 責務完全カバー

### bbox 編集の本命

AI-OCR では Template が OCR 精度の中核となるため、3ペインで Master-Canvas-Detail を**同時に見せる**のが必須。タブ分離型や Canvas 特化型では編集効率が落ちる。

### 領域座標は正規化保持

Canvas サイズ変更や将来のズーム追加時も**座標値そのものは変更不要** (0.0-1.0 正規化座標)。

## 長期 (将来ゴール) → パターン④ OCR Studio 型(UiPath 完成系)

OCR Preview + Validation + Regex + Dictionary連携 + Version管理 + History を
1 画面に統合した完成形。
- **テスト OCR** をテンプレ編集画面から直接実行 (Section 8 将来要件)
- 領域別の **Confidence 表示** で要調整領域を即座に把握
- テンプレ調整 → 即時検証 → 再調整のサイクルが 1 画面で回せる

ただしテスト OCR エンドポイントの追加が前提。短期は ① で十分。
