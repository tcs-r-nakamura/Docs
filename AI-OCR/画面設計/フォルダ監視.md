# フォルダ監視画面 パターン比較

以下に、AI-OCRで実際にあり得る
フォルダ監視画面の構成案を複数提示します。

> 共通用語 (JobStatus / ReviewStatus / Provider / 対応ファイル形式 等) の
> 内部値と画面表記の対応は [用語集.md](用語集.md) を参照。

---

# 凡例

各セクションで使う見出しの意味:

- **必須情報**
  - フォルダ監視画面に存在する/載せるべき項目
- **関連実装(他画面)**
  - フォルダ監視画面外で既に実装されている関連機能(参考用)
- **将来要件**
  - フォルダ監視画面に追加する予定/検討中の機能
- **注意事項**
  - 実装上の制約・設計上の前提・既知の挙動など、画面利用時の留意点

---

# フォルダ監視画面に必要な画面情報

---

## 1. 監視フォルダ一覧(最重要)

### 必須情報

- フォルダ名
- フォルダ Path
- 一覧アクション
  - 新規 / 編集 / アーカイブ

### 将来要件

- 監視状態(実行中 / 停止中 / エラー)
- 最終検知日時
- フォルダ単位の OCR Engine / Template 表示
- 有効/無効トグル
- 更新日時の一覧表示
- ルール数の一覧表示
- フォルダ別の保留ファイル上限
- フォルダ別の取得頻度設定

### 注意事項

- AI-OCR では `invoice/` / `scan/` / `order/` など複数フォルダ運用が前提
- 現状は OCR Engine / Template が **ルール単位** の紐付けで、フォルダ単位ではない
- `CreatedAt` / `UpdatedAt` / `Description` はモデル保持済だが、現状の一覧 UI には未表示

---

## 2. Folder 監視設定

### 必須情報

UI でユーザーが指定する設定:

- フォルダ名
- Folder Path (サーバー側の絶対パス)
- 説明 (任意)

API 側でデフォルトで動作する監視機能(設定 UI 無し):

- 自動ファイル監視(watchdog によるイベント駆動)
  - Linux: inotify (`IN_CLOSE_WRITE`)
  - macOS: FSEvents
  - Windows: ReadDirectoryChangesW
- File 完成待機
  - Linux: `on_closed` イベントでカーネル保証
  - 他 OS: ファイルサイズ安定確認 (0.5 秒間隔 × 3 回、タイムアウト 10 秒)
- Rename 検知 (`on_moved` ハンドラ)
- 手動同期(Sync) ボタンによる既存ファイルの一括スキャン

### 関連実装(他画面/共通基盤)

- `api/folder_monitor/infrastructure/watching/folder_event_worker.py`
  - watchdog Observer の起動・停止・ウォッチャー登録管理
- `ocr_job_dispatcher.py`: 検出ファイルをルール判定して OCR ジョブを投入
- **対応ファイル形式** (`api/folder_monitor/application/_file_extensions.py:3`)
  - `.pdf .png .jpg .jpeg .tiff .tif` (PDF / PNG / JPG / TIFF の 4 形式)
  - ※ OCR エンジン本体は GIF / BMP / WebP も対応するが、
    フォルダ監視はピックアップ対象から除外している

### 将来要件

- Recursive 監視
  - 現状 `recursive=False` でハードコード(`folder_event_worker.py:412, 459`)
- 監視 ON/OFF トグル
  - ウォッチャー単位の有効/無効フラグなし
- Polling 間隔の指定
  - イベント駆動のため通常不要だが、ネットワーク共有等で必要な場面あり
- ネットワーク共有(UNC / SMB)対応
- クラウドストレージ(S3 / OneDrive / SharePoint)対応
- FileSystemWatcher / Polling のモード切替 UI

### 注意事項

- 現状の `FolderWatcher` ドメインは `name` / `folder_path` / `description` のみ保持
  - Recursive / ON/OFF / Polling 間隔等はモデル拡張が必要
- File 完成待機は watchdog 側で実装済みのため、設計書記載の「コピー途中ファイル誤投入防止」は既に解決済み
- ネットワーク共有は inotify 等のネイティブ API が動かない場合があるため、Polling フォールバックが必要

---

## 3. OCR ルール管理

### 必須情報

- ルール名
- ファイルパターン (glob、例: `*.pdf` / `invoice_*.png`)
  - 拡張子条件とファイル名条件を 1 つのパターンで兼ねる
- OCR Engine (エンジンID)
- Template (テンプレートID、任意)
- 優先度 (小さいほど優先)
- 説明 (任意)
- 一覧アクション
  - 新規 / 編集 / 削除
- DataGrid 表示列
  - 名前 / ファイルパターン / エンジン / 優先度

### 将来要件

- 拡張子条件 / ファイル名条件の分離
  - 現状は glob 1 本で兼ねており、UI 上での意図分離なし
- Folder 条件 (サブフォルダ単位の絞り込み)
  - 現状ルールはウォッチャー単位、フォルダ内パスでの条件分岐は無し
- 有効/無効トグル (`is_active` フィールドが現状無し)
- エンジン/テンプレートを ID 数値ではなく名称ドロップダウンで選択
- ルールの並べ替え (優先度ドラッグ)
- ルール複製・テンプレート化
- 複合条件 (AND / OR)

---

## 4. OCR 処理設定

### 必須情報

- OCR Engine (ルールの `engine_id`)
- Template (ルールの `template_id`、任意)

### 関連実装(他画面)

- OCR 実行画面で Provider / Engine / Template / 言語 / 前処理を選択する仕組みあり
  - 言語と前処理はジョブ単位の指定で、フォルダ監視のルールには紐付かない
- エンジンとテンプレートは共通の API ドメインを参照

### 将来要件

- OCR Language のルール紐付け
- ルールごとの前処理プリセット
- confidence 閾値
  - 低信頼度ジョブを Error フォルダへ振り分ける等の運用フックに使う
- AI 補助による Template 自動判定

### 注意事項

- 現状ルールに紐付くのは **エンジン + テンプレートのみ**
  - 言語・前処理・閾値はジョブ作成時のデフォルト値が適用される設計

---

## 5. 処理後設定

### 必須情報

なし。本画面では処理後のファイル移動・削除・リネーム機能を持たない。
OCR 完了後の元ファイルは検出時の場所に残る。

### 将来要件

- Move Folder (OCR 完了後の移動先)
- Archive Folder (アーカイブ用フォルダ)
- Error Folder (失敗ファイルの隔離先)
- Rename Rule (OCR 結果に応じた命名規則)
- Delete After OCR (OCR 完了後の元ファイル削除)
- クラウドストレージへのアーカイブ転送 (S3 / OneDrive / SharePoint)
- リネーム時の OCR 結果情報埋め込み (`{date}_{template}_{idx}` 等)

### 注意事項

- 元ファイルの保持/削除は監査要件に直結するため、デフォルトは保持を推奨
- API に `t_folder_watcher_archived` テーブルがあるが、これは **ウォッチャー自体のソフトデリート** 用であり、
  ファイル単位のアーカイブ機構ではない

---

## 6. OCR 処理履歴

### 必須情報

- ファイル名(検出ファイルパスから抽出)
- ステータス(成功 / 一部成功 / 失敗 / ルール不一致)
- ジョブ数(検出 1 件に対し紐付くジョブ件数)
- 検出日時
- ページネーション(前 / 次 / 全件数表示)
- アクション
  - 手動同期(Sync) / 再読み込み

### 関連実装(他画面)

- 結果確認画面でジョブ単位の詳細(結果テキスト・bbox・信頼度)が確認可能
  - 検出ログから直接遷移する動線は未実装

### 将来要件

- エラーメッセージの一覧表示
  - `FolderFileLog.Error` はモデル保持済だが DataGrid 列に出ていない
- OCR 開始 / OCR 完了時刻
  - 現状は検出時刻のみ
- 処理時間 (開始〜完了の集計)
- ファイルプレビュー (検出ログ行から元ファイル or OCR 結果を確認)
- 失敗ジョブの再実行導線
- 期間指定の集計 (日/週/月の成功率・件数)

---

## 7. Queue / 実行状態

### 必須情報

なし。本画面では Queue サマリを表示しない。
検出ログ(セクション 6)で個別ファイルの最終ステータスのみ確認可能。

### 関連実装(他画面/共通基盤)

- ジョブ単位のステータスは API で管理(`queued` / `running` / `succeeded` / `failed` / `canceled`)
  - 結果確認画面のジョブ一覧で確認可能
- フォルダ監視からは検出 → ルールマッチ → ジョブ作成の流れで、
  ジョブ自体は OCR 実行画面が投入するものと同じパイプラインに乗る

### 将来要件

- 実行待ち件数 / 実行中件数 / Error 件数の集計表示
- Retry 件数
  - そもそも自動リトライ機構が現状無い
- 最終実行(直近の検出/OCR 実行時刻)
- フォルダ別の Queue 集計
- グラフ表示(時系列の検出数・成功率)
- 上限超過時のアラート

### 注意事項

- フォルダ監視画面と結果確認画面でジョブの見え方が分かれている
  - フォルダ監視: 検出ログ単位
  - 結果確認: ジョブ単位

---

## 8. 通知設定

### 必須情報

なし。本画面ではユーザー向け通知設定を持たない。

### 関連実装(他画面/共通基盤)

- 内部ワーカー向けの **イベント通知ポート** は実装あり
  - `api/folder_monitor/infrastructure/watching/watcher_event_notifier.py`
  - ウォッチャー CRUD 時にバックグラウンドワーカーへホットリロード通知を送る用途
  - **ユーザー向け通知ではない** ため混同注意

### 将来要件

- OCR 失敗通知 / Folder Error 通知 / Queue 異常通知
- 通知チャネル
  - Slack / Mail / Teams / Webhook カスタム通知
- 通知レベル(Error / Warning / Info)の切替
- フォルダ別 / ルール別の通知有効化設定

### 注意事項

- 無人 OCR 運用が前提のため、通知設計は監視と連動して必須化したい
- 通知基盤は OCR 実行画面側のエラー通知とも共通化したい
  - `ErrorHandler` / `ErrorCategory` と連携する形が望ましい

---

## 9. エラー管理

### 必須情報

- 検出ログのステータス分類
  - `Succeeded` / `Partial` / `Failed` / `NoMatch`(`FolderFileLogStatus` enum)
- エラーメッセージ保持
  - `FolderFileLog.Error` に raw string で記録(現状 UI 列には未表示)
- 画面全体エラー表示オーバーレイ(`FolderMonitorView.xaml:444-`)

### 関連実装(他画面/共通基盤)

ファイル監視ワーカーで以下のエラーを実装済(`folder_event_worker.py`):

- 未サポート拡張子の自動スキップ
  - `SUPPORTED_EXTENSIONS` リストで判定、対象外はログ出力のみで処理せず
- 書き込み完了タイムアウト
  - `_wait_for_stable` で 10 秒タイムアウト、未完成なら処理スキップ
- ファイルアクセスエラー(`OSError`)のキャッチ
- 重複検出(`IntegrityError` で安全に除外)

### 将来要件

- エラーカテゴリの分離(現状すべて `Failed` に集約)
  - File Lock Error / OCR Error / Timeout / Unsupported File / Access Error
- カテゴリ別アイコン・色分け
  - 共通 `ErrorHandler` / `ErrorCategory` と連携
- 連続失敗時のフォルダ自動停止
  - 監視 ON/OFF トグル(セクション 2 将来要件)と連動
- リトライ導線(失敗ジョブの再実行)
- エラーメッセージの DataGrid 列追加(モデル保持済、低コスト改善)

### 注意事項

- 現状はエラーが発生しても `Failed` ステータスのみで原因がわからない
  - UI からは `Error` 文字列を辿る必要があり、運用効率が悪い
- 共通 `ErrorHandler` 基盤を活用すれば、OCR 実行画面と統一したエラー UI が実現可能

---

## 10. テスト実行

### 必須情報

- 手動同期(Sync)
  - 監視フォルダをスキャン → ルールマッチング → 該当ファイルに OCR ジョブを投入
  - `SyncWatcherUseCase` / `FolderMonitorView.xaml:340-343`
- Sync 結果サマリ表示
  - 検出 X 件 / 成功 Y 件 / 失敗 Z 件
- ルールマッチング(glob、`FolderRule.matches()`)
- NoMatch ファイルは記録のみ(ジョブ投入なし)
- 既記録ファイル(同パス + 同更新日時)はスキップ

### 関連実装(他画面)

- 結果確認画面でジョブ単位の OCR 結果プレビューが可能
  - フォルダ監視から投入したジョブも同一パイプラインで確認できる

### 将来要件

- ドライラン
  - Sync は実際にジョブを投入する仕様のため、判定のみのテストモードが無い
- サンプル投入で Rule 検証する UI
  - 1 ファイル指定 → ルール判定結果(マッチしたルール / なし) のみ表示
- OCR Preview
  - 投入前のジョブ作成パラメータ確認(エンジン / テンプレート / 言語 / 前処理)
- ルール適用結果の差分表示
  - ルール変更前後で同一サンプル群の判定結果を比較

### 注意事項

- 本番運用前のルール検証手段が無いため、誤判定で OCR コストが膨らむリスクあり
- Sync は **新規ファイルのみ処理**(`exists_by_path_mtime` で重複除外)するため、
  ルール再判定のためのリプレイは現状不可

# フォルダ監視画面の代表的な画面分割

現在の実装状況・将来要件・AI-OCR 製品の実例を踏まえ、
フォルダ監視画面のレイアウト案を以下の 2 軸 × 3 パターンで整理する。

- **将来設計なし版**(現実装寄り) … パターン①
- **将来設計あり版**(AI-OCR 完成系寄り) … パターン②〜④

---

## 前提整理

現在の実装状況はかなり `UiPath + ABBYY` 寄りの「業務 OCR 運用型」。
特に Folder / Rule / OCR / Queue を分離している点が良い設計と一致する。

| 方針 | 評価 |
| ---- | -- |
| 左:Folder 一覧 | ◎ |
| 中央:Rule 一覧 | ◎ |
| 右:Rule 詳細 | ◎ |
| OCR 設定分離 | ◎ |
| Queue 運用想定 | ◎ |

---

# 将来設計なし版(現実装ベース)

---

## パターン① 3ペイン + 中央タブ型(最推奨)

現在の構成を強化し、ルール一覧と検出ログをタブで切替表示する案。

### 画面図

```text
┌──────────────┬──────────────────────┬──────────────┐
│ Folder一覧   │ [ルール] [検出ログ]  │ Rule詳細     │
│              ├──────────────────────┤              │
│ ● invoice/   │ (タブで切替表示)     │ OCR Engine   │
│   検知 5分前 │                      │ Template     │
│ ● scan/      │ [ルール] 選択時:     │ Priority     │
│   検知 1h前  │   *.pdf              │ Description  │
│ ⚠ order/     │   invoice_*.pdf      │              │
│   アクセス   │   *.jpg              │ [保存]       │
│   エラー     │   ＋ ✎ ×             │              │
│              │                      │              │
│ ＋ ✎ × ⟳     │ [検出ログ] 選択時:   │              │
│              │   ファイル名/        │              │
│              │   ステータス/日時    │              │
└──────────────┴──────────────────────┴──────────────┘

凡例:
  ● = 監視中  ⚠ = アクセス/監視エラー
  ※ 状態アイコン (●/⚠) と「検知 N前」表示は将来要件 (Section 1 将来要件参照)。
    現実装には未存在。短期改修で追加する想定
  Folder一覧 下の ＋/✎/× = フォルダ新規/編集(監視設定モーダル)/アーカイブ
  ⟳ = 手動同期 (選択フォルダの一括スキャン → ルールマッチング → ジョブ投入)
  中央タブ:
    [ルール]   = OCR ルール一覧 (内側 ＋/✎/× でルール CRUD)
    [検出ログ] = ファイル検出履歴 (ファイル単位、現実装の検出ログタブ相当)
  Rule詳細 (右ペイン) = [ルール]タブで選択中のルールに連動
```

### 画面分割

| 領域 | 内容 |
| ---- | ---- |
| 左 20% | フォルダ一覧 + フォルダ CRUD アイコン (＋/✎/×) |
| 中央 45% | TabControl: [ルール](OCR ルール一覧) / [検出ログ](ファイル検出履歴) |
| 右 35% | ルール詳細 (常駐編集ペイン、[ルール]タブの選択に連動) |

### メリット

| 項目 | 評価 |
| ---- | -- |
| Rule 管理しやすい | ◎ |
| OCR 運用向き | ◎ |
| 拡張しやすい | ◎ |
| 大量 Folder 向き | ◎ |
| 検出ログアクセス | ◎ |

### デメリット

| 項目 | 評価 |
| ---- | -- |
| 情報量多い | △ |
| 小画面弱い | △ |
| 同時性なし | △ (タブ切替必要、同時表示にはパターン④) |

### 向いている

```text
・本命構成
・業務OCR
・運用重視
```

# 将来設計あり版(完成系 AI-OCR)

---

## パターン② Dashboard 型(ABBYY 系)

OCR センター向けの監視特化型。大規模運用での状態把握を最優先する。

### 画面図

```text
┌────────────────┬──────────────────────┬──────────────┐
│ Folder         │ Rule Monitor         │ Queue Status │
│                │                      │              │
│ ● invoice/  ✎  │ 検知数  Rule状態 ✎   │ 実行中 12    │
│ ● scan/     ✎  │ OCR Engine           │ 完了 320     │
│ ⚠ order/    ✎  │ Last Process         │ Error 4      │
│                │ [失敗ログ→]          │ Retry 2      │
│ ＋ × ⟳         │                      │ CPU使用率    │
│                │                      │ 同期結果サマリ│
└────────────────┴──────────────────────┴──────────────┘

凡例:
  ● = 監視中  ⚠ = アクセス/監視エラー
  ※ 状態アイコン (●/⚠) と「検知 N前」表示は将来要件 (Section 1 将来要件参照)。
    現実装には未存在。短期改修で追加する想定
  ＋ = 新規フォルダ (監視設定モーダル)
  ✎ = 編集 (フォルダ/ルール毎、モーダル展開)
  × = アーカイブ  [失敗ログ→] = 失敗履歴一覧へ遷移
  ⟳ = 手動同期 (一括スキャン)、結果サマリは Queue Status に表示

※ 配置上の制約:
  - 編集は基本的にモーダル展開 (画面内に常駐編集ペインを置かない方針)
  - 検出ログの本体 (ファイル名/日時一覧) は Queue Status の集計のみ画面内、
    詳細一覧は [失敗ログ→] / 結果確認画面に遷移する設計
```

### 将来要件

| 機能 | 内容 |
| ---- | ---- |
| Queue 監視 | OCR 監視 |

# 一押しのパターン

## 短期 (即時実装) → パターン① 3ペイン + 中央タブ型(最推奨)

### 理由

- **現実装の 2-pane + TabControl からの改修コスト最小**
- フォルダ監視の本質である **「監視が止まっていないか」を一目で把握** できる
- フォルダ編集 = モーダル / ルール編集 = 常駐 Inspector ペイン の責務分離が明確
- 検出ログを **中央タブ [検出ログ] で画面内に常駐** 表示
- 状態アイコン (●/⚠) + 最終検知日時で **フォルダの監視状態が一覧で見える** (将来要件)
- **手動同期 (⟳) ボタン** が画面内にあり、新規ファイルの即時投入が可能
- 12/12 責務完全カバー

### 既存実装との親和性

watchdog Observer によるバックグラウンド監視 + 手動同期 (`SyncWatcherUseCase`) の構造を変えずに UI だけ拡張できる。

## 長期 (将来ゴール) → パターン④ 3ペイン+中央縦分割型(運用統合完成系)

中央を縦分割して **ルール一覧と検出ログを同時表示** することで、「このルールでヒットしたファイル」を画面遷移なしで即座に確認可能。拡張子条件の分離・通知・リトライなどの将来要件が実装された後の到達点。
