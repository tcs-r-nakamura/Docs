# メール監視画面 パターン比較

以下に、AI-OCRで実際にあり得る
メール監視画面の構成案を複数提示します。

> 共通用語 (JobStatus / ReviewStatus / Provider / 対応ファイル形式 等) の
> 内部値と画面表記の対応は [用語集.md](用語集.md) を参照。

---

# 凡例

各セクションで使う見出しの意味:

- **必須情報**
  - メール監視画面に存在する/載せるべき項目
- **関連実装(他画面)**
  - メール監視画面外で既に実装されている関連機能(参考用)
- **将来要件**
  - メール監視画面に追加する予定/検討中の機能
- **注意事項**
  - 実装上の制約・設計上の前提・既知の挙動など、画面利用時の留意点

# メール監視画面に必要な画面情報

---

## 1. メールアカウント一覧(最重要)

### 必須情報

- アカウント名
- 一覧アクション
  - 新規 / 編集 / アーカイブ

### 将来要件

- メールアドレス / IMAP Host / Port / 認証方式の一覧表示
  - 現状モデル保持済だが一覧 UI に出ていない (詳細ダイアログのみ)
- 接続状態(接続中 / エラー / 未接続)のリアルタイム表示
- 最終同期日時の一覧表示
- 有効/無効トグル
  - 現状はアーカイブ(ソフトデリート)のみで、一時停止の概念なし
- アカウント別の取得頻度設定の一覧視認
  - `poll_interval_seconds` はモデル保持済
- アカウント別の保留メール上限

### 注意事項

- AI-OCR では `invoice@` / `order@` / `support@` など複数アカウント運用が前提
- 認証方式は SSL / STARTTLS のいずれかから選択する設計
  - OAuth 等の他方式は将来要件 (セクション 2)

---

## 2. IMAP 接続設定

(※ SMTP は未実装。送信機能 / 通知返信は Section 8 通知設定の将来要件として整理)

### 必須情報

- アカウント名
- IMAP ホスト
- ポート (デフォルト 993)
- ユーザー
- メールボックス (デフォルト `INBOX`)
- 接続タイプ (`ssl` / `starttls`)
- ポーリング間隔 (秒、最小 30)
- 説明 (任意)

### 関連実装(他画面/共通基盤)

- パスワードはフォームに含まず、暗号化ストアに別保管
  - キー命名: `imap.{AccountId}.password`
  - `OcrViewer.Mail/Domain/Models/MailAccount.cs:47` で参照
- バックグラウンド監視サービス `MailMonitorWorker`(`OcrViewer.Mail`)
  - 30 秒周期で全アカウントを確認し、アカウント別 `poll_interval_seconds` を尊重
  - MailKit による IMAP 接続
  - 未読メール取得 → ルール判定 → 添付抽出 → ジョブ投入

### 将来要件

- 接続テストボタン (フォーム入力直後の確認用)
- OAuth 認証 (Gmail / Microsoft 365)
- Timeout 設定の明示
  - 現状は IMAP アダプタ内のハードコード
- Exchange / Gmail API 直接接続
- 接続失敗時の自動リトライ

### 注意事項

- 認証情報は安全な保管(OS キーチェーン / シークレット管理)が必須
  - 現状は暗号化された設定ストアを利用
- パスワード変更時はアカウントレコードではなく **設定ストア側** を更新する必要あり

---

## 3. OCR ルール管理

### 必須情報

- ルール名
- 送信者パターン (メールアドレスのパターンマッチ)
- OCR Engine (エンジンID、数値入力)
- Template (テンプレートID、数値、任意)
- 優先度 (小さいほど優先)
- 説明 (任意)
- 一覧アクション
  - 新規 / 編集 / 削除
- DataGrid 表示列
  - 名前 / 送信者パターン / エンジン / 優先度

### 関連実装(他画面/共通基盤)

- ルール判定は `OcrViewer.Mail/Domain/Services/RuleMatcher.cs`
  - 送信者パターンのみで判定 (case-insensitive、ドメイン/メールアドレス一致)
- 対応添付の自動フィルタは `EmailMessage.GetSupportedAttachments()` (`EmailMessage.cs:58`)
  - 対応拡張子: `.pdf .png .jpg .jpeg .gif .tiff .tif .bmp` (PDF / PNG / JPG / GIF / TIFF / BMP の 6 形式)
  - ※ OCR エンジン本体は WebP も対応するが、メール監視は対象外
- ZIP 添付の中身も `ZipExtractor` で展開して対応拡張子を抽出
- ルール削除は `t_mail_account_rule_disabled` へのソフトデリート

### 将来要件

- Subject 条件 (件名の正規表現/部分一致)
- 添付条件の明示的指定
  - 現状は MIME type + 拡張子のハードコードフィルタ
  - ルール側で「添付必須」「特定拡張子のみ」等を指定可能にする
- ファイル形式の選択 UI
  - 現状は対応拡張子がコード固定
- 有効/無効トグル
  - 現状はソフトデリートのみで一時停止の概念なし
- エンジン/テンプレートを ID 数値ではなく名称ドロップダウンで選択
- 複合条件(AND / OR)
- ルールの並べ替え(優先度ドラッグ)
- ルール複製・テンプレート化

---

## 4. OCR 処理設定

### 必須情報

- OCR Engine (ルールの `engine_id`)
- Template (ルールの `template_id`、任意)

### 関連実装(他画面)

- OCR 実行画面で Provider / Engine / Template / 言語 / 前処理を選択する仕組みあり
  - 言語と前処理はジョブ単位の指定で、メール監視のルールには紐付かない
- エンジンの解決は `_engine_resolver` で行い、ジョブ投入時に `provider_code` + `engine_code` に変換
- バックグラウンドワーカー(`MailMonitorWorker`)が添付を取り出して直接 OCR ジョブを投入

### 将来要件

- OCR Language のルール紐付け
- ルールごとの前処理プリセット
- confidence 閾値
  - 低信頼度ジョブをエラー扱いにする等の運用フックに使う
- AI 補助による Template 自動判定

### 注意事項

- ルールに紐付くのは **エンジン + テンプレートのみ**
  - 言語・前処理・閾値はジョブ作成時のデフォルト値が適用される設計

---

## 5. フォルダ・ラベル設定

### 必須情報

- Mailbox (アカウント単位で 1 つ、デフォルト `INBOX`)
- 処理後の既読化
  - 処理完了したメールに `MessageFlags.Seen` フラグを付与
  - `MailKitImapAdapter.MarkSeenAsync` / `MailMonitorWorker.cs:171, 180, 220`

### 将来要件

- 複数フォルダ監視 / OCR 対象 Folder の選択
  - 現状は Mailbox 1 つのみ指定可
- Archive Folder (処理完了後の移動先)
- Error Folder (失敗ファイルの隔離先)
- 処理後 Move
  - 現状は既読フラグのみで、フォルダ間移動はしない
- ラベル(Gmail / Exchange)対応
- 処理結果のメール返信
- 添付ファイルのストレージ転送 (S3 / OneDrive / SharePoint)

### 注意事項

- 現状 `MarkSeenAsync` は **既読フラグの付与のみ** で、元メールは Inbox に残る
- フォルダ移動を実装する場合は IMAP の `MOVE` 拡張または `COPY` + `EXPUNGE` の対応が必要

---

## 6. OCR 処理履歴

### 必須情報

- 送信者
- 件名
- ステータス (`succeeded` / `failed` / `partial` / `no_match`)
- ジョブ数 (受信 1 件に対し紐付くジョブ件数)
- 受信日時 (`yyyy/MM/dd HH:mm` 形式)
- アクション
  - 一覧再読み込み

### 関連実装(他画面)

- 結果確認画面でジョブ単位の詳細(結果テキスト・bbox・信頼度)が確認可能
  - メール監視から投入したジョブも同一パイプラインで確認できる
- 検出ログから直接遷移する動線は未実装

### 将来要件

- エラーメッセージの一覧表示
  - `Error` 文字列はモデル保持済だが DataGrid 列に出ていない
- OCR 開始 / OCR 完了時刻
  - 現状は受信時刻のみ
- 処理時間 (受信〜OCR 完了の集計)
- メール本文プレビュー
- 添付ファイルプレビュー
- 失敗ジョブの再実行導線
- 期間指定の集計 (日/週/月の成功率・件数)

### 注意事項

- 受信日時(ReceivedAt)はメールの送信日時ではなく、ワーカーが処理した記録日時
- ステータスはサーバー側で導出される値で、ジョブの成否とメッセージレコードを組み合わせる
  - すべてのジョブが成功 → `succeeded`
  - すべて失敗 → `failed`
  - 一部成功 → `partial`
  - マッチするルールなし → `no_match`

---

## 7. Queue / 実行状態

### 必須情報

なし。本画面では Queue サマリを表示しない。
処理履歴(セクション 6)で個別メールの最終ステータスのみ確認可能。

### 関連実装(他画面/共通基盤)

- ジョブ単位のステータスは API で管理(`queued` / `running` / `succeeded` / `failed` / `canceled`)
  - 結果確認画面のジョブ一覧で確認可能
- メール監視からは受信 → ルールマッチ → 添付抽出 → ジョブ作成の流れで、
  ジョブ自体は OCR 実行画面が投入するものと同じパイプラインに乗る
- `MailMonitorWorker` は **内部状態として `lastPollTime` を保持** しているが、
  API / UI には公開していない

### 将来要件

- 実行待ち件数 / 実行中件数 / Error 件数の集計表示
- Retry 件数
  - そもそも自動リトライ機構が現状無い
- 最終実行(直近の受信/OCR 実行時刻)
  - ワーカー内部の `lastPollTime` を API 経由で公開すれば対応可能
- アカウント別の Queue 集計
- グラフ表示(時系列の受信数・成功率)
- 上限超過時のアラート

### 注意事項

- メール監視画面と結果確認画面でジョブの見え方が分かれている
  - メール監視: メッセージ単位
  - 結果確認: ジョブ単位

---

## 8. 通知設定

### 必須情報

なし。本画面ではユーザー向け通知設定を持たない。

### 関連実装(他画面/共通基盤)

- バックグラウンドワーカー(`MailMonitorWorker`)はエラーを `ILogger` で記録するのみ
  - クライアント側ログ出力で、ユーザー向け通知ではない
- メール送信機構自体は別途検討必要
  - 現状は IMAP(受信)のみで、SMTP(送信)アダプタは未実装

### 将来要件

- OCR 失敗通知 / 認証エラー通知 / Queue 異常通知
- 通知チャネル
  - Slack / Mail / Teams / Webhook カスタム通知
- 通知レベル(Error / Warning / Info)の切替
- アカウント別 / ルール別の通知有効化設定

### 注意事項

- 無人 OCR 運用が前提のため、通知設計は監視と連動して必須化したい
- 通知基盤は OCR 実行画面側のエラー通知とも共通化したい
  - `ErrorHandler` / `ErrorCategory` と連携する形が望ましい

---

## 9. エラー管理

### 必須情報

- 処理履歴のステータス分類
  - `Succeeded` / `Partial` / `Failed` / `NoMatch`
- エラーメッセージ保持
  - 添付ごとに `filename: エラーメッセージ` 形式で連結
  - `t_mail_message_failed` テーブルに記録
  - 現状 UI 列には未表示
- 画面全体エラー表示オーバーレイ

### 関連実装(他画面/共通基盤)

バックグラウンドワーカーで以下を実装済(`OcrViewer.Mail/Application/Workers/MailMonitorWorker.cs`):

- ジョブ作成失敗のキャッチ
  - `catch (Exception ex) when (ex is not OperationCanceledException)`
  - キャンセル時はエラー化しない
- 認証エラー / 添付取得失敗のキャッチ
  - 例外をログ出力 + エラーメッセージに集約
- Unsupported File の自動スキップ
  - `EmailMessage.GetSupportedAttachments()` で対応拡張子のみフィルタ
  - スキップ時は記録なし(silently skip)
- ログ出力 (`logger.LogWarning` / `LogInformation`)

### 将来要件

- エラーカテゴリの分離(現状すべて連結文字列で `Failed`/`Partial` に集約)
  - 認証エラー / OCR Error / Timeout / 添付取得失敗 / Unsupported File
- カテゴリ別アイコン・色分け
  - 共通 `ErrorHandler` / `ErrorCategory` と連携
- Unsupported File の記録(silently skip からの脱却)
- Timeout の専用処理(現状ハードコード値のみ)
- 連続失敗時のアカウント自動停止
- リトライ導線(失敗ジョブの再実行)
- エラーメッセージの DataGrid 列追加(モデル保持済、低コスト改善)

### 注意事項

- 現状はエラーが発生しても `Failed` / `Partial` ステータスのみで原因がわからない
  - UI からは集約された `Error` 文字列を辿る必要がある
- 共通 `ErrorHandler` 基盤を活用すれば、OCR 実行画面と統一したエラー UI が実現可能

---

## 10. テスト実行

### 必須情報

なし。本画面では手動でのテスト実行機能を持たない。
処理は `MailMonitorWorker` のバックグラウンド自動実行のみ。

### 関連実装(他画面)

- 結果確認画面でジョブ単位の OCR 結果プレビューが可能
  - メール監視から投入したジョブも同一パイプラインで確認できる
- 一覧再読み込み(`LoadMessagesAsync`)で履歴は最新化可能

### 将来要件

- テスト受信(手動 fetch トリガー)
  - フォルダ監視の Sync 相当の機能
  - ワーカーの周期を待たずに即時チェックする UI
- テスト OCR(ドライラン)
  - ルール判定のみで実 OCR を投げない検証モード
- サンプル投入で Rule 検証する UI
  - 1 メール指定 → ルール判定結果(マッチしたルール / なし) のみ表示
- OCR Preview
  - 投入前のジョブ作成パラメータ確認(エンジン / テンプレート / 言語 / 前処理)
- ルール適用結果の差分表示
  - ルール変更前後で同一サンプル群の判定結果を比較

### 注意事項

- 本番運用前のルール検証手段が無いため、誤判定で OCR コストが膨らむリスクあり
- ワーカー周期は最小 30 秒のため、設定変更後の動作確認が遅い

# メール監視画面の代表的な画面分割

現在の実装状況・将来要件・AI-OCR 製品の実例を踏まえ、
メール監視画面のレイアウト案を以下の 2 軸 × 3 パターンで整理する。

- **将来設計なし版**(現実装寄り) … パターン①〜②
- **将来設計あり版**(AI-OCR 完成系寄り) … パターン③〜⑤

メール監視は、単なる「メール受信設定」ではなく、
**メール添付ファイルを OCR へ自動投入するワークフロー画面** として考えるのが適切。

---

## 前提整理

| 方針 | 評価 |
| ---- | -- |
| 左:Mail アカウント一覧 | ◎ |
| 中央:OCR Rule 一覧 | ◎ |
| 右:Rule 詳細 | ◎ |
| OCR Engine / Template 分離 | ◎ |
| Queue / 処理履歴の責務分離 | ◎ |

## パターン① 3ペイン + 中央タブ型(最推奨)

### 画面図

```text
┌──────────────┬──────────────────────┬──────────────┐
│ Mail一覧     │ [ルール] [履歴]      │ Rule詳細     │
│              ├──────────────────────┤              │
│ ● invoice@   │ (タブで切替表示)     │ OCR Engine   │

│   同期 1h前  │   sender=invoice     │ Description  │
│ ⚠ support@   │   sender=order       │              │
│   認証エラー │   sender=support     │ [保存]       │
│              │   ＋ ✎ ×             │              │
│ ＋ ✎ ×       │                      │              │
│              │ [履歴] 選択時:       │              │
│              │   送信者/件名/       │              │
│              │   ステータス/日時    │              │
└──────────────┴──────────────────────┴──────────────┘

凡例:
  ● = 動作中  ⚠ = 接続/認証エラー
  ※ 状態アイコン (●/⚠) と「同期 N前」表示は将来要件 (Section 1 将来要件参照)。
    現実装には未存在。短期改修で追加する想定
  Mail一覧 下の ＋/✎/× = アカウント新規/編集(IMAP接続設定モーダル)/アーカイブ
  中央タブ:
    [ルール] = OCR ルール一覧 (内側 ＋/✎/× でルール CRUD)
    [履歴]  = メール受信履歴 (メッセージ単位、現実装の処理履歴タブ相当)
  Rule詳細 (右ペイン) = [ルール]タブで選択中のルールに連動
```

### 画面分割

| 領域 | 内容 |
| ---- | ---- |
| 左 20% | メールアカウント一覧 + アカウント CRUD アイコン (＋/✎/×) |
| 中央 45% | TabControl: [ルール](OCR ルール一覧) / [履歴](メール受信履歴) |
| 右 35% | ルール詳細 (常駐編集ペイン、[ルール]タブの選択に連動) |

### メリット

| 項目 | 評価 |
| ---- | ---- |
| OCR 運用向き | アカウントごとのルール管理がしやすい |
| 拡張性 | Subject 条件・添付条件などを追加しやすい |
| 見通し | Mail → Rule → OCR の流れが分かりやすい |
| 履歴アクセス | 中央タブ切替でメール受信履歴を画面内で確認可能 |

### デメリット

| 項目 | 評価 |
| ---- | ---- |
| 情報量 | 初心者には少し多く見える |
| 画面幅 | 小さい画面では窮屈 |
| 同時性なし | ルール一覧と受信履歴を同時表示できない (タブ切替必要)。同時表示にはパターン⑤ |

# 一押しのパターン

## 短期 (即時実装) → パターン① 3ペイン + 中央タブ型(最推奨)

### 理由

- **現実装の構造に最も近く改修コスト最小** (現在の 2-pane + TabControl を 3-pane + 中央タブに拡張するだけ)
- メール監視の本質である **「無人運用が止まっていないか」を一目で把握** できる
- アカウント編集 = モーダル / ルール編集 = 常駐 Inspector ペイン の責務分離が明確
  - ルール編集が頻繁なので常駐ペインで効率化
  - アカウント編集は項目数が多いのでモーダル維持
- メール受信履歴を **中央タブ [履歴] で画面内に常駐** 可能 (現実装の処理履歴タブと同じ機能)
- 状態アイコン (●/⚠) + 最終同期日時で **アカウントの動作状態が一覧で見える** (将来要件)
- 11/11 責務完全カバー

### 学習コスト最小

ファイラ・メーラと同じ Master-Detail 構造で、初見でも直感的に理解可能。

## 長期 (将来ゴール) → パターン⑤ 3ペイン+中央縦分割型(運用統合完成系)

中央を縦分割して **ルール一覧と受信履歴を同時表示** することで、「このルールでヒットした受信メール」を画面遷移なしで即座に確認可能。Subject 条件・添付フィルタ・通知・リトライなどの将来要件が実装された後の到達点。
