# ResultView 確認ステータス管理機能 設計書

**機能名**: OCR結果一覧 確認ステータス管理
**対象画面**: ResultView

---

## 1. 背景・目的

OCR結果の運用フローにおいて、各 OCR 結果がオペレーターにより「確認済みか否か」「修正が行われたか」を把握できないという課題がある。本機能は OCR 結果ごとに確認ステータスを記録・表示・絞り込みできるようにし、確認作業の進捗管理と品質追跡を可能にする。

---

## 2. 現状確認

### 2-1. ResultView 構造

| ペイン | 幅 | 内容 |
|--------|-----|------|
| 左 | 250px | ジョブ履歴リスト + 検索・フィルタ |
| 中央 | * | 画像ビューア（バウンディングボックス付き） |
| 右 | 350px | テキストパネル（編集・Undo/Redo） |

### 2-2. 既存フィルタ

| フィルタ | 種別 | バインディング |
|---------|------|--------------|
| テキスト検索 | TextBox | `SearchQuery` |
| ステータス（ジョブ + 確認） | 統合フィルターパネル（チェックボックス） | `ResultViewModel.JobStatusFilterOptions` / `ReviewStatusFilterOptions`（`IReadOnlyList<SelectableItem>`）。内部状態は `_statusFilters`（`HashSet<string>`）で管理するが、公開バインディング名としての `StatusFilters` プロパティは存在しない |
| 投入日 | 統合フィルターパネル（DatePicker × 2） | `DateFrom` / `DateTo` |

フィルタは `FilteredJobHistory`（LINQ / in-memory）で即時反映される。既存の `StatusFilter`（`string?` 単一選択 ComboBox）と `IsDateFilterVisible` / `OpenDateFilterCommand` 等は統合フィルターパネルに置き換える（§5 参照）。

### 2-3. 既存ステータス体系との区別

現在 `JobStatus`（`OcrViewer.Sdk/Domain/ValueObjects/JobStatus.cs`）が OCR パイプラインの処理状態（`Queued` / `Running` / `Succeeded` / `Failed` / `Canceled`）を管理している。本機能で追加する「確認ステータス」はこれとは独立した概念であり、OCR 処理が完了（`Succeeded`）した後のオペレーター確認フェーズを表す。混同を避けるため型名は `ReviewStatus` とし、UI でも「ジョブステータス」と「確認ステータス」を明確に区別する。

### 2-4. 永続化の仕組み

本システムはマルチユーザー対応のため、**確認ステータスおよびジョブ一覧はサーバー側 PostgreSQL に保存する**。クライアントは API を介してデータの読み書きを行う。

**サーバー側（新規追加）**:

| テーブル | プレフィックス | 役割 |
|---------|-------------|------|
| `a_job_review` | `a_`（属性） | ジョブ単位のレビューサマリー（`m_job` と 1:1） |
| `t_job_block_review_set` | `t_`（イベント） | TextBlock 単位のレビュー操作履歴（追記のみ） |

**`a_job_review` カラム定義**:

| カラム名 | 型 | 説明 |
|--------|-----|------|
| `job_id` | INTEGER（PK、FK → `m_job.id`） | ジョブ ID |
| `summary_status` | VARCHAR(20) | ジョブ全体の確認状態（`"unreviewed"` / `"completed"` / `null`（succeeded 以外）） |
| `updated_at` | TIMESTAMPTZ | 最終更新日時（ジョブ成功時は `succeeded_at` と同値、レビュー更新時は `reviewed_at` と同値） |

**`t_job_block_review_set` カラム定義**:

| カラム名 | 型 | 説明 |
|--------|-----|------|
| `id` | SERIAL（PK） | 自動採番 |
| `job_id` | INTEGER（FK → `m_job.id`、index） | ジョブ ID |
| `page_no` | INTEGER | ページ番号（1 始まり） |
| `block_type` | VARCHAR(20) | `"line"` / `"word"` / `"table"` |
| `block_index` | INTEGER | そのページ内の配列インデックス（0 始まり） |
| `review_status` | VARCHAR(20) | `"unreviewed"` / `"completed"` / `"completed_with_edit"` |
| `edited_text` | TEXT（NULL 可） | テキスト修正内容（ジョブ再表示時に復元する。修正がない場合は NULL） |
| `reviewed_at` | TIMESTAMPTZ | 操作日時 |

> **イベントソーシング**: `t_job_block_review_set` は操作のたびに INSERT する（UPDATE / DELETE 禁止）。最新状態は `job_id` + `page_no` + `block_type` + `block_index` でグループ化し、最大 `id` の行を使う。

> **`a_job_review` の作成タイミング**: `m_job` の INSERT と同一トランザクションで INSERT する（既存の `a_*` テーブルと同じパターン）。作成時は `summary_status = null` で初期化し、`t_job_succeeded` 記録と同一トランザクションで `summary_status = 'unreviewed'` に UPDATE する。`failed`・`canceled`・`running`・`queued` のジョブは `summary_status` が `null` のまま維持される（「レビュー対象外」を意味する）。`GET /v1/jobs` は `m_job` と `a_job_review` を INNER JOIN で取得できる。

> **`block_index` の安定性と `page_no` の変換**: `block_index` は OCR 結果 JSON（`result_path`）の `page.words` / `page.lines` / `page.tables` の配列インデックス（0 始まり）に対応する。ジョブは `SUCCEEDED` 後に再処理されないため配列順は不変である。クライアント側の `CurrentPageIndex`（0 始まり）に対し、`page_no` は 1 始まりのため、実装時は `page_no = CurrentPageIndex + 1` で変換する。

**クライアント側**:

- ジョブ一覧は `GET /v1/jobs` API から取得する（`job-history.json` をジョブ一覧として使わない）
- `job-history.json` は `FilePath`（OCR 対象画像のローカルパス）のみ保持し、画像表示のキャッシュとして使う
- TextBlock 単位のレビュー状態は `GET /v1/jobs/{job_id}/review-state` API から取得し、ローカルには保持しない
- ジョブ表示時は OCR 結果 JSON を読み込んだ後に `GET /v1/jobs/{job_id}/review-state` を呼び出し、`edited_text` が存在するブロックのテキストを上書きして表示する（`review_status` が `"completed_with_edit"` のブロックのみ上書き対象）

**新規 API エンドポイント**:

| メソッド | パス | 用途 |
|---------|------|------|
| `GET` | `/v1/jobs` | ジョブ一覧取得（レビューサマリーを含む） |
| `GET` | `/v1/jobs/{job_id}/review-state` | TextBlock 単位のレビュー状態取得（`review_status` / `edited_text` を含む） |
| `PATCH` | `/v1/jobs/{job_id}/review-state` | 1ブロック分のレビュー状態を更新（差分更新） |

**`GET /v1/jobs/{job_id}/review-state` レスポンス**:

レビュー操作済みのブロックのみを配列で返す（既存の `GET /v1/results/{job_id}` と同じく全件一括返却・ページネーションなし）。レスポンスに含まれないブロックはクライアントが `"unreviewed"` として扱う。

| フィールド名 | 型 | 説明 |
|------------|-----|------|
| `page_no` | INTEGER | ページ番号（1始まり） |
| `block_type` | STRING | `"line"` / `"word"` / `"table"` |
| `block_index` | INTEGER | そのページ内の配列インデックス（0始まり） |
| `review_status` | STRING | `"completed"` / `"completed_with_edit"` |
| `edited_text` | STRING \| NULL | 修正テキスト（`"completed_with_edit"` のときのみ非 `null`） |

**`PATCH /v1/jobs/{job_id}/review-state` リクエストボディ**:

| フィールド名 | 型 | 必須 | 説明 |
|------------|-----|------|------|
| `page_no` | INTEGER | ○ | ページ番号（1始まり） |
| `block_type` | STRING | ○ | `"line"` / `"word"` / `"table"` |
| `block_index` | INTEGER | ○ | そのページ内の配列インデックス（0始まり） |
| `review_status` | STRING | ○ | `"unreviewed"` / `"completed"` / `"completed_with_edit"` |
| `edited_text` | STRING \| NULL | △ | `review_status` が `"completed_with_edit"` のとき必須。それ以外は `null` |

**`PATCH /v1/jobs/{job_id}/review-state` レスポンスボディ**:

| フィールド名 | 型 | 説明 |
|------------|-----|------|
| `summary_status` | STRING | サーバーが再集計したジョブ全体のレビュー状態（`"unreviewed"` / `"completed"`） |

> **1リクエスト = 1ブロック**: 1回の `PATCH` で更新するブロックは1件のみ。サーバーは受信のたびに `t_job_block_review_set` へ1行 INSERT し、`a_job_review.summary_status` を再集計して UPDATE する（同一トランザクション）。

> **`summary_status` の再集計ルール**: `PATCH` 処理時、サーバーは OCR 結果 JSON のブロック総数と `t_job_block_review_set` の登録済みレコード数を照合し、以下のルールで集計する。`t_job_block_review_set` に存在しないブロックは `"unreviewed"` として扱う。1件でも `"unreviewed"`（未登録含む）があれば `"unreviewed"`、全ブロックが登録済みかつ全件が `"completed"` または `"completed_with_edit"` であれば `"completed"` を `a_job_review.summary_status` にセットする。

**`GET /v1/jobs` レスポンスフィールド**:

| フィールド名 | 型 | 取得元 | 説明 |
|------------|-----|--------|------|
| `reportId` | INTEGER | `m_job.id` | ジョブ ID |
| `fileName` | STRING | `m_job.original_filename` | ファイル名 |
| `fileSizeBytes` | INTEGER | `m_job.file_size_bytes` | ファイルサイズ（バイト） |
| `createdAt` | TIMESTAMPTZ | `m_job.created_at` | 投入日時 |
| `status` | STRING | イベントテーブルから導出（既存 `GET /v1/statuses/{job_id}` と同ロジック） | `"queued"` / `"running"` / `"succeeded"` / `"failed"` / `"canceled"` |
| `provider` | STRING | `m_provider` JOIN | OCR プロバイダー名 |
| `engine` | STRING \| NULL | `m_engine` JOIN | OCR エンジン名 |
| `summaryStatus` | STRING \| NULL | `a_job_review.summary_status`（INNER JOIN） | `"unreviewed"` / `"completed"` / `null`（`succeeded` 以外のジョブは `null`） |

> **`filePath` はレスポンスに含まない**: `filePath` はクライアントがジョブ投入時に使用したローカルファイルパスであり、サーバーは保持しない。クライアントは `reportId` をキーとして `job-history.json` から `filePath` を引く（画像表示のキャッシュ用途）。

> **既存エンドポイントへの影響なし**: `GET /v1/statuses/{job_id}`・`GET /v1/results/{job_id}` の仕様は変更しない。

- 1件以上の条件が有効なとき、ヘッダーアイコンに件数バッジと `FilterSummary` を表示

### 3-2. 画面項目定義

| 項目名 | 種別 | バインディング | 初期値 | 役割 |
|--------|------|--------------|--------|------|
| 統合フィルターアイコン | Button | `ResultViewModel.OpenFilterPanelCommand` | — | パネル開閉。条件数バッジ（`FilterActiveCount`）と `FilterSummary` を重ねて表示 |
| 統合フィルターパネル | Popup/Border | `ResultViewModel.IsFilterPanelVisible` | 非表示 | 投入日・ステータスをまとめて設定 |
| ジョブステータス チェックボックス群 | CheckBox × 5 | `SelectableItem.IsSelected`（TwoWay）を `ResultViewModel.JobStatusFilterOptions` にバインド | 全未選択 | 成功／失敗／処理中／待機中／キャンセル の複数選択（セクション内 OR）。`HashSet<string>` は直接 IsChecked にバインドできないため既存 `SelectableItem` を使って同期する（§6-4 参照） |
| 確認ステータス チェックボックス群 | CheckBox × 2 | `SelectableItem.IsSelected`（TwoWay）を `ResultViewModel.ReviewStatusFilterOptions` にバインド | 全未選択 | 完了／未確認 の複数選択（セクション内 OR、ジョブステータスと AND）。XAML 例: `<CheckBox Content="{Binding DisplayName}" IsChecked="{Binding IsSelected, Mode=TwoWay}"/>`（`ExecutionView.xaml` と同じパターン） |
| フィルター条件サマリー | TextBlock | `ResultViewModel.FilterSummary` | 非表示 | パネルを閉じた後にヘッダー下へ適用中の条件を日本語で表示（例:「成功・失敗 かつ 未確認」） |
| すべてクリアボタン | Button | `ResultViewModel.ClearAllFiltersCommand` | — | 投入日・ステータス両フィルターをリセット |
| 確認ステータスバッジ（一覧行） | Border + TextBlock | `JobHistoryItemViewModel.ReviewStatusBadgeDisplay`（ラベル）/ `ReviewStatusKey`（DataTrigger 色切り替え） | 「未確認」 | 各ジョブの確認状態をラベル表示（succeeded のみ表示、完了 / 未確認 の2値） |
| 編集モード切り替えボタン（[✏]） | ToggleButton | `ResultViewModel.IsEditMode` | OFF | ON 時に全 TextBlock を TextBox に切り替え。ON 状態でアイコン強調表示 |
| 一括完了ボタン | Button | `ResultViewModel.BulkCompleteUnreviewedCommand` | 非活性 | 現在ページの「未確認」TextBlock をすべて「完了」に変更（修正完了は変更しない） |
| TextBlock ステータスボタン（Right Pane 各行） | Button | `TextBlockViewModel.ReviewStatusKey`（ラベル）/ `MarkCompleteCommand`（直接バインド）/ `MarkUnreviewedCommand`（**XAML 非バインド**・code-behind の `MarkUnreviewed_Click` 経由） | 「確認済みにする」 | 「確認済みにする」→`MarkCompleteCommand` 直接実行。「未確認に戻す」→ダイアログなし（`Completed`）または確認ダイアログ（`CompletedWithEdit`）をcode-behindで処理し `MarkUnreviewedCommand` 実行（§4-2, §6-5 参照） |

**確認ステータスバッジ カラーマッピング**

ジョブ一覧行のバッジは「完了」と「未確認」の2値のみを表示する。`CompletedWithEdit`（修正完了）は TextBlock 単位のステータスであり、ジョブ行バッジには表示しない。

| 値 | 表示文字列 | バッジ色 | 表示箇所 |
|----|-----------|---------|---------|
| `Unreviewed` | 未確認 | グレー `#E9ECEF` | ジョブ一覧バッジ |
| `Completed` | 完了 | 青 `#CCE5FF` | ジョブ一覧バッジ |
| `CompletedWithEdit` | 修正完了 | 緑 `#D4EDDA` | TextBlock 単位（Right Pane）のみ |

`ReviewStatusDisplay` は上記の日本語文字列を返す（表示専用）。ステータスフィルターのチェックボックス Tag 値は英語小文字（`"completed"`）を使用し、`FilteredJobHistory` 内で `_statusFilters.Contains(j.ReviewStatusKey)` で比較する。DataTrigger によるバッジ色切り替えも同じ `ReviewStatusKey` を使用する。

### 3-3. ユーザー操作と挙動

| 操作 | 挙動 |
|------|------|
| ジョブ履歴から項目を選択 | Right Pane に OCR 結果を表示。編集モードは OFF にリセット |
| [✏] ボタンを押下 | 編集モード ON：全 TextBlock が TextBox に切り替わる。ボタン強調表示 |
| 再度 [✏] ボタンを押下 | 編集モード OFF：全 TextBlock が表示モードに戻る。**未確定の編集内容は破棄される（`CancelEdit()` 呼び出しのため Undo スタックには残らない）** |
| 編集モード ON 中に Tab キー | 現在の TextBox から次の TextBox へフォーカス移動 |
| 編集モード ON 中にテキストを確定（✓ または Tab） | 最初の OCR 結果と異なる場合 → 「修正完了」に自動遷移。`CompletedWithEdit` のときに元のテキストと同じ場合 → 「未確認」に戻す（`Completed` は変化なし）。Left Pane のジョブバッジも即時更新 |
| 「すべて完了にする」ボタンをクリック | 確認ダイアログを表示（例:「このページの未確認 3 件を完了にしますか？」）。「はい」→ 現在ページの「未確認」TextBlock をすべて「完了」に変更。「完了」「修正完了」は変更しない |
| TextBlock の「確認済みにする」ボタンをクリック | 「完了」に遷移 |
| TextBlock の「未確認に戻す」ボタンをクリック | 「未確認」に遷移。Completed のときはダイアログなし。CompletedWithEdit のときは確認ダイアログを表示し、「はい」→ テキストを OCR 初期値に戻し「未確認」に遷移、「いいえ」→ 何もしない |
| [▼] アイコンをクリック | 統合フィルターパネルを開く |
| フィルターパネル外をクリック / Escape キー | 統合フィルターパネルを閉じる |

## 4. 機能仕様

### 4-1. 確認ステータス定義

| 値 | 意味 |
|----|------|
| `Unreviewed`（未確認） | 初期状態（新規ジョブ登録時に自動付与） |
| `CompletedWithEdit`（修正完了） | OCR 結果を編集して確認済み |
| `Completed`（完了） | OCR 結果を編集せず確認済み |

**実装パターン**:

`ReviewStatus` は単純 enum として `OcrViewer.Sdk/Domain/Models/ReviewStatus.cs` に独立ファイルで配置する（`JobStatusValue` + `JobStatus` の 2 層ラッパー構造は採らない）。変換・表示用メソッドは `ReviewStatusExtensions.cs` に分離する（`MatchTypeExtensions.cs` と同じく `Domain/Models/` 配置、責務分離のパターンを踏襲）。メソッド構成（`FromKey()` / `ToKey()` / `ToDisplay()`）は `ReviewStatus` 固有の設計であり、詳細実装は §6-1 参照。

### 4-2. ステータス遷移

**前提**:
- `Completed`（完了）状態では、テキストは常に OCR 初期値と同一である（`HasChanges = false`）
- `CompletedWithEdit`（修正完了）状態では、テキストは OCR 初期値と異なる（`HasChanges = true`）

**ステータスボタン**:

| 現在のステータス | 表示するボタン | 活性条件 |
|----------------|--------------|---------|
| `Unreviewed` | 「確認済みにする」（`MarkCompleteCommand`） | `ReviewStatus == Unreviewed` のときのみ活性。`Completed` / `CompletedWithEdit` では非活性 |
| `Completed` または `CompletedWithEdit` | 「未確認に戻す」（`MarkUnreviewedCommand`） | `ReviewStatus == Completed` または `CompletedWithEdit` のときのみ活性 |

「未確認に戻す」の動作:
- `ResetToOriginal()` でテキストを OCR 初期値に戻し、`ReviewStatus = Unreviewed` に変更する
- `CompletedWithEdit` から押した場合のみ確認ダイアログを表示する（編集内容が失われるため）
- `Completed` から押した場合はダイアログなし（テキストは既に初期値のため実質変化なし）

**「未確認に戻す」ボタンの呼び出し経路**:

`MarkUnreviewedCommand` は `TextBlockViewModel` が持つが、XAML から直接バインドしない。`CompletedWithEdit` のときは確認ダイアログを挟む必要があるため、`ResultView.xaml.cs` の code-behind がボタンクリックを受け取り、以下の経路で実行する。

| ステータス | code-behind の処理 |
|-----------|------------------|
| `Completed` | 確認ダイアログなし → そのまま `tb.MarkUnreviewedCommand.Execute(null)` |
| `CompletedWithEdit` | `MessageBox.Show(…, MessageBoxButton.YesNo)` で確認 → Yes なら `tb.MarkUnreviewedCommand.Execute(null)` / No なら何もしない |

**遷移テーブル**:

| 操作（トリガー） | 遷移元 | 遷移先 | 備考 |
|----------------|--------|--------|------|
| ジョブ登録 | — | `Unreviewed` | 初期状態 |
| 「確認済みにする」クリック | `Unreviewed` | `Completed` | テキスト変化なし |
| テキスト確定（変更あり） | `Unreviewed` | `CompletedWithEdit` | |
| テキスト確定（変更あり） | `Completed` | `CompletedWithEdit` | 完了でも編集があれば修正完了へ |
| テキスト確定（変更あり） | `CompletedWithEdit` | `CompletedWithEdit` | 自己遷移（修正内容を上書き） |
| テキスト確定（変更なし） | `CompletedWithEdit` | `Unreviewed` | 元に戻したら未確認へ |
| テキスト確定（変更なし） | `Completed` | `Completed` | 変化なし |
| テキスト確定（変更なし） | `Unreviewed` | `Unreviewed` | 変化なし |
| 「未確認に戻す」クリック | `Completed` | `Unreviewed` | `ResetToOriginal()` 実行。ダイアログなし |
| 「未確認に戻す」→「はい」 | `CompletedWithEdit` | `Unreviewed` | `ResetToOriginal()` 実行。確認ダイアログあり |
| 「すべて完了にする」→「はい」 | `Unreviewed`（対象のみ） | `Completed` | `CompletedWithEdit` は対象外 |

### 4-3. ジョブ単位のステータス集計ルール

**前提**: `Succeeded` のジョブには必ず1件以上の TextBlock が存在する。TextBlock が0件の場合は未取得（そのジョブをまだ開いていない）として扱う。

**集計ルール**:

| TextBlock の状態 | ジョブバッジ表示 |
|-----------------|----------------|
| 1件でも `Unreviewed` がある | **未確認**（グレー） |
| 全件が `Completed` または `CompletedWithEdit` | **完了**（青） |
| `JobStatus` が `Succeeded` 以外 | バッジを表示しない |

- `CompletedWithEdit` は集計上「完了」として扱う
- 不正値（JSON 読み込み時の未知文字列等）は `Unreviewed` として扱う（TextBlock 個別・ジョブ集計値ともに同様）

**バッジ値の保持**:

各 `JobHistoryItemViewModel` は自身のレビュー集計値（`ReviewStatusKey`）を保持する。

| 状況 | 集計値の取得元 |
|------|-------------|
| TextBlock 未取得（未選択） | `GET /v1/jobs` レスポンスの `summaryStatus` |
| TextBlock のステータスが変わったとき | `PATCH` レスポンスの `summary_status` |

**集計タイミング**:

| タイミング | 処理 |
|----------|------|
| `LoadResultAsync` 完了時 | `GET /v1/jobs/{job_id}/review-state` のレスポンスから各 TextBlock の `ReviewStatus` を**復元**する。`ReviewStatusKey`（ジョブバッジ）はこのタイミングでは更新しない（初期バッジ値は `GET /v1/jobs` の `summaryStatus` をそのまま使う） |
| TextBlock のステータスが変わったとき | `PATCH /v1/jobs/{job_id}/review-state` を呼び出し、レスポンスの `summary_status` で `ReviewStatusKey` を更新する |
| 別のジョブに切り替えたとき | 切り替え前のジョブの `ReviewStatusKey` は最後の `PATCH` レスポンス値を維持する |

**集計の流れ**:

```
TextBlock のステータスが変わる
         ↓
ResultViewModel が変化を検知
         ↓
IReviewStateGatewayPort.PatchReviewStateAsync() でサーバーに送信する
         ↓
レスポンスの summary_status を受け取る
         ↓
SelectedHistoryItem.ReviewStatusKey = summary_status
→ Left Pane バッジが即時更新される
```

> **一括完了時の PATCH 送信順序**: `BulkCompleteUnreviewed` では PATCH を逐次送信する（並列 fire-and-forget にしない）。並列送信すると応答が順不同で返り `summary_status` が古い値で上書きされる可能性があるため、前の PATCH レスポンスを受け取ってから次を送信する。途中の PATCH が失敗しても残りの送信は続行する（ベストエフォート。失敗分は `ErrorMessage` に表示）。

> **PATCH 失敗時の扱い**: `TextBlock.ReviewStatus` のロールバックは行わない（初版許容）。エラーは `ResultViewModel.ErrorMessage` に設定して表示する（既存の `ExecuteWithLoadingAsync` エラーハンドリングと同パターン）。

> **同一 TextBlock への連続操作**: `OnTextBlockPropertyChanged` からの fire-and-forget により、同一ブロックを素早く連続変更すると複数の PATCH が並走し、古い値が後着する可能性がある（初版許容）。性能・整合性の問題が生じた場合はキャンセル可能なトークン（`CancellationTokenSource` per `TextBlockKey`）を用いたデバウンスを検討する。

### 4-4. 永続化データ構造

**データ保存先の整理**:

レビュー状態はサーバー側 PostgreSQL（`t_job_block_review_set`・`a_job_review`）に保存する。クライアントの `job-history.json` にレビュー状態のフィールドは追加しない。

| データ | 保存先 | API |
|--------|--------|-----|
| ジョブ一覧・レビューサマリー | サーバー（PostgreSQL） | `GET /v1/jobs` |
| TextBlock 単位のレビュー状態 | サーバー（PostgreSQL） | `GET /v1/jobs/{job_id}/review-state` |
| OCR 対象画像のローカルパス | `job-history.json`（`FilePath` のみ） | — |

**レビュー状態の読み込み（`LoadResultAsync` 内）**:

OCR 結果 JSON の読み込み後、`GET /v1/jobs/{job_id}/review-state` を呼び出す。レスポンスに含まれるブロックは `page_no`（1始まり）・`block_type`・`block_index` で識別される。クライアント内部では下記の `TextBlockKey` 形式に変換して TextBlock ViewModel とマッチングする。

**`TextBlockKey` フォーマット**（クライアント内部の識別子）:

| 部位 | 内容 |
|------|------|
| `pageIndex` | ページ番号（0始まり = `page_no - 1`） |
| `type` | `"line"` / `"word"` / `"table"` |
| `blockIndex` | そのページ内の配列インデックス（0始まり） |

例: `"0_line_2"`（1ページ目・line タイプ・インデックス 2）

**`LoadResultAsync` の処理フロー（ジョブ選択時）**:

ジョブを選択したとき（`OnSelectedHistoryItemChanged`）、`LoadResultAsync` を下記の順で実行する。

| ステップ | 処理 | 備考 |
|---------|------|------|
| 1 | `_getResultUseCase.ExecuteAsync(reportId)` | OCR 結果 JSON を取得し `CurrentResult` にセット |
| 2 | `_reviewStateGateway.GetReviewStateAsync(reportId)` | `GET /v1/jobs/{job_id}/review-state` を呼び出してレビュー状態を取得 |
| 3 | レスポンスの各エントリを `TextBlockKey` 形式に変換して `_reviewStateCache` を構築 | `page_no - 1` → `pageIndex` に変換。`{"0_line_2": (Completed, null)}` の形式 |
| 4 | `ImageDisplay.CurrentPageIndex = 0` でページをリセット | |
| 5 | `UpdateBoundingBoxesForCurrentPage()` | バウンディングボックスを更新 |
| 6 | `UpdateTextBlocksForCurrentPage()` | `_reviewStateCache` を参照して各 TextBlock の `ReviewStatus` と `edited_text` を復元 |

`_reviewStateCache` は `Dictionary<string, (ReviewStatus ReviewStatus, string? EditedText)>` 型で、ジョブ切り替えのたびに再構築する。ステップ 6 の時点ではまだ `TextBlocks.CollectionChanged` に TextBlock が追加される前のため、`vm.ReviewStatus = cached.ReviewStatus` で直接セットしても `OnTextBlockPropertyChanged` は発火しない（余計な PATCH リクエストは送信されない）。

**レビュー状態の保存（`SaveCurrentReviewStatus` 内）**:

TextBlock のステータスが変わるたびに `PATCH /v1/jobs/{job_id}/review-state` を呼び出す。1回のリクエストで1ブロック分を送信する（2-4 節「`PATCH /v1/jobs/{job_id}/review-state` リクエストボディ」参照）。PATCH 成功後は `_reviewStateCache` も更新し、ページを切り替えて戻ったときに最新状態が復元できるようにする。

## 6. 実装方針（概要）

### 6-1. ReviewStatus 型

`enum` を `Domain/Models/` に独立ファイルとして配置する（`MatchType` は `Dictionary.cs` 内で定義されており独立ファイルはないが、`ReviewStatus` は独立ファイルとして配置する）。変換・表示用メソッドを `static` 拡張クラス（`ReviewStatusExtensions.cs`）に分離する。**配置場所**のみ `MatchTypeExtensions.cs` と同じ `Domain/Models/` に揃えるが、`MatchTypeExtensions` は `ParseFromString()` 1本しか持たないため、**API 構成（`FromKey()` / `ToKey()` / `ToDisplay()`）は `ReviewStatusExtensions` 独自の設計**である。

### 6-2. TextBlockViewModel への追加

`ReviewStatus` は `[ObservableProperty]` で管理し、`[NotifyCanExecuteChangedFor]` でボタンの活性制御を自動化する（既存の `_isDateFilterVisible` + `[NotifyCanExecuteChangedFor]` と同じパターン）。

`TextBlockKey` は ResultViewModel 側から付与し、TextBlockViewModel は `init` プロパティで受け取るだけ。

> **Note（既存パターンからの意図的な逸脱）**
> `MarkCompleteCommand` / `MarkUnreviewedCommand` は既存の `TextBlockViewModel` パターン（plain method のみ）から意図的に外れ、item VM に `[RelayCommand]` を直接配置する。理由: CanExecute による項目ごとのボタン活性制御（`Unreviewed` のみ「確認済みにする」が有効など）を `[NotifyCanExecuteChangedFor]` で自動化するため。`TextEditingViewModel` の編集コマンド群は TextBlock をまたいだ Undo/Redo を管理する役割があるが、ステータスコマンドは各 TextBlock の独立した状態遷移であり item VM が持つのが適切。

```csharp
[ObservableProperty]

[NotifyCanExecuteChangedFor(nameof(MarkCompleteCommand))]
[NotifyCanExecuteChangedFor(nameof(MarkUnreviewedCommand))]

// CommitEdit() の変更箇所（レビュー状態遷移のみここに集約）
// ─ 呼び出し経路は3種類あり、いずれもこのメソッドを経由する：
//   ① TextEditing.CommitEditTextBlockCommand 経由（LostFocus / Tab）
//     → Undo/Redo に登録される。Undo 呼び出し時は SetTextWithoutTracking() が呼ばれ、
//       ReviewStatus も連動して再評価される（CompletedWithEdit → Unreviewed 等）。
//   ② ResultView.xaml.cs の EditingTextBox_KeyDown（Enter キー）
//     → CommitEdit() を直接呼ぶため Undo/Redo に登録されない。
//       ReviewStatus 遷移は永続（Undo 不可）。現状の動作を維持する（変更不要）。
//   ③ ResultView.xaml.cs の ConfirmEditButton_Click（✓ ボタン）→ 同上
// ReviewStatus の遷移は呼び出し経路に関わらずすべてここで処理する
// ※ ②③ 経由の ReviewStatus 遷移は Undo で戻せないが、テキスト変更も同様に Undo 不可のため
//   テキストと ReviewStatus の不整合は生じない（初版許容）
public void CommitEdit()
{
    Text = EditingText;
    IsEditing = false;
    OnPropertyChanged(nameof(HasChanges));

    if (HasChanges)
        ReviewStatus = ReviewStatus.CompletedWithEdit;
    else if (ReviewStatus == ReviewStatus.CompletedWithEdit)
        ReviewStatus = ReviewStatus.Unreviewed;
    // Completed + 変更なし → そのまま維持
}

// 「確認済みにする」ボタン（Unreviewed のときのみ活性）

// CompletedWithEdit のとき → ResultView.xaml.cs（code-behind）が確認ダイアログを表示し「はい」のときに呼ぶ
// ResetToOriginal() は IsEditing を変更しないため、編集モード中に呼ぶ場合は
// 呼び出し元（ResultView.xaml.cs）が先に CancelEdit() を呼んで IsEditing を落とす
[RelayCommand(CanExecute = nameof(CanMarkUnreviewed))]
private void MarkUnreviewed()
{
    ResetToOriginal();
    // CompletedWithEdit → Unreviewed は ResetToOriginal() が処理済み
    // Completed → Unreviewed はここで処理（テキストは既に初期値のため HasChanges = false のまま）
    if (ReviewStatus == ReviewStatus.Completed)
        ReviewStatus = ReviewStatus.Unreviewed;
}
private bool CanMarkUnreviewed() =>
    ReviewStatus == ReviewStatus.Completed ||
    ReviewStatus == ReviewStatus.CompletedWithEdit;

// Undo/Redo 用テキスト設定（CommitEdit() と同じ遷移ルールを適用）
// テキストが元の OCR 結果に戻った場合は修正完了 → 未確認に自動遷移する
public void SetTextWithoutTracking(string text)
{
    Text = text;
    EditingText = text;
    OnPropertyChanged(nameof(HasChanges));

    if (HasChanges)
        ReviewStatus = ReviewStatus.CompletedWithEdit;
    else if (ReviewStatus == ReviewStatus.CompletedWithEdit)
        ReviewStatus = ReviewStatus.Unreviewed;
}

// 元テキストへの復元（MarkUnreviewed() および ResetAllEdits() から呼ばれる）
// テキストを元に戻し、CompletedWithEdit であれば未確認に自動遷移する
// Completed の状態遷移（Completed → Unreviewed）は MarkUnreviewed() 側で行う
public void ResetToOriginal()
{
    Text = _originalText;
    EditingText = _originalText;
    OnPropertyChanged(nameof(HasChanges));

    if (ReviewStatus == ReviewStatus.CompletedWithEdit)
        ReviewStatus = ReviewStatus.Unreviewed;
}
```

### 6-4. ResultViewModel への追加

#### TextBlock の ReviewStatus 変化を検知する仕組み

`ImageDisplay.PageChanged` や `JobHistory.CollectionChanged` と同じ購読パターンを使う（`_undoRedoService` は `TextEditingViewModel` 内にあり `ResultViewModel` からは直接参照しない）。  
コンストラクタで `TextBlocks.CollectionChanged` を購読し、各 TextBlock の `PropertyChanged` を購読・解除する。  
`ObservableCollection.Clear()` は `Reset` 通知を送り `OldItems` が null になるため、`UpdateTextBlocksForCurrentPage()` の `Clear()` 前に手動で全件解除する。

```csharp
// ─ フィールド宣言（ResultViewModel クラス先頭に追加）─
private Dictionary<string, (ReviewStatus ReviewStatus, string? EditedText)> _reviewStateCache = new();

// コンストラクタに追加
TextBlocks.CollectionChanged += OnTextBlocksCollectionChanged;
foreach (var opt in JobStatusFilterOptions.Concat(ReviewStatusFilterOptions))
    opt.PropertyChanged += OnFilterOptionPropertyChanged;  // SelectableItem.IsSelected 変化を購読

// Add（TextBlocks.Add(vm)）で新 vm を購読、Remove で解除する
// Clear() は Action.Reset 通知（OldItems = null）を送るため Clear() 前に手動解除する（UpdateTextBlocksForCurrentPage() 参照）
private void OnTextBlocksCollectionChanged(object? sender, NotifyCollectionChangedEventArgs e)
{
    foreach (TextBlockViewModel vm in e.NewItems ?? (IList)Array.Empty<object>())
        vm.PropertyChanged += OnTextBlockPropertyChanged;
    foreach (TextBlockViewModel vm in e.OldItems ?? (IList)Array.Empty<object>())
        vm.PropertyChanged -= OnTextBlockPropertyChanged;
    // ✔ TextBlocks.Add(vm) → CollectionChanged(Add) → e.NewItems=[vm] → vm を購読
    // ✔ TextBlocks.Clear() → CollectionChanged(Reset) → OldItems=null（解除されない）
    //   → Clear() 前に UpdateTextBlocksForCurrentPage() 内で foreach で手動解除している
}

// ReviewStatus または Text（CompletedWithEdit 状態での再編集）変化時の処理
// ─ CompletedWithEdit のまま Text だけ変わるケース（再編集）は ReviewStatus が変化しない ─
// ─ その場合も edited_text をサーバーへ送る必要があるため Text 変化も監視する           ─
private void OnTextBlockPropertyChanged(object? sender, PropertyChangedEventArgs e)
{
    if (sender is not TextBlockViewModel changedTb) return;
    if (_isBatchUpdating) return;

    if (e.PropertyName == nameof(TextBlockViewModel.ReviewStatus))
    {
        OnPropertyChanged(nameof(FilteredJobHistory));
        OnPropertyChanged(nameof(IsFilteredEmpty));
        BulkCompleteUnreviewedCommand.NotifyCanExecuteChanged();
        _ = SaveCurrentReviewStatusAsync(changedTb);
    }
    else if (e.PropertyName == nameof(TextBlockViewModel.Text) &&
             changedTb.ReviewStatus == ReviewStatus.CompletedWithEdit)
    {
        // ReviewStatus は変わらず Text のみ変化（CompletedWithEdit → CompletedWithEdit の再編集）
        // edited_text が更新されるため PATCH を送信する
        _ = SaveCurrentReviewStatusAsync(changedTb);
    }
}

// UpdateTextBlocksForCurrentPage() の先頭に追加（Clear() 前に手動解除）
private void UpdateTextBlocksForCurrentPage()
{
    // Clear() は Reset 通知のため OldItems が null になる → Clear() 前に手動解除
    foreach (var tb in TextBlocks)
        tb.PropertyChanged -= OnTextBlockPropertyChanged;

    TextBlocks.Clear();
    // ...（既存処理）...
    TextEditing.SetTextBlocks(TextBlocks);
    OnPropertyChanged(nameof(FilteredTextBlocks));
    BulkCompleteUnreviewedCommand.NotifyCanExecuteChanged();  // ページ切替後に活性を更新
}

// Dispose() に追加
public override void Dispose()
{

    {
        ImageDisplay.PageChanged -= OnPageChanged;
        JobHistory.CollectionChanged -= OnJobHistoryCollectionChanged;
        TextBlocks.CollectionChanged -= OnTextBlocksCollectionChanged;    // 追加

            tb.PropertyChanged -= OnTextBlockPropertyChanged;             // 追加

}
```

#### 保存（SaveCurrentReviewStatusAsync）

TextBlock のステータスが変わるたびに `PATCH /v1/jobs/{job_id}/review-state` を呼び出す。  
`TextBlockKey`（`"{pageIndex}_{type}_{blockIndex}"`）を API パラメータに変換して送信する。

```csharp
private async Task SaveCurrentReviewStatusAsync(TextBlockViewModel tb)
{
    if (SelectedHistoryItem is null || tb.TextBlockKey is null) return;
    var item = SelectedHistoryItem;  // await 前にキャプチャ（ジョブ切替による上書きを防ぐ）
    var cache = _reviewStateCache;   // await 前にキャプチャ（ジョブ切替後に別インスタンスを汚染しない）

    try
    {
        // TextBlockKey "{pageIndex}_{type}_{blockIndex}" → API パラメータに変換
        var parts = tb.TextBlockKey.Split('_');
        var pageNo = int.Parse(parts[0]) + 1;  // pageIndex（0始まり）→ page_no（1始まり）
        var blockType = parts[1];
        var blockIndex = int.Parse(parts[2]);

        var response = await _reviewStateGateway.PatchReviewStateAsync(
            jobId: item.ReportIdValue,
            pageNo: pageNo,
            blockType: blockType,
            blockIndex: blockIndex,
            reviewStatus: tb.ReviewStatus.ToKey(),
            editedText: tb.ReviewStatus == ReviewStatus.CompletedWithEdit ? tb.Text : null
        );

        // サーバーが再集計した summary_status でバッジを更新
        // PatchReviewStateResponse.SummaryStatus は non-nullable（record 定義参照）のため
        // response 自体のみ null チェックする（SummaryStatus の二重チェック不要）
        if (response is not null)
            item.ReviewStatusKey = response.SummaryStatus;

        // キャプチャしたキャッシュ参照に書き戻す（ジョブ切替後の新キャッシュを汚染しない）
        // ReferenceEquals による別インスタンスへのマージは行わない（stale write のリスクがあるため）
        cache[tb.TextBlockKey] = (tb.ReviewStatus, tb.ReviewStatus == ReviewStatus.CompletedWithEdit ? tb.Text : null);
    }
    catch (OperationCanceledException) { }  // キャンセルは無視（ViewModelBase パターン）
    catch (Exception ex)
    {
        // TextBlock.ReviewStatus のロールバックは行わない（初版許容）
        ErrorMessage = $"レビュー状態の保存に失敗しました: {ex.Message}";
    }
}
```

`OnTextBlockPropertyChanged` からは変化した TextBlock を引数として渡し、fire-and-forget（`_ = SaveCurrentReviewStatusAsync(changedTb)`）で呼ぶ。`BulkCompleteUnreviewed` からは `await` で逐次呼び出す（§4-3 参照）。

#### 一括完了（BulkCompleteUnreviewed）

`_isNormalizing` と同じ再入防止パターンで `_isBatchUpdating` フラグを使い、一括変更中の `OnTextBlockPropertyChanged` による個別保存を抑止する。変更完了後に変化した N 件分の PATCH を **逐次送信**する（応答順不同によるバッジ巻き戻りを防ぐため。途中の PATCH が失敗しても残りを続行する）。

```csharp
private bool _isBatchUpdating;

[RelayCommand(CanExecute = nameof(CanBulkCompleteUnreviewed))]
private async Task BulkCompleteUnreviewed()
{
    // 確認ダイアログ表示後に実行
    ErrorMessage = null;  // 操作の起点で1回だけクリア（個別 PATCH ごとにはクリアしない）
    var changedBlocks = TextBlocks.Where(t => t.ReviewStatus == ReviewStatus.Unreviewed).ToList();
    _isBatchUpdating = true;
    try
    {
        foreach (var tb in changedBlocks)
            tb.ReviewStatus = ReviewStatus.Completed;
    }
    finally
    {
        _isBatchUpdating = false;
    }

    // _isBatchUpdating 中にスキップされた通知を補う（TextBlock.ReviewStatus 変化分）
    OnPropertyChanged(nameof(FilteredJobHistory));
    OnPropertyChanged(nameof(IsFilteredEmpty));
    BulkCompleteUnreviewedCommand.NotifyCanExecuteChanged();

    foreach (var tb in changedBlocks)
        await SaveCurrentReviewStatusAsync(tb);  // 逐次送信（並列 fire-and-forget にしない）

    // PATCH 完了後にバッジ（ReviewStatusKey）が更新されるため、フィルター結果を再更新
    OnPropertyChanged(nameof(FilteredJobHistory));
    OnPropertyChanged(nameof(IsFilteredEmpty));
}

private bool CanBulkCompleteUnreviewed() =>
    TextBlocks.Any(t => t.ReviewStatus == ReviewStatus.Unreviewed);
```

```csharp
// 例:「成功・失敗 かつ 未確認」「成功 かつ 2026/04/01 〜 2026/04/30」
public string FilterSummary
{
    get
    {
        var parts = new List<string>();

        // ジョブステータス部（日本語名で "・" 結合）
        var jobLabels = _statusFilters
            .Where(k => JobStatusKeys.Contains(k))
            .Select(k => k switch
            {
                "succeeded" => "成功", "failed" => "失敗",
                "running"   => "処理中", "queued" => "待機中",
                "canceled"  => "キャンセル", _ => k
            });
        var jobPart = string.Join("・", jobLabels);
        if (!string.IsNullOrEmpty(jobPart)) parts.Add(jobPart);

        // 確認ステータス部（日本語名で "・" 結合）
        var reviewLabels = _statusFilters
            .Where(k => ReviewStatusKeys.Contains(k))
            .Select(k => k == "completed" ? "完了" : "未確認");
        var reviewPart = string.Join("・", reviewLabels);
        if (!string.IsNullOrEmpty(reviewPart)) parts.Add(reviewPart);

        // 投入日部
        if (DateFrom.HasValue || DateTo.HasValue)
        {
            var from = DateFrom.HasValue ? DateFrom.Value.ToString("yyyy/MM/dd") : "〜";
            var to   = DateTo.HasValue   ? DateTo.Value.ToString("yyyy/MM/dd")   : "〜";
            parts.Add(DateFrom.HasValue && DateTo.HasValue
                ? $"{from} 〜 {to}"
                : DateFrom.HasValue ? $"{from} 以降" : $"{to} 以前");
        }

        return string.Join(" かつ ", parts);
    }
}
```

## 8. 懸念点・確認事項

| 項目 | 内容 | 対応方針 |
|------|------|---------|
| **Undo / ResetAllEdits 後の ReviewStatus 同期** | Undo でテキストを元に戻したとき、または `ResetAllEdits()` で全テキストをリセットしたとき、テキストが元の OCR 結果と一致するなら `CompletedWithEdit` → `Unreviewed` に自動遷移すべき | `SetTextWithoutTracking()`（Undo/Redo 経路）と `ResetToOriginal()`（全リセット経路）に `CommitEdit()` と同じ遷移ロジックを追加して解消する（§6-2 参照） |
| **確認ダイアログの実装方法** | 「すべて完了にする」と `CompletedWithEdit` からの「未確認に戻す」で YesNo 確認ダイアログが必要。アプリ全体に既存の YesNo ダイアログパターンがなく、新規実装となる | `ResultView.xaml.cs` の code-behind で `MessageBox.Show(message, title, MessageBoxButton.YesNo)` を呼び、`MessageBoxResult.Yes` のときにコマンドを実行する（「すべて完了」→ `BulkCompleteUnreviewedCommand`、「未確認に戻す」→ `MarkUnreviewedCommand`） |
| **未ロードジョブのバッジ表示** | `Succeeded` ジョブを一度も開いていない場合、`summaryStatus` は `GET /v1/jobs` レスポンスの値（`"unreviewed"`）が表示される | 許容する（開いていないジョブは確認されていないため「未確認」は正しい） |
| **フィルターパネルを開いたまま別ジョブを選択した場合** | `IsFilterPanelVisible` は `true` のまま残り、フィルターパネルが開いたまま表示が切り替わる | `OnSelectedHistoryItemChanged` で `IsFilterPanelVisible = false` にリセットする方向で実装時に判断する |
| **`SaveCurrentReviewStatusAsync()` の呼び出し頻度** | TextBlock のステータス変更のたびに `PATCH /v1/jobs/{job_id}/review-state` を呼び出す。連続操作時にリクエストが繰り返し発生する | 初版では許容し、性能問題が生じた場合は遅延送信（デバウンス）を検討する |
| **ページ未遷移時のバッジ集計** | バッジ更新は `PATCH` レスポンスの `summary_status`（全ページ集計済み）を使うため、未表示ページのブロックも含めた正しい値が返る | サーバー側の再集計により解消。クライアント側での TextBlocks 走査は不要 |
| **フィルターパネル表示中のショートカット抑止** | `_isDateFilterVisible` → `_isFilterPanelVisible` への置き換え時に、XAML の `Escape` キーバインドと `CanUseKeyShortcut()` の参照先も合わせて変更する必要がある | §6 に明記済み。実装時にチェックリストとして確認する |
| **レビュー実施者の記録なし** | 現バージョンはユーザー認証基盤がないため `t_job_block_review_set` に実施者情報を持てない。マルチユーザー環境で「誰が確認したか」の監査ができない | 認証機能を追加した際に `reviewer_user_id` カラムの追加を検討する。初版では対応しない |
| **FilePath が null のジョブの画像表示** | メール経由ジョブ等で `FilePath = null` の場合、`ImageDisplayViewModel.SourceImagePath` に null を渡すことになる。`ImageDisplayViewModel` が null を受け取ったときの挙動（画像クリア or 前回画像を維持）を確認・仕様化する必要がある | `ImageDisplayViewModel` が `SourceImagePath = null` をセットされたとき画像をクリアする実装を確認し、必要に応じて対応する。FilePath が null のジョブを選択した場合は「画像なし」状態にする |
| **LoadJobHistoryAsync の呼び出し元変更** | コンストラクタで `LoadJobHistory()` を `_ = LoadJobHistoryAsync()` に変更するため、起動時のジョブ一覧表示がわずかに遅延する。API が応答しない場合に一覧が空になるリスクがある | 初版では許容する。エラー時は `ExecuteWithLoadingAsync` 等の既存エラーハンドリングで対応し、一覧が取得できない旨をユーザーに通知する |
