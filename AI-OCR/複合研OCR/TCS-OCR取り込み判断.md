# TCS-OCR 取り込み判断（販売OCRシステム）

販売OCR の機能を TCS-OCR にどう取り込むかの判断資料。
TCS-OCR 既存実装の調査結果と突き合わせて 3 分類で整理する。
仕様メモは `販売OCRシステム.md` を参照。

---

## 分類軸

| 分類 | 意味 |
| --- | --- |
| **拡張** | TCS-OCR の既存機能を土台に、一部追加すれば実現できる |
| **新規** | TCS-OCR に該当機能がなく、新しく作る必要がある |
| **確認** | 仕様が曖昧で、実装判断の前に要件追加調査が必要 |

完全に既存機能でカバーできる項目は本資料から除外している。
何を除外したかは末尾「判断から外した項目」に記録する。

### 分類サマリ

- **拡張（7 件）**
  - 1. 業務 OK / NG 判定
  - 2. TIFF（OCR 入力画像）の業務識別子リネーム保存
  - 3. バウンディングボックスの「業務エラー赤枠」表示
  - 4. マスタ参照 UI（ポップアップ）
  - 5. 修正履歴ログ出力（監査トレイル）
  - 6. エラー時のページ遷移ガード
  - 7. 画像ビューアの拡大・縮小・ドラッグ移動
- **新規（5 件）**
  - 8. 業務エラーチェックロジック群（ID 存在 / 店番 Mod10 / `?` 混入 / 入力不備）
  - 9. マスタ DB / API（店舗・商品台帳）
  - 10. 汎用データ作成（基幹システム向け変換）
  - 11. 外部システムへのデータ転送（FTP / SFTP / REST API）
  - 12. データ保持期間管理 / 自動削除
- **確認（2 件）**
  - 13. 電子帳簿保存法対応
  - 14. 注文用紙テンプレート定義の移行スコープ

---

## 拡張（既存機能 + 一部追加）

### 1. 業務 OK / NG 判定
- 元仕様: 4-2 OK/NG データの分離
- 既存基盤:
  - レビューステータス `unreviewed` / `completed` / `completed_with_edit`（`a_job_review.summary_status`）が直近コミット `cb11d47` で導入済み
  - `api/jobs/domain/value_objects/review_status.py`
  - `db/alembic/versions/add_review_tables.py`
- 追加すべきこと:
  - 「業務 NG（基幹システムに送れない状態）」を表す値の追加（例: `rejected`）
  - 業務エラーチェック結果から自動で NG 状態に遷移させるロジック（チェックロジック本体は「新規」側）
- 補足: 既存の `summary_status` は「人が確認したか」を表す軸であり、「業務上送れるか」とは別軸。値の追加で済むか、別フィールドを切るかは設計時に判断。

### 2. TIFF（OCR入力画像）の業務識別子リネーム保存
- 元仕様: 4-2 / 4-3 TIFF 画像のリネーム保存（`年月日_注文用シートID_店番_OCR認識後.tiff`）
- 既存基盤:
  - `storage_root/inputs/{job_id}/` への入力ファイル保存は実装済み（`api/jobs/infrastructure/storage/file_storage.py`）
  - 保存形式は入力拡張子で分岐する：jpg/jpeg/bmp/webp/gif は PNG に変換して `original.png`、png はそのまま `original.png`、**それ以外（TIFF/PDF 含む）は変換せず元バイナリを `original.bin` として保存**（`api/shared/infrastructure/image_standardizer.py:7,68-71`）
  - つまり**販売OCR の入口である TIFF は、現状そのまま `original.bin` に保存される**（拡張子も業務識別子も付かない）
- 追加すべきこと:
  - 業務識別子（注文用シートID / 店番 / 日付）でのリネーム保存 or シンボリックリンク機能
  - 命名規約を設定で持つ仕組み
- 補足: TIFF を残すか PDF/A 等にするかは「確認 13: 電帳法対応」で別途決める。

### 3. バウンディングボックスの「業務エラー赤枠」表示
- 元仕様: 4-3 / 4-3-1 エラー箇所の赤枠表示・赤文字表示
- 既存基盤:
  - `BoundingBoxViewModel` で Confidence ベース（High / Medium / Low）の色分けは実装済み
  - `ConfidenceLevel`: `client/OcrViewer.Sdk/Domain/ValueObjects/Confidence.cs`
  - 描画は `ResultView.xaml:367-379` の `DataTrigger` で色分けされ、Low 信頼度は既に赤枠（`ErrorBrush`）
- 追加すべきこと:
  - 業務エラー（ID 不在 / Mod10 NG / `?` 混入 / 入力不備）を保持するデータモデル（エラー種別 + 対象項目 + 座標）
  - Confidence 色とは別軸の業務エラー色分け
  - 業務エラーがある行のフィルタ表示
- 補足: 描画基盤は流用可、ただし「OCR の自信なさ」と「業務上の不正」はデータモデルとして分離する必要あり。

### 4. マスタ参照 UI（ポップアップ）
- 元仕様: 4-3 マスタ参照（ID / 店番 / 品番の検索 UI）
- 既存基盤:
  - クイック辞書登録パネル `QuickDictionaryPanelViewModel`（`client/OcrViewer/Presentation/ViewModels/QuickDictionaryPanelViewModel.cs`）
  - 機能は「結果画面で選択したテキストを `ShowWithPatternAsync(pattern)` で受け取り、辞書エントリとして登録するポップアップ」。検索パネルではなく登録パネル
  - 流用できる UI 構造: 選択テキストをポップアップに渡す導線、ドロップダウンによる対象選択、パターン入力フィールド
- 追加すべきこと:
  - 「マスタ参照ポップアップ」を新規 ViewModel として作成（既存パネルの UI 構造をテンプレートとして参考）
  - 動作は登録ではなく「マスタに存在するか確認 / 値を取得して表示」
- 補足: マスタ DB / API そのものは「新規」側で別途必要。UI コンポーネントとしては新規作成だが、既存パネルの構造・配置・キーバインドをそのまま踏襲できるため「拡張」枠で扱う。

### 5. 修正履歴ログ出力（監査トレイル）
- 元仕様: 4-3 電帳法対応の修正履歴ログ出力（CSV）
- 既存基盤:
  - `t_job_block_review_set` は追記専用（INSERT のみ、UPDATE/DELETE 禁止）の操作履歴テーブル（`api/jobs/infrastructure/persistence/models/review_models.py:27`）
  - 各操作で「レビューステータス（`review_status`）」「修正後テキスト（`edited_text`）」「操作日時（`reviewed_at`）」が 1 行ずつ記録される
- 追加すべきこと:
  - **修正者（user_id）の保存**（現在のテーブルに列が無い）
  - **修正前の元 OCR テキストの保持**（現在は修正後テキストしか残らない）
  - CSV / JSON 形式での修正履歴エクスポート機能
- 補足: 「いつ・何に直したか」は取れるが、「誰が・何から直したか」は現状残らない。監査要件次第で列追加が必要。TCS-OCR の認証連携状況（user_id を取得できるか）次第で実装範囲が変わる → 着手前に「確認」へ昇格する可能性あり。

### 6. エラー時のページ遷移ガード
- 元仕様: 4-3-1 エラー時のページ移動禁止
- 既存基盤:
  - 「ジョブが成功するまで結果画面へ遷移できない」ガードが実装済み（実行中・失敗時・未着手時すべてブロック）
  - 実体: `JobMonitorViewModel.CanNavigateToResult => IsJobSucceeded`（`client/OcrViewer/Presentation/ViewModels/JobMonitorViewModel.cs:88`）
  - `ExecutionViewModel.CanNavigateToResult` は `JobMonitor.CanNavigateToResult` への委譲（`client/OcrViewer/Presentation/ViewModels/ExecutionViewModel.cs:45`）
- 追加すべきこと:
  - 「結果画面 → 後続画面（基幹送信 / 完了等）」の遷移可否を判定する仕組み（販売OCR が要求するのはこちらの方向）
  - 判定条件: レビュー未完了 / 業務エラー残あり / NG 状態
  - ガード発火時のメッセージ表示
- 補足: 既存の「結果画面に**入れる**条件」と、追加すべき「結果画面から**出る**条件」は別物。既存ガードは方向が逆なので、パターン（プロパティ + `NotifyPropertyChangedFor` + ボタン CanExecute）の流用にとどまる。

### 7. 画像ビューアの拡大・縮小・ドラッグ移動
- 元仕様: 4-3 データ確認画面の表示機能（拡大 / 縮小 / ドラッグ移動）
- 既存基盤と実態:
  - 拡大・縮小の**入口は存在する**：`ImageDisplayViewModel` に `ZoomIn` / `ZoomOut` / `FitToWindow` / `ActualSize` コマンドと `Ctrl+/-` / `Ctrl+0` / `Ctrl+1` キーバインドあり（`ImageDisplayViewModel.cs:156-186`、`ResultView.xaml:30-37`）
  - **ただし `ZoomLevel` が描画に結線されていない**：`ZoomLevel` の消費箇所は `ImageDisplayViewModel.cs` 内のみで、XAML 側に `ScaleTransform` / `LayoutTransform` 等のバインドが無い。画像は `Viewbox Stretch="Uniform" MaxWidth/Height=800` に固定フィット表示され、**ズーム操作をしても見た目は変わらない**（`ResultView.xaml:298-307`）
  - **ドラッグ移動（Pan）は未実装**：`ScrollViewer` のスクロールバー/ホイール操作のみで、マウスでつかんで動かす Pan のハンドラ・コマンド・オフセット制御は無い（`PanningMode` 設定も無し）
- 追加すべきこと:
  - `ZoomLevel` を `ScaleTransform` 等に結線して拡大・縮小を実際に効かせる（既存機能の未完部分の修正）
  - ドラッグ Pan の新規実装（マウスドラッグ → スクロールオフセット制御）
- 補足: 拡大・縮小は「半分作られているが効いていない」状態の修正、ドラッグ移動は新規追加。販売OCR が求める操作感（ホイール拡縮時の中心保持等）は実機確認のうえ詰める。

## 新規（TCS-OCR に該当なし）

### 8. 業務エラーチェックロジック群
- 元仕様: 4-3-1 エラーチェック項目
- 内訳:
  - ID 存在チェック（マスタ参照）
  - 店番 Mod10 チェック
  - 「?」文字チェック
  - 入力不備チェック（数量あって品番なし）
- 既存状況:
  - TCS-OCR の辞書機能は「誤読補正」用であり、マスタ存在チェックや値検証は実装されていない
  - 値の妥当性検証ロジックは現状無し（`modulus` / `checksum` / `?` 検出いずれも該当なし）
- 必要なもの:
  - チェッカ実装（4 種）
  - チェック結果を業務エラーとして保持するデータモデル（「拡張 3」と接続）

### 9. マスタ DB / API（店舗・商品台帳）
- 元仕様: 4-3 マスタ参照の参照先（`accdb` / `csv`）
- 既存状況: 存在しない（DB モデルに店舗・商品・取引先マスタは無い）
- 必要なもの:
  - 店舗マスタ / 商品マスタのテーブル定義 + 取込フロー
  - 参照 API
- 補足: マスタ参照 UI（拡張 4）と業務エラーチェック（新規 8）の両方が依存。

### 10. 汎用データ作成（基幹システム向け変換）
- 元仕様: 4-3 汎用データ作成
- 既存状況:
  - OCR 結果は `storage_root/results/{job_id}/result.json` に出るが、基幹システム向けへの変換は実装されていない
  - フィールド単位の型変換 `OutputTypeConverter`（text/number/date の正規化）は存在するが、これは個別項目の整形のみで、基幹システムのレコードレイアウト生成ではない
- 必要なもの:
  - 変換ルール定義（テンプレートごと）
  - 変換実行モジュール（レコード組み立て・マッピング・出力）
- 補足: 販売OCR の核心機能。これがないと OCR 結果を基幹システムに渡せない。

### 11. 外部システムへのデータ転送
- 元仕様: 4-3 FTP 転送
- 既存状況: 外部システム送信機能は無い（FTP / SFTP / 外部 POST いずれも該当なし）
- 必要なもの:
  - 送信プロトコル実装（FTP / SFTP / REST API 等、切替可能なアダプタ設計を推奨）
  - 非同期ワーカー + リトライ機構
  - 接続設定の管理 UI / 設定ファイル
- 補足: FTP は現代化対象（SFTP / API へ）。「FTP 限定」ではなくアダプタ層を切る前提で設計したい。

### 12. データ保持期間管理 / 自動削除
- 元仕様: 4-3 保存期間・自動削除（999 で無制限）
- 既存状況: 保存期間設定・自動削除は実装されていない（retention / TTL / スケジューラいずれも無し。ジョブ結果はソフト削除もできない）
- 必要なもの:
  - 保存期間設定（全体 / テンプレートごと / ジョブごと、粒度は要設計）
  - 期限切れデータ削除の定期ジョブ
- 補足: 電帳法対応との整合（10 年保存等）が必要 → 「確認 13」とセットで設計。

## 確認（要件定義が必要）

### 13. 電子帳簿保存法対応

**電子帳簿保存法（電帳法）とは**:
国税関係の帳簿・書類（注文書・請求書・領収書等）を電子データで保存する際のルールを定めた法律。
紙の代わりに電子保存するなら「後から改ざんできない」「決められた期間きちんと残す」「必要なときに検索して出せる」ことを求める。
販売OCR は注文書（取引書類）を扱うため、読み取った画像・データはこの法律の対象になりうる。

**主な要件（一般的な区分）**:
- **真実性の確保**: 改ざん防止。タイムスタンプの付与、または訂正・削除の履歴が残る仕組み
- **可視性の確保**: 検索性。取引年月日・取引金額・取引先での検索、ディスプレイ・書面への速やかな出力
- **保存期間**: 原則 7 年（欠損金がある事業年度等は最長 10 年）

販売OCR 仕様には「10 年保存」「TIFF リネーム」「親機 SQLite 登録」の 3 点が書かれているだけで、これだけでは上記の法令要件を満たすか判定できない。Phase 1 着手前に要件を詰める必要がある。

**TCS-OCR の現状（要件別）**:
現状、電帳法対応として設計された機能は無い。関係しそうな部品は別目的で作られたもの。

| 電帳法の要件 | TCS-OCR の現状 | 判定 |
| --- | --- | --- |
| 真実性（改ざん防止） | タイムスタンプは**アプリ内の処理時刻のみ**（`started_at` / `succeeded_at` / `reviewed_at`）。信頼できる時刻認証（TSA）・電子署名は無し | ❌ 未対応 |
| 真実性（訂正・削除履歴） | 修正履歴 `t_job_block_review_set` は**追記専用（INSERT のみ、UPDATE/DELETE 禁止）**で履歴は残る。ただし**「誰が」「修正前の元テキスト」は残らない** | △ 部分的 |
| 可視性（検索性） | ジョブ一覧はファイル名・日付・ステータスで絞り込み可。**「取引金額」「取引先」での検索は不可**（業務項目が構造化・索引化されていない） | ❌ ほぼ未対応 |
| 可視性（画面・書面出力） | 結果画面での表示は可。帳票としての出力・印刷機能は無し | △ 部分的 |
| 保存期間（7〜10 年） | **保存期間管理・自動削除のいずれも無し**（項目 12）。期限を意識した保存もソフト削除も不可 | ❌ 未対応 |

関連はあるが目的が違う部品:
- `input_hash`（入力ファイル SHA-256）あり。ただし用途は**重複検知**で改ざん検知ではない
- ファイル保存はあるが、**TIFF は変換も改名もされず `original.bin` として置かれるだけ**（命名規約・長期保存設計なし）
- DB は PostgreSQL（親機 SQLite より堅牢ではあるが、それ自体が電帳法対応を意味しない）

確認すべきこと:
- 対象範囲: どのデータ / どの画像が電帳法対象か
- 保存形式: PDF/A 等の指定有無
- 検索性: 日付 / 取引先 / 金額等での検索可否
- 訂正・削除履歴: 既存レビューステータス + 修正履歴ログ（拡張 5）で要件を満たすか
- タイムスタンプ / 改ざん防止: 必要な方式（電子署名 / ハッシュチェーン等）
- 保存先: ローカルストレージ / クラウドストレージ（S3 / Azure Blob）の選定

要件が固まれば以降は「新規」へ。

### 14. 注文用紙テンプレート定義の移行スコープ
- 4-1（注文用紙作成・印刷）は取り込まない方針だが、注文用紙のレイアウト情報（注文用紙 ID / 店番 / 品番が紙のどこに印字されるか）は OCR 側で必要
- TCS-OCR の `templates` ドメイン（`m_template_region` / `a_template_region`、正規化座標 0.0-1.0）に格納すれば技術的には対応可能（格納能力は確認済み、ただし一括取込ツールは無い）

確認すべきこと:
- 既存の販売OCR 構成マスタ（ACODB）データを `templates` に移行するか、TCS-OCR 上で手動再作成するか
- 移行する場合の変換スクリプト要否
- テンプレート種別（注文用紙の版・店舗バリエーション）の管理粒度

## 取り込まない

| 機能 | 理由 |
| --- | --- |
| 4-1 注文用紙作成・プレ印刷 | OCR の前工程の別業務。OCR を動かすには不要、実装コスト大、OCR 本体への影響ゼロ。事業として必要と決まってから別フェーズで検討（注文用紙のテンプレート定義移行のみ「確認 14」で扱う） |
| OCR 後の自動印刷 | 紙利用は顧客次第。標準装備にする必要なし。運用が固まってから足せばよい |
| 二重 FAX 対応 | 元の販売OCR でも未対応と明記。FAX 機器側で運用回避すべき問題で、OCR ソフトで解くものではない |

## 判断から外した項目（既存機能で完全にカバー）

以下は TCS-OCR 既存実装で完全にカバーされているため、本資料の判断対象から外した。
判断の妥当性を検証する際の参考に記録する。

| 販売OCR の機能 | TCS-OCR 既存実装 |
| --- | --- |
| OCR 認識処理本体 | `engines` モジュール（Azure DI / Google DAI / PaddleOCR / YomiToku / Gemini / Qwen VL 等） |
| OCR エンジン選択 | ジョブ作成時に `engine_id` 指定可能 |
| テンプレート選択 | ジョブ作成時に `template_id` 指定可能 |
| 辞書（共通 / 領域別）による誤読補正 | `dictionaries` モジュール、`r_dictionary_region` で領域割り当て |
| 画像補正（回転 / 傾き / ノイズ除去） | OCR エンジン側で実施（TCS-OCR から見ると `engines` モジュールに委譲済み） |
| 中間データの保存 | `storage_root/{inputs,raw,results,logs}/{job_id}/`。生レスポンス・結果・エラーは `raw.json` / `result.json` / `error.json`。入力は拡張子で分岐（PNG 変換 or `original.bin`、詳細は拡張 2） |
| マウス・キーボード操作両対応 | 全画面でキーバインド対応、マウス操作も標準対応 |
