# TCS-OCR取り込み判断（販売OCRシステム）

販売OCRの機能をTCS-OCRにどう取り込むかの判断資料。
TCS-OCR既存実装の調査結果と突き合わせて3分類で整理する。
仕様メモは`販売OCRシステム.md`を参照。

---

## 分類軸

| 分類 | 意味 |
| --- | --- |
| **拡張** | TCS-OCRの既存機能を土台に、一部追加すれば実現できる |
| **新規** | TCS-OCRに該当機能がなく、新しく作る必要がある |
| **確認** | 仕様が曖昧で、実装判断の前に要件追加調査が必要 |

完全に既存機能でカバーできる項目は本資料から除外している。
何を除外したかは末尾「判断から外した項目」に記録する。

### 分類サマリ

- **拡張（7件）**
  - 1. 業務OK / NG判定
  - 2. TIFF（OCR入力画像）の業務識別子リネーム保存
  - 3. バウンディングボックスの「業務エラー赤枠」表示
  - 4. マスタ参照UI（ポップアップ）
  - 5. 修正履歴ログ出力（監査トレイル）
  - 6. エラー時のページ遷移ガード
  - 7. 画像ビューアの拡大・縮小・ドラッグ移動
- **新規（5件）**
  - 8. 業務エラーチェックロジック群（ID存在 / 店番Mod10 / `?` 混入 / 入力不備）
  - 9. マスタDB / API（店舗・商品台帳）
  - 10. 汎用データ作成（基幹システム向け変換）
  - 11. 外部システムへのデータ転送（FTP / SFTP / REST API）
  - 12. データ保持期間管理 / 自動削除
- **確認（2件）**
  - 13. 電子帳簿保存法対応
  - 14. 注文用紙テンプレート定義の移行スコープ

---

## 拡張

### 1. 業務OK / NG判定
- 元仕様: 4-2 OK/NGデータの分離
- 既存基盤:
  - レビューステータス `unreviewed` / `completed` / `completed_with_edit`（`a_job_review.summary_status`）導入済み
  - `api/jobs/domain/value_objects/review_status.py`
  - `db/alembic/versions/add_review_tables.py`
- 追加すべきこと:
  - 「業務NG（基幹システムに送れない状態）」を表す値の追加（例: `rejected`）
  - 業務エラーチェック結果から自動でNG状態に遷移させるロジック（チェックロジック本体は「新規」側）
- 補足: 既存の `summary_status` は「人が確認したか」を表す軸であり、「業務上送れるか」とは別軸。値の追加で済むか、別フィールドを切るかは設計時に判断。

### 2. TIFF（OCR入力画像）の業務識別子リネーム保存
- 元仕様: 4-2 / 4-3 TIFF画像のリネーム保存（`年月日_注文用シートID_店番_OCR認識後.tiff`）
- 既存基盤:
  - `storage_root/inputs/{job_id}/` への入力ファイル保存は実装済み（`api/jobs/infrastructure/storage/file_storage.py`）
  - 保存形式は入力拡張子で分岐する：jpg/jpeg/bmp/webp/gifはPNGに変換して `original.png`、pngはそのまま `original.png`、それ以外（TIFF/PDF含む）は変換せず元バイナリを `original.bin` として保存（`api/shared/infrastructure/image_standardizer.py:7,68-71`）
  - つまり販売OCRの入口であるTIFFは、現状そのまま `original.bin` に保存される（拡張子も業務識別子も付かない）
- 追加すべきこと:
  - 業務識別子（注文用シートID / 店番 / 日付）でのリネーム保存orシンボリックリンク機能
  - 命名規約を設定で持つ仕組み
- 補足: TIFFを残すかPDF/A等にするかは「確認13: 電帳法対応」で別途決める。

### 3. バウンディングボックスの「業務エラー赤枠」表示
- 元仕様: 4-3 / 4-3-1エラー箇所の赤枠表示・赤文字表示
- 既存基盤:
  - `BoundingBoxViewModel` でConfidenceベース（High / Medium / Low）の色分けは実装済み
  - `ConfidenceLevel`: `client/OcrViewer.Sdk/Domain/ValueObjects/Confidence.cs`
  - 描画は `ResultView.xaml:367-379` の `DataTrigger` で色分けされ、Low信頼度は既に赤枠（`ErrorBrush`）
- 追加すべきこと:
  - 業務エラー（ID不在 / Mod10 NG / `?` 混入 / 入力不備）を保持するデータモデル（エラー種別 + 対象項目 + 座標）
  - Confidence色とは別軸の業務エラー色分け
  - 業務エラーがある行のフィルタ表示
- 補足: 描画基盤は流用可、ただし「OCRの自信なさ」と「業務上の不正」はデータモデルとして分離する必要あり。

### 4. マスタ参照UI（ポップアップ）
- 元仕様: 4-3マスタ参照（ID / 店番 / 品番の検索UI）
- 既存基盤:
  - クイック辞書登録パネル `QuickDictionaryPanelViewModel`（`client/OcrViewer/Presentation/ViewModels/QuickDictionaryPanelViewModel.cs`）
  - 機能は「結果画面で選択したテキストを `ShowWithPatternAsync(pattern)` で受け取り、辞書エントリとして登録するポップアップ」。検索パネルではなく登録パネル
  - 流用できるUI構造: 選択テキストをポップアップに渡す導線、ドロップダウンによる対象選択、パターン入力フィールド
- 追加すべきこと:
  - 「マスタ参照ポップアップ」を新規ViewModelとして作成（既存パネルのUI構造をテンプレートとして参考）
  - 動作は登録ではなく「マスタに存在するか確認 / 値を取得して表示」
- 補足: マスタDB / APIそのものは「新規」側で別途必要。UIコンポーネントとしては新規作成だが、既存パネルの構造・配置・キーバインドをそのまま踏襲できるため「拡張」枠で扱う。

### 5. 修正履歴ログ出力（監査トレイル）
- 元仕様: 4-3電帳法対応の修正履歴ログ出力（CSV）
- 既存基盤:
  - `t_job_block_review_set` は追記専用（INSERTのみ、UPDATE/DELETE禁止）の操作履歴テーブル（`api/jobs/infrastructure/persistence/models/review_models.py:27`）
  - 各操作で「レビューステータス（`review_status`）」「修正後テキスト（`edited_text`）」「操作日時（`reviewed_at`）」が1行ずつ記録される
- 追加すべきこと:
  - 修正者（user_id）の保存（現在のテーブルに列が無い）
  - 修正前の元OCRテキストの保持（現在は修正後テキストしか残らない）
  - CSV / JSON形式での修正履歴エクスポート機能
- 補足: 「いつ・何に直したか」は取れるが、「誰が・何から直したか」は現状残らない。監査要件次第で列追加が必要。TCS-OCRの認証連携状況（user_idを取得できるか）次第で実装範囲が変わる → 着手前に「確認」へ昇格する可能性あり。

### 6. エラー時のページ遷移ガード
- 元仕様: 4-3-1エラー時のページ移動禁止
- 既存基盤:
  - 「ジョブが成功するまで結果画面へ遷移できない」ガードが実装済み（実行中・失敗時・未着手時すべてブロック）
  - 実体: `JobMonitorViewModel.CanNavigateToResult => IsJobSucceeded`（`client/OcrViewer/Presentation/ViewModels/JobMonitorViewModel.cs:88`）
  - `ExecutionViewModel.CanNavigateToResult` は `JobMonitor.CanNavigateToResult` への委譲（`client/OcrViewer/Presentation/ViewModels/ExecutionViewModel.cs:45`）
- 追加すべきこと:
  - 「結果画面 → 後続画面（基幹送信 / 完了等）」の遷移可否を判定する仕組み（販売OCRが要求するのはこちらの方向）
  - 判定条件: レビュー未完了 / 業務エラー残あり / NG状態
  - ガード発火時のメッセージ表示
- 補足: 既存の「結果画面に入れる条件」と、追加すべき「結果画面から出る条件」は別物。既存ガードは方向が逆なので、パターン（プロパティ + `NotifyPropertyChangedFor` + ボタンCanExecute）の流用にとどまる。

### 7. 画像ビューアの拡大・縮小・ドラッグ移動
- 元仕様: 4-3データ確認画面の表示機能（拡大 / 縮小 / ドラッグ移動）
- 既存基盤と実態:
  - 拡大・縮小の入口は存在する：`ImageDisplayViewModel` に `ZoomIn` / `ZoomOut` / `FitToWindow` / `ActualSize` コマンドと `Ctrl+/-` / `Ctrl+0` / `Ctrl+1` キーバインドあり（`ImageDisplayViewModel.cs:156-186`、`ResultView.xaml:30-37`）
  - ただし `ZoomLevel` が描画に結線されていない：`ZoomLevel` の消費箇所は `ImageDisplayViewModel.cs` 内のみで、XAML側に `ScaleTransform` / `LayoutTransform` 等のバインドが無い。画像は `Viewbox Stretch="Uniform" MaxWidth/Height=800` に固定フィット表示され、ズーム操作をしても見た目は変わらない（`ResultView.xaml:298-307`）
  - ドラッグ移動（Pan）は未実装：`ScrollViewer` のスクロールバー/ホイール操作のみで、マウスでつかんで動かすPanのハンドラ・コマンド・オフセット制御は無い（`PanningMode` 設定も無し）
- 追加すべきこと:
  - `ZoomLevel` を `ScaleTransform` 等に結線して拡大・縮小を実際に効かせる（既存機能の未完部分の修正）
  - ドラッグPanの新規実装（マウスドラッグ → スクロールオフセット制御）
- 補足: 拡大・縮小は「半分作られているが効いていない」状態の修正、ドラッグ移動は新規追加。販売OCRが求める操作感（ホイール拡縮時の中心保持等）は実機確認のうえ詰める。

## 新規

### 8. 業務エラーチェックロジック群
- 元仕様: 4-3-1エラーチェック項目
- 内訳:
  - ID存在チェック（マスタ参照）
  - 店番Mod10チェック
  - 「?」文字チェック

### 10. 汎用データ作成（基幹システム向け変換）
- 元仕様: 4-3汎用データ作成
- 既存状況:
  - OCR結果は `storage_root/results/{job_id}/result.json` に出るが、基幹システム向けへの変換は実装されていない
  - フィールド単位の型変換 `OutputTypeConverter`（text/number/dateの正規化）は存在するが、これは個別項目の整形のみで、基幹システムのレコードレイアウト生成ではない
- 必要なもの:
  - 変換ルール定義（テンプレートごと）
  - 変換実行モジュール（レコード組み立て・マッピング・出力）
- 補足: 販売OCRの核心機能。これがないとOCR結果を基幹システムに渡せない。

### 11. 外部システムへのデータ転送
- 元仕様: 4-3 FTP転送
- 既存状況: 外部システム送信機能は無い（FTP / SFTP / 外部POSTいずれも該当なし）
- 必要なもの:
  - 送信プロトコル実装（FTP / SFTP / REST API等、切替可能なアダプタ設計を推奨）
  - 非同期ワーカー + リトライ機構
  - 接続設定の管理UI / 設定ファイル
- 補足: FTPはそのまま使うのではなくSFTP / REST APIへの置き換えを前提にする。「FTP限定」ではなくアダプタ層を切る設計にしたい。

### 12. データ保持期間管理 / 自動削除
- 元仕様: 4-3保存期間・自動削除（999で無制限）
- 既存状況: 保存期間設定・自動削除は実装されていない（retention / TTL / スケジューラいずれも無し。ジョブ結果はソフト削除もできない）
- 必要なもの:
  - 保存期間設定（全体 / テンプレートごと / ジョブごと、粒度は要設計）
  - 期限切れデータ削除の定期ジョブ
- 補足: 電帳法対応との整合（10年保存等）が必要 → 「確認13」とセットで設計。

## 確認

### 13. 電子帳簿保存法対応

電子帳簿保存法（略して電帳法）は、国税関係の帳簿・書類（注文書・請求書・領収書等）を電子データで保存する際のルールを定めた法律。
紙の代わりに電子保存するなら「後から改ざんできない」「決められた期間きちんと残す」「必要なときに検索して出せる」ことが求められる。
販売OCRは注文書（取引書類）を扱うため、読み取った画像・データはこの法律の対象になりうる。

主な要件は次の3つ。

- 真実性の確保 ― 改ざん防止。タイムスタンプの付与、または訂正・削除の履歴が残る仕組み
- 可視性の確保 ― 取引年月日・取引金額・取引先での検索、ディスプレイ・書面への速やかな出力
- 保存期間 ― 原則7年（欠損金がある事業年度等は最長10年）

販売OCR仕様には「10年保存」「TIFFリネーム」「親機SQLite登録」の3点が書かれているだけで、これだけでは上記の法令要件を満たすか判定できない。Phase 1着手前に要件を詰める必要がある。

TCS-OCRには現状、電帳法対応として設計された機能は無い。関係しそうな部品も別目的で作られたものなので、要件別の対応状況は次のとおり。

| 電帳法の要件 | TCS-OCRの現状 | 判定 |
| --- | --- | --- |
| 真実性（改ざん防止） | タイムスタンプはアプリ内の処理時刻のみ（`started_at` / `succeeded_at` / `reviewed_at`）。信頼できる時刻認証（TSA）・電子署名は無し | 未対応 |
| 真実性（訂正・削除履歴） | 修正履歴 `t_job_block_review_set` は追記専用（INSERTのみ、UPDATE/DELETE禁止）で履歴は残る。ただし「誰が」「修正前の元テキスト」は残らない | 部分的 |
| 可視性（検索性） | ジョブ一覧はファイル名・日付・ステータスで絞り込み可。「取引金額」「取引先」での検索は不可（業務項目が構造化・索引化されていない） | ほぼ未対応 |
| 可視性（画面・書面出力） | 結果画面での表示は可。帳票としての出力・印刷機能は無し | 部分的 |
| 保存期間（7〜10年） | 保存期間管理・自動削除のいずれも無し（項目12）。期限を意識した保存もソフト削除も不可 | 未対応 |

関連はあるが目的が違う部品:
- `input_hash`（入力ファイルSHA-256）あり。ただし用途は重複検知で改ざん検知ではない
- ファイル保存はあるが、TIFFは変換も改名もされず `original.bin` として置かれるだけ（命名規約・長期保存設計なし）
- DBはPostgreSQL（親機SQLiteより堅牢ではあるが、それ自体が電帳法対応を意味しない）

確認すべきこと:
- 対象範囲: どのデータ / どの画像が電帳法対象か
- 保存形式: PDF/A等の指定有無
- 検索性: 日付 / 取引先 / 金額等での検索可否
- 訂正・削除履歴: 既存レビューステータス + 修正履歴ログ（拡張5）で要件を満たすか
- タイムスタンプ / 改ざん防止: 必要な方式（電子署名 / ハッシュチェーン等）
- 保存先: ローカルストレージ / クラウドストレージ（S3 / Azure Blob）の選定

要件が固まれば以降は「新規」へ。

### 14. 注文用紙テンプレート定義の移行スコープ
- 4-1（注文用紙作成・印刷）は取り込まない方針だが、注文用紙のレイアウト情報（注文用紙ID / 店番 / 品番が紙のどこに印字されるか）はOCR側で必要
- TCS-OCRの `templates` ドメイン（`m_template_region` / `a_template_region`、正規化座標0.0-1.0）に格納すれば技術的には対応可能（格納能力は確認済み、ただし一括取込ツールは無い）

確認すべきこと:
- 既存の販売OCR構成マスタ（ACODB）データを `templates` に移行するか、TCS-OCR上で手動再作成するか
- 移行する場合の変換スクリプト要否
- テンプレート種別（注文用紙の版・店舗バリエーション）の管理粒度

## 取り込まない

| 機能 | 理由 |
| --- | --- |
| 4-1注文用紙作成・プレ印刷 | OCRの前工程の別業務。OCRを動かすには不要、実装コスト大、OCR本体への影響ゼロ。事業として必要と決まってから別フェーズで検討（注文用紙のテンプレート定義移行のみ「確認14」で扱う） |
| OCR後の自動印刷 | 紙利用は顧客次第。標準装備にする必要なし。運用が固まってから足せばよい |
| 二重FAX対応 | 元の販売OCRでも未対応と明記。FAX機器側で運用回避すべき問題で、OCRソフトで解くものではない |

## 判断から外した項目（既存機能で完全にカバー）

以下はTCS-OCR既存実装で完全にカバーされているため、本資料の判断対象から外した。
判断の妥当性を検証する際の参考に記録する。

| 販売OCRの機能 | TCS-OCR既存実装 |
| --- | --- |
| OCR認識処理本体 | `engines` モジュール（Azure DI / Google DAI / PaddleOCR / YomiToku / Gemini / Qwen VL等） |
| OCRエンジン選択 | ジョブ作成時に `engine_id` 指定可能 |
| テンプレート選択 | ジョブ作成時に `template_id` 指定可能 |
| 辞書（共通 / 領域別）による誤読補正 | `dictionaries` モジュール、`r_dictionary_region` で領域割り当て |
| 画像補正（回転 / 傾き / ノイズ除去） | OCRエンジン側で実施（TCS-OCRから見ると `engines` モジュールに委譲済み） |
| 中間データの保存 | `storage_root/{inputs,raw,results,logs}/{job_id}/`。生レスポンス・結果・エラーは `raw.json` / `result.json` / `error.json`。入力は拡張子で分岐（PNG変換or `original.bin`、詳細は拡張2） |
| マウス・キーボード操作両対応 | 全画面でキーバインド対応、マウス操作も標準対応 |
| データ修正画面のDB反映（店番修正等） | `PATCH /jobs/{job_id}/review-state` で同等のことを実現 |
| フォルダ監視（受信トリガ） | `folder_monitor` モジュール、globルール / 優先度 / 重複検知 |
| メール監視（受信トリガ） | `mail_monitor` モジュール、IMAPポーリング / 送信者パターン / 重複検知 |
| 親機SQLite | TCS-OCRは最初からPostgreSQL（移行不要） |
