# TCS-OCR取り込み判断（販売OCRシステム）

販売OCRの機能をTCS-OCRにどう取り込むかの判断資料。
TCS-OCR既存実装の調査結果と突き合わせて3分類で整理する。
仕様メモは`販売OCRシステム.md`を参照。

---

## 分類軸

| 分類 | 意味 |
| --- | --- |
| **拡張** | TCS-OCRの既存機能を土台に、一部追加すれば実現できる |
| **新規** | TCS-OCRに該当機能がなく、新しく作る必要がある |
| **確認** | 仕様が曖昧で、実装判断の前に要件追加調査が必要 |

完全に既存機能でカバーできる項目は本資料から除外している。
何を除外したかは末尾「判断から外した項目」に記録する。

### 分類サマリ

- **拡張（7件）**
  - 1. 業務OK / NG判定
  - 2. TIFF（OCR入力画像）の業務識別子リネーム保存
  - 3. バウンディングボックスの「業務エラー赤枠」表示
  - 4. マスタ参照UI（ポップアップ）
  - 5. 修正履歴ログ出力（監査トレイル）
  - 6. エラー時のページ遷移ガード
  - 7. 画像ビューアの拡大・縮小・ドラッグ移動
- **新規（5件）**
  - 8. 業務エラーチェックロジック群（ID存在 / 店番Mod10 / `?` 混入 / 入力不備）
  - 9. マスタDB / API（店舗・商品台帳）
  - 10. 汎用データ作成（基幹システム向け変換）
  - 11. 外部システムへのデータ転送（FTP / SFTP / REST API）
  - 12. データ保持期間管理 / 自動削除
- **確認（2件）**
  - 13. 電子帳簿保存法対応
  - 14. 注文用紙テンプレート定義の移行スコープ

---

## 拡張

### 1. 業務OK / NG判定
- 元仕様: 4-2 OK/NGデータの分離
- 業務NGとは:
  - OCRは成功し人も確認したが、業務ルール上そのまま基幹システムへ連携してはいけない状態を指す。
  - TCS-OCRが既に持つ「ジョブ失敗」「低信頼度（Confidence Low）」「未レビュー」とは別軸。これらが「読めたか」「OCRが自信あるか」「人が見たか」であるのに対し、業務NGは「中身が業務的に正しいか」を表す。
  - ジョブが成功していても発生しうる（`?`混入や業務エラーがあればNG）。ジョブ状態だけでは判定できない。
  - 判定条件は 4-3-1 のエラーチェック項目に対応:
    - ID: マスタに存在しないIDはNG
    - 店番: モジュラス10チェック不一致はNG
    - 「?」混入: OCRが読めず `?` が残っている場合はNG
    - 入力不備: 数量があるのに品番が無い場合はNG
  - 判定ロジック本体は「新規8」、参照先マスタは「新規9」。拡張1の守備範囲はNG状態を保持する枠とAPIまで。
  - 要確認（業務側）: NGは送信ブロック（修正必須）か警告（送信可）か / 項目ごとに重大度を分けるか / NG解除は再チェックで自動か人の明示OK宣言か。
- 既存基盤:
  - レビューステータス `unreviewed` / `completed` / `completed_with_edit`（`a_job_review.summary_status`）導入済み
  - `api/jobs/domain/value_objects/review_status.py`
  - `db/alembic/versions/add_review_tables.py`
- 追加すべきこと:
  - 「業務NG（基幹システムに送れない状態）」を表す状態の追加（既存 `summary_status` への値追加ではなく、別フィールドで管理。理由は後述の補足参照）
  - 業務エラーチェック結果から自動でNG状態に遷移させるロジック（チェックロジック本体は「新規」側）
- 補足（コード確認済み）: 既存の `summary_status` は「人が確認したか」を表す軸であり、「業務上送れるか」とは別軸。業務NGは同一フィールドへの値追加ではなく、別フィールドで持つべき。
  - 理由: `summary_status` は `patch_review_state_use_case.py:138-148` でブロック単位のレビュー状況から毎回再計算される派生値。同じフィールドに `rejected` 等を入れても、次のレビュー操作で `completed`/`unreviewed` に上書きされて消える。
  - コスト: `summary_status` はDB enum ではなく `String(20)` + null（`review_models.py:19`）なので、別フィールド追加は enum 型 ALTER 不要で安価（新列追加マイグレーションのみ）。

### 2. TIFF（OCR入力画像）の業務識別子リネーム保存
- 元仕様: 4-2 / 4-3 TIFF画像のリネーム保存（`年月日_注文用シートID_店番_OCR認識後.tiff`）
- 既存基盤:
  - 入力ファイル保存は実装済み（`api/jobs/infrastructure/storage/file_storage.py`）。ただし保存先は実IDフォルダではなく、一時ID `JobId(0)` のまま `storage_root/inputs/0/` に固定名で保存され、採番後も移動・`input_path` 更新がない（`create_job_use_case.py:147`、`job_repository_impl.py` の save）。raw/results/logs は実ID（`{job_id}/`）を使うので入力だけが例外。`inputs/0/` は全ジョブ共有・固定名のため並行投入で上書きされる既知バグあり（Codex確定、別途記録）
  - 保存形式は入力拡張子で分岐する：jpg/jpeg/bmp/webp/gifはPNGに変換して `original.png`、pngはそのまま `original.png`、それ以外（TIFF/PDF含む）は変換せず元バイナリを `original.bin` として保存（`api/shared/infrastructure/image_standardizer.py:7,68-71`）
  - つまり販売OCRの入口であるTIFFは、現状そのまま `original.bin` に保存される（拡張子も業務識別子も付かない）
- 追加すべきこと:
  - 業務識別子（注文用シートID / 店番 / 日付）でのリネーム保存orシンボリックリンク機能
  - 命名規約を設定で持つ仕組み
- 発見（コード確認）:
  - TIFFを変換しないのは意図的な設計。`image_standardizer.py:6` のコメントに「単一ページ画像のみ。PDF・TIFFはマルチページの可能性があるため除外」と明記され、`_CONVERT_TO_PNG_EXTENSIONS` にTIFF/PDFを含めていない。バグや未対応ではなく、複数ページを壊さないための保管。
  - リネームの材料のうち、日付・元拡張子は `m_job.original_filename`（`job_models.py:33`）＋作成日時（`:45`）から取れるが、注文用シートID・店番はOCR認識結果由来で、入力保存の時点には存在しない。形式末尾の `_OCR認識後` が示すとおり、命名はOCR完了後にしか行えない。なお店番・シートIDの抽出は既存のテンプレート領域抽出（`RegionExtractionResult`、`normalized_result.py:217-236`）が担うため新規10には依存しない。依存するのは、テンプレートに「店番」「シートID」等の名前付き領域が定義されていること（確認14のテンプレート移行）。
  - 現状は「1ジョブ＝1入力ファイル＝1 `original.bin`」。マルチページTIFF（FAX1通に複数シート）の場合、1ファイルに複数の業務識別子が対応し、`_シートID_店番_` の1シート前提が破綻する。
- 要確認（業務側）:
  - FAX1通＝注文用シート1枚か、複数枚混在ありか（マルチページTIFFの扱い）
  - リネームは実体を改名するか、`original.bin` を残して別名リンク/コピーを作るか（`original.bin` は拡張子も持たない正規保存物のため、別名を作る方が既存保存と衝突しない）
  - 命名のタイミング（OCR後 / 業務チェック後 / 送信時のどこで付けるか）
- 補足: TIFFを残すかPDF/A等にするかは「確認13: 電帳法対応」で別途決める（刷新候補#3も「TIFF→PDF/A」を推奨）。

### 3. バウンディングボックスの「業務エラー赤枠」表示
- 元仕様: 4-3 / 4-3-1エラー箇所の赤枠表示・赤文字表示
- 既存基盤:
  - `BoundingBoxViewModel` でConfidenceベース（High / Medium / Low）の色分けは実装済み
  - `ConfidenceLevel`: `client/OcrViewer.Sdk/Domain/ValueObjects/Confidence.cs`
  - 描画は `ResultView.xaml:382-393` の `DataTrigger` で色分けされ、Low信頼度は既に赤枠（`ErrorBrush`、391行目）。※従来 367-379 と記載していたが `feature/review-status` の改変で行番号がドリフト
- 追加すべきこと:
  - 業務エラー（ID不在 / Mod10 NG / `?` 混入 / 入力不備）を保持するデータモデル（エラー種別 + 対象項目 + 座標）
  - Confidence色とは別軸の業務エラー表示
  - 業務エラーがある行のフィルタ表示
- 発見（コード確認）:
  - 信頼度は枠線だけでなく背景の塗りも4色で表現済み（`ResultView.xaml:379-393`）。高=緑 `#20198754` / Unknown=青 / 中=黄 / 低=赤 `#20DC3545`。赤は枠線・背景とも低信頼度で使用済み。
  - 業務エラーを「赤背景」で示すと、低信頼の薄赤塗りと見分けがつかない。かつWPFのDataTriggerは同一プロパティを後勝ちで上書きするため、信頼度の塗りを消してしまい「信頼度＋業務エラーを重ねて表示」が成立しない（どちらか一方しか出せない）。
  - 業務エラーは店番・シートID等の業務項目（テンプレート領域）単位。既存の枠は行・単語・表（OCRブロック）単位で1:1とは限らず、赤枠を描く座標は新規8＋テンプレート領域に依存（拡張2と同様、描画基盤は流用可だがデータは他機能依存）。
- 設計判断（採用方針）:
  - 信頼度の枠線・背景はそのまま維持（さわらない）。
  - 業務エラーは枠とは別チャネルで重ねて表示する：⚠アイコンを枠に重ねる。エラー理由は枠内に詰め込まず、右パネル/一覧側に表示（「業務エラー行のフィルタ表示」と統合）。
  - 背景の赤塗りは低信頼の塗りと衝突するため原則不可。重大エラーに限り、赤の斜線ハッチング等、質感で区別できる形に留める。
- 要確認:
  - エラー理由の出し方（ツールチップ / 常時ラベル / 右パネル一覧）
  - 赤枠を描く座標の単位（OCRブロックかテンプレート領域か）
  - 業務エラー行フィルタの一覧UIの有無
- 補足: 描画基盤は流用可、ただし「OCRの自信なさ」と「業務上の不正」はデータモデルとして分離する必要あり。

### 4. マスタ参照UI（ポップアップ）
- 元仕様: 4-3マスタ参照（ID / 店番 / 品番の検索UI）
- 既存基盤:
  - クイック辞書登録パネル `QuickDictionaryPanelViewModel`（`client/OcrViewer/Presentation/ViewModels/QuickDictionaryPanelViewModel.cs`）
  - 機能は「結果画面で選択したテキストを `ShowWithPatternAsync(pattern)` で受け取り、辞書エントリとして登録するポップアップ」。検索パネルではなく登録パネル
  - 流用できるUI構造: 選択テキストをポップアップに渡す導線、ドロップダウンによる対象選択、パターン入力フィールド
- 追加すべきこと:
  - 「マスタ参照ポップアップ」を新規ViewModelとして作成（既存パネルのUI構造をテンプレートとして参考）
  - 動作は登録ではなく「マスタに存在するか確認 / 値を取得して表示」
- 発見（コード確認）:
  - 既存パネルの中核は登録（書き込み）。`RegisterAsync():135` が `CreateEntryAsync` を呼び辞書へCREATEする。マスタ参照に必要なのは逆向きの照会（読み取り：存在するか / 値は何か）で、動作が真逆。
  - 流用できるのは小窓のガワまで。開閉（`IsVisible` / `ShowWithPatternAsync` / `Close`）・結果画面からの選択テキスト受け渡し導線・ドロップダウン＋入力欄のレイアウトは流用可。中核アクション（登録→照会）・データ取得（`LoadDictionariesAsync`→マスタ検索）・結果表示（成功メッセージ→存在有無＋取得値）は新規。「拡張」枠だが中身はほぼ新規。
  - データ源は辞書ゲートウェイ `IDictionaryGatewayPort`（`:17`）。マスタ参照には新ポート＋マスタDB / API（新規9）が必要で、拡張4は新規9に依存する。
  - 4-3-1注記より、店番・入力不備のマスタ参照は「確認用途のみ」で自動存在チェックはしない。拡張4＝人が手動照会する確認UI、新規8のID存在チェック＝システムが自動でマスタ照合、で目的が異なる（両方とも新規9を叩く）。
- 要確認:
  - 検索キーと粒度（ID / 店番 / 品番を別ポップアップにするか、1つで対象切替か）
  - 照会の入出力（存在有無のみか、名称等の付随情報も返すか）
  - 新規9とのI/F（拡張4・新規8の両方が使うため、先に確定すると効率的）
- 補足: マスタDB / APIそのものは「新規」側で別途必要。UIコンポーネントとしては新規作成だが、既存パネルの構造・配置・キーバインドをそのまま踏襲できるため「拡張」枠で扱う。

### 5. 修正履歴ログ出力（監査トレイル）
- 元仕様: 4-3電帳法対応の修正履歴ログ出力（CSV）
- 既存基盤:
  - `t_job_block_review_set` は追記専用（INSERTのみ、UPDATE/DELETE禁止）の操作履歴テーブル（`api/jobs/infrastructure/persistence/models/review_models.py:27`）
  - 各操作で「レビューステータス（`review_status`）」「修正後テキスト（`edited_text`）」「操作日時（`reviewed_at`）」が1行ずつ記録される
- 追加すべきこと:
  - 修正者（user_id）の保存（現在のテーブルに列が無い）
  - 修正前の元OCRテキストの保持（現在は修正後テキストしか残らない）
  - CSV / JSON形式での修正履歴エクスポート機能
- 発見（コード確認）:
  - 「追記専用」はアプリ規約のみ。`save_block_review():519` が `session.add()`（INSERT）しかしないことで担保されているだけで、DBレベルの強制（トリガ / RULE / UPDATE・DELETE権限のREVOKE）は無い（db/配下に該当なし）。DBに直接触れば書き換え可能で、電帳法の「真実性（改ざん防止）」としては弱い。
  - 利用者認証が存在しない。usersテーブルも認証ミドルウェアも無い（grepでヒットする oauth / login はGoogle APIのservice account・IMAPログインで、アプリ利用者の認証とは別物）。クライアントも `AnonymousAuthenticationProvider` を使用（`client/OcrViewer.Sdk/Infrastructure/GatewayConfig/KiotaClientFactory.cs:75-77`）＝匿名前提。「修正者（user_id）」を記録する元情報源そのものが無く、認証機能の導入が前提になる。docの「確認へ昇格する可能性あり」は、コード確認の結果ほぼ確定。
- 分類の分解（一括で「拡張」ではない）:
  - CSV/JSONエクスポート → 拡張で可能（既存テーブルから出力するだけ）
  - 元OCRテキストの保持（何から直したか）→ 拡張で可能（列追加 or `result.json` との紐づけ。元テキストはstorageにある）
  - 修正者（誰が直したか）→ 認証が前提。認証が無い現状では実装不能（実質「確認」）
  - 改ざん防止の法的強度 → 確認13と連動（DB強制 / タイムスタンプ / ハッシュチェーン等の方式決定）
- 要確認:
  - 監査で「誰が」は必須要件か（必須なら認証導入が拡張5の前提）
  - 改ざん防止はどの強度まで求められるか（アプリ規約で足りるか、DB強制 / ハッシュチェーンまで要るか）→ 確認13
  - 元テキストは履歴行に持つか、`result.json` 参照で足りるか
- 補足: 「いつ・何に直したか」は取れるが、「誰が・何から直したか」は現状残らない。監査要件次第で列追加が必要。TCS-OCRの認証連携状況（user_idを取得できるか）次第で実装範囲が変わる → 着手前に「確認」へ昇格する可能性あり。

### 6. エラー時のページ遷移ガード
- 元仕様: 4-3-1エラー時のページ移動禁止
- 既存基盤:
  - 「ジョブが成功するまで結果画面へ遷移できない」ガードが実装済み（実行中・失敗時・未着手時すべてブロック）
  - 実体: `JobMonitorViewModel.CanNavigateToResult => IsJobSucceeded`（`client/OcrViewer/Presentation/ViewModels/JobMonitorViewModel.cs:88`）
  - `ExecutionViewModel.CanNavigateToResult` は `JobMonitor.CanNavigateToResult` への委譲（`client/OcrViewer/Presentation/ViewModels/ExecutionViewModel.cs:45`）
- 追加すべきこと:
  - 「結果画面 → 後続画面（基幹送信 / 完了等）」の遷移可否を判定する仕組み（販売OCRが要求するのはこちらの方向）
  - 判定条件: レビュー未完了 / 業務エラー残あり / NG状態
  - ガード発火時のメッセージ表示
- 発見（コード確認）:
  - 既存の入口ガードは1経路のみで正しい（当初「3経路中1経路しかガードされず穴がある」と書いたが撤回）。結果画面 `ResultViewModel` は一覧（`_jobHistory`、`GET /v1/jobs`、`:107,357`）と個別詳細（`LoadResultWithFileAsync(reportId)`、`:397`）を兼ねる。実行画面経由は特定ジョブの詳細を自動ロードするため `IsJobSucceeded` で止める必要があるが、メイン/メニュー経由（`MainWindowViewModel.NavigateToResults` / `MenuViewModel.NavigateToResults`）は一覧を開くだけで、同じガードを付けるのはむしろ誤り（直近実行が未成功だと一覧すら開けなくなる）。
  - 既存ガードは方向だけでなく判定材料も別物。既存は「入る」ガードで条件は `IsJobSucceeded`（`:88`、ジョブ成功＝システム状態）。必要なのは「出る」ガードで条件はレビュー完了＋業務エラー無し＋NGでない（拡張1の業務軸 / 新規8）。流用できるのはMVVMパターン（プロパティ＋`NotifyPropertyChangedFor`＋`CanExecute`）の骨格のみ。
  - 4-3-1原文は「該当エラーを修正するまで同一ページ外への移動はできない」。送信ボタンの抑止だけでなく、戻る / 一覧へ / 設定へ等あらゆる離脱の遮断を要求。離脱経路が複数あるため、単発の `CanExecute` を各所に足すより、ナビゲーション層で離脱を一括インターセプトする方式が安全。
  - 守るべき後続画面（基幹送信 / 完了）は新規11で未実装。出口ガードが守る遷移先がまだ存在しない。
- 設計論点（出口ガード）:
  - 「移動禁止」の範囲：前進（送信）だけ止めるか、4-3-1どおりあらゆる画面離脱を止めるか
  - 判定材料：レビュー完了＋業務エラー無し＋NGなし → 拡張1・新規8に依存
  - `ResultViewModel` は一覧と詳細が同居するため「出る」の定義が曖昧：画面ごと離脱を止めるのか、エラーのあるジョブ詳細から一覧表示に戻るのも止めるのか

### 13. 電子帳簿保存法対応

電子帳簿保存法（略して電帳法）は、国税関係の帳簿・書類（注文書・請求書・領収書等）を電子データで保存する際のルールを定めた法律。
紙の代わりに電子保存するなら「後から改ざんできない」「決められた期間きちんと残す」「必要なときに検索して出せる」ことが求められる。
販売OCRは注文書（取引書類）を扱うため、読み取った画像・データはこの法律の対象になりうる。

主な要件は次の3つ。

- 真実性の確保 ― 改ざん防止。タイムスタンプの付与、または訂正・削除の履歴が残る仕組み
- 可視性の確保 ― 取引年月日・取引金額・取引先での検索、ディスプレイ・書面への速やかな出力
- 保存期間 ― 原則7年（欠損金がある事業年度等は最長10年）

販売OCR仕様には「10年保存」「TIFFリネーム」「親機SQLite登録」の3点が書かれているだけで、これだけでは上記の法令要件を満たすか判定できない。Phase 1着手前に要件を詰める必要がある。

TCS-OCRには現状、電帳法対応として設計された機能は無い。関係しそうな部品も別目的で作られたものなので、要件別の対応状況は次のとおり。

| 電帳法の要件 | TCS-OCRの現状 | 判定 |
| --- | --- | --- |
| 真実性（改ざん防止） | タイムスタンプはアプリ内の処理時刻のみ（`started_at` / `succeeded_at` / `reviewed_at`）。信頼できる時刻認証（TSA）・電子署名は無し | 未対応 |
| 真実性（訂正・削除履歴） | 修正履歴 `t_job_block_review_set` は追記専用（INSERTのみ、UPDATE/DELETE禁止）で履歴は残る。ただし「誰が」「修正前の元テキスト」は残らない | 部分的 |
| 可視性（検索性） | ジョブ一覧はファイル名・日付・ステータスで絞り込み可。「取引金額」「取引先」での検索は不可（業務項目が構造化・索引化されていない） | ほぼ未対応 |
| 可視性（画面・書面出力） | 結果画面での表示は可。帳票としての出力・印刷機能は無し | 部分的 |
| 保存期間（7〜10年） | 保存期間管理・自動削除のいずれも無し（項目12）。期限を意識した保存もソフト削除も不可 | 未対応 |

関連はあるが目的が違う部品:
- `input_hash`（入力ファイルSHA-256）あり。ただし用途は重複検知で改ざん検知ではない
- ファイル保存はあるが、TIFFは変換も改名もされず `original.bin` として置かれるだけ（命名規約・長期保存設計なし）。さらに入力は全ジョブ共有の `inputs/0/` に固定名で保存され並行投入で上書きされうる（別記の既知バグ、Codex確定）ため、原本画像が確実に保存される保証が現状ない。これは電帳法の画像保存・真実性の前提を直接崩すので、対応前に修正が必要
- DBはPostgreSQL（親機SQLiteより堅牢ではあるが、それ自体が電帳法対応を意味しない）

確認すべきこと:
- 対象範囲: どのデータ / どの画像が電帳法対象か
- 保存形式: PDF/A等の指定有無
- 検索性: 日付 / 取引先 / 金額等での検索可否
- 訂正・削除履歴: 既存レビューステータス + 修正履歴ログ（拡張5）で要件を満たすか
- タイムスタンプ / 改ざん防止: 必要な方式（電子署名 / ハッシュチェーン等）
- 保存先: ローカルストレージ / クラウドストレージ（S3 / Azure Blob）の選定

要件が固まれば以降は「新規」へ。
